### 10.3.4 安装目录：用户侧删除、语义搬到构建器（用户 2026-11-01 拍板）

结论：**汉化页的「选择 PXC 安装目录」整块移除**，`gen.install_dir` 字段一起删；
**能力不消失** —— 构建器的按钮行新增一个并排入口「选择新版 PXC 路径」（`docs/01` §4.1.1），
那才是"指定另一份英文骨架"的真实使用者。

用户给的理由是"用户用不到英文模板，只需要对照表即可；而维护者知道英文表在哪"。
这个理由要拆成两半看，因为前半句在技术上不成立，后半句成立：

| 判断 | 成立吗 | 说明 |
| --- | --- | --- |
| "维护者知道英文表在哪" | ✅ 成立 | 构建器（`g_ovMode=1`）本来就有自己的 `gen.baseline`，维护者用它指定骨架目录，与普通用户的安装目录互不影响 |
| "只需要对照表即可" | ❌ 不成立 | `locale_generator::generate()` 的签名是 `generate(const Baseline& base, const Db& db, ...)` —— **骨架是必需入参**。对照表只有扁平的 `key → {en, zh}`（17019 条），它不含"哪个键属于哪个文件、是对象还是字符串、哪些是 bool/数字"这些结构信息；输出是分文件的层级 JSON，这些只能从骨架读 |

那为什么仍然可以删掉按钮？因为**它几乎总是自动推得出来**：

```
版本库里登记过 exe  →  installDirOfExe(exe)  ← 从 exe 路径上溯
                    →  data/locale/en → data/locale/sample locale
                    →  pack/locale.zip 的 en/（Steam 版没有 data/）
没登记 exe / 推不出  →  用户目录 Locale/en → 兜底规则
```

手动选只在两种情况下有用：一个 exe 都没登记、或想用另一份安装包的 en 骨架。**两种都是维护者场景，普通用户碰不到。**
所以删按钮是对的。

**代价与补偿（2026-11-03 更新：内置骨架已整份删除）**：退化链的尽头不再是"内置 1.22"，而是
**"一个能用的骨架都没有"**。这只可能由"一个 PXC 都没登记"或"登记的 exe 全被删"造成，
所以文案要给出可操作的一句话：

> 「没找到任何可用的英文骨架。请先在版本库登记你正在用的 PixelComposer.exe。」

`g_genStatus` 的失败分支保留，`note` 换成上面这句（现在写的是候选路径，用户看不懂）。
删内置骨架的理由（27 个退役节点在对照表里 0 条目）见 `docs/08` §8.1.4。

### 10.3.5 备份开关：界面上不存在，只活在 launcher.json（回答"放在哪了"）

用户问"你说的备份开关是什么，放在哪了" —— **它没有 UI，是我在 §10.3.3 里用词不准。**

实际结构（`store.h:53` 的 `BackupSettings`）：

```jsonc
// launcher.json
"backup": {
  "enabled": true,       // 要不要在跨版本打开前备份
  "crossMajor": true,    // 只在跨大版本时备份（false = 任何版本不一致都备份）
  "dir": ""              // 空 = <启动器目录>/pxc_backups
}
```

三个字段在 `app.cpp` 里只有两处消费者，都是**读**，没有一处 UI 写入：

| 位置 | 用途 |
| --- | --- |
| `backupDirPath()` | 算出备份目录（空串取默认） |
| `startProject(..., g_cfg.backup, ...)` | 决定这次打开要不要先备份（`shouldBackup(enabled, crossMajor, confidence, ...)`） |

所以要改它只能手改 `launcher.json`。这也解释了为什么 §10.3.3 那句话读起来别扭 ——
不存在"留原处"这回事，界面上压根没有入口。

**这版不动它**：备份是"跨版本打开会损坏工程"这条风险线的最后一道保险（用户多次强调过这条），
把它做成一个能关的开关，等于给用户一个把保险关掉的机会。要开的话建议做成三个档
（总是 / 仅跨大版本 / 关闭）而不是一个布尔，并且归到"备份"分组、配清楚的后果说明 —— 那是另一轮的事。

## 10.4 界面设置页

三项从上到下：界面缩放（滑块）、文本缩放（滑块）、主题色（颜色选择）。两个滑块都**脱手生效**。

### 10.4.1 界面缩放（滑块，脱手生效）

EUI 已有这条链路，而且是**等比缩放**（布局、控件、字号、间距一起放大）：

```
物理像素 ──÷(dpiScale × uiScale)──▶ 逻辑坐标 ──compose──▶ 逻辑尺寸
                                       ▲
                            渲染时 ×(dpiScale × uiScale) 回到物理
```

**定位改了：从"适配高分屏"改成"微调界面大小"。** 用户的原话是"既然已经叠加 DPI，那界面缩放改为滑块，
用于微调界面大小适应用户习惯"。这两件事的差别决定了范围：

| | 原来的定位（下拉） | 现在的定位（滑块） |
| --- | --- | --- |
| 想解决的 | 高分屏上字太小 | 同一块屏上，用户觉得默认大小偏大/偏小 |
| 合理范围 | 100%~400%，25% 一档 | **75%~200%，5% 一档** |
| 感知 | 一档一跳，跳得很大 | 连续微调，一次 5% 几乎无跳变 |

> 范围 75%~200% **已确认**（2026-11-01 第二轮，§10.8「两个数已定」）。
> 上限不能再高：`uiScale=2` 时窗口 screen 宽度已经是 2080（见 §10.4.1.1），1080p 屏放不下；
> 下限到 75% 时 1040/0.75 = 1387 逻辑宽，工作台卡片从 3 列变 4 列，再小就是"字小得看不清"，没意义。

| 项 | 取值 |
| --- | --- |
| 控件 | `components::slider`，`size(260, 22)`，右侧跟一行只读数值「125%」 |
| 范围 / 步长 | 0.75 ~ 2.00 / **0.05**（滑块是连续 float，落值时量化到 5%） |
| 默认 | 1.00 |
| 生效时机 | **脱手才生效**（为什么要脱手、`onChange` 为什么不够，见 §10.4.1.0） |
| 写盘 | 脱手 → 应用 → 确认保留后才写（回滚时不写） |

**为什么必须"脱手才生效"**（用户明确要求）：

`uiScale` 一变，`effectiveScale = dpiScale × uiScale` 就变，于是 `logicalWidth/Height` 变，
框架 `dsl_app_impl.h:327` 判 `logicalWidth != logicalWidth` 成立 → **整棵树重新 compose**。
再加窗口同步放大（`SetWindowPos`），拖动过程中每一帧都在重建布局 + 改窗口几何：滑块会抖，
而且在真机上窗口尺寸高频变化会反复触发 GL 视口重建。

所以拆成两段：

| 阶段 | 行为 |
| --- | --- |
| 拖动中 | 只更新右侧那个「125%」数字（纯文本，不碰 `uiScale`），滑块跟手 |
| 松手 | 1) 定值 → 2) 改窗口尺寸 → 3) 写 `uiScale` → 4) 弹确认条倒计时 |

#### 10.4.1.0 脱手回调从哪来（`onChange` 到底是什么时机）

第二轮你说"使用 `onChange` 即可，它只在滑块释放且数值发生改变时才触发"。**后半句对，前半句不对** ——
`onChange` 在拖动过程中就会持续触发，跟松不松手无关。这不是我推测，是六条能指着行号的证据：

| # | 位置 | 事实 |
| --- | --- | --- |
| 1 | `components/slider.h:62` | `SliderBuilder::onChange` 被塞进 `sliderState(...)` 的第 5 个参数 |
| 2 | `core/dsl.h:1902-1911` | 那个参数直接落到 `Element::onSliderValueChanged` |
| 3 | `core/runtime/runtime_update.h:577-598` | `setSliderValue()` 的判据是 `changed = !closeEnough(next, instance.value)`，**变了就回调**，`dragging` 只被记一笔，不参与判定 |
| 4 | `core/runtime/runtime_input.h:453-457` | 按下那一帧（`pressStarted`）就调 `updateRuntimeSlider(..., true)` —— 也就是说**点一下轨道立刻触发一次** |
| 5 | `core/runtime/runtime_input.h:492-495` | 按住期间每次指针移动都走同一条路 → **拖动中每变一次值触发一次** |
| 6 | `core/runtime/runtime_input.h:477-484` | 松手那一帧只做 `dragging = false`，**不回调任何东西**；如果这一帧值没变（按下去原地松开），连 `onChange` 都不会来 |

所以现成的语义是"**值变了就叫我**"，缺的正是"**松手了叫我一次**"。这两件事在缩放上不能混：
`uiScale` 一变就是整树 recompose + 改窗口几何（§10.4.1 上一段），拖动中每帧都做，界面会打滑。

**这条不用自己发明 —— 上游 vendored EUI 里已经有，而且已经在用。**

`components/slider.h` 带两个标注过的能力（来自另一个项目的实战补丁，`[BUILD k]` / `[BUILD m]`）：

| 能力 | 签名 | 实现 |
| --- | --- | --- |
| 松手钩子 `[BUILD k]` | `.onRelease(std::function<void()>)` | 在 `.hit` 元素上挂 `.onRelease([...](const auto&, const auto&){ cb(); })`。`Element::onRelease` 是现成的，`runtime_input.h:471` 的调用点排在 `:477` 滑块分支**之前**，所以拖到滑块外松手也会触发；`InteractionState::released`（`input_types.h:240-250`）只在"在该元素按下 + 抬起那一帧"为真 |
| 双击复位 `[BUILD m]` | `.default(float norm)` | `slider_internal` 用一张按 id 索引的 inline map 记"上次松手的位置与时间"，两次松手 <300ms 且位置差 <3% 就判定双击 → 用默认值再发一次 `onChange`，随后照常走 `onRelease` |

**本仓库已经对齐**：`EUI-NEO-main/components/slider.h` 换成了带这两个能力的版本（原来那份没有；diff 只有增补，
被替换的只有 `const std::function<void(float)> onChange = onChange_;` 一行）。`core/` 一行没动。

上游实战用法（`DLSS5-for-Image/src/gui.cpp:2782-2802`，界面缩放滑块，注释写的就是我们的场景）：

```cpp
components::slider(ui, "set.scale.s")
    .value((float)sel / (float)(N - 1))          // 位置由离散档位索引驱动
    .default((float)kDefault / (float)(N - 1))   // 双击回 100%
    .onChange([&st](float nv) {
        // 只把 nv 量化成档位、写进 pending，绝不在这里 apply
        st.uiScale = levels[round(nv * (N - 1))];
    })
    .onRelease([&st]() {
        applyAllSettings();   // 整树只重排这一次
        markDirty();
    })
```

它自己的注释把原因写死了：`Applying EUI's global uiScale mid-drag reflows the panel and moves the very slider
being dragged (jank). Commit happens in onRelease.` —— 和 §10.4.1 上面那段推理是同一个结论，只是人家已经踩过了。

> 回调带不带值？上游给的是 `void()`，值在 `onChange` 里自己存（"pending 值"本来就要存一份，否则拖动中
> 右侧那个「125%」数字没法更新）。所以不需要 `shared_ptr` 记最后值那一套，也不需要从 `PointerEvent.x`
> 反算 —— 后者尤其不能做：缩放一应用元素 frame 就变，反算出来的值和用户看到的对不上。

#### 10.4.1.1 窗口同步放大（含超屏回滚）

用户拍板：**缩放同时放大窗口**，并要求"提示窗口是否符合预期 + 倒计时，未确认则恢复"，
理由是"避免窗口过大超出屏幕无法恢复"。

窗口尺寸怎么算：`DslAppConfig::windowSize(1040, 720)` 是 **GLFW 的 screen coordinate**（不是物理像素，
系统 150% 时 1040 screen → 1560 framebuffer）。要让"逻辑视口保持 1040×720"，窗口 screen 尺寸应变成：

```
新宽 = 1040 × newScale      新高 = 720 × newScale
```

运行时改尺寸**不走框架**（`windowSize` 只在建窗时读一次，且 `dslAppConfig()` 是只读单例），
直接用主窗 HWND：

```cpp
HWND h = (HWND)pxc_nui::mainWindow();
if (IsZoomed(h)) { ShowWindow(h, SW_RESTORE); waitNotZoomed(h); }   // 最大化时 SetWindowPos 无效
SetWindowPos(h, nullptr, x, y, w, h, SWP_NOZORDER | SWP_NOACTIVATE);
```

> `SW_RESTORE` 是投递给目标线程的**异步**动作，调完立刻 `IsZoomed` 还是旧值 —— 这条坑在
> `pxc_reuse::waitRestored()` 里已经踩过并解决（`docs/03` §7.3.3），直接复用同样的轮询写法（≤1.5 s）。

**三件必做的事**：

| # | 做什么 | 为什么 |
| --- | --- | --- |
| 1 | 先算工作区上限：`MonitorFromWindow` + `GetMonitorInfo().rcWork`，宽高各自 `min(目标, 工作区)` | "防超屏"的第一道闸。夹过之后窗口一定在屏内，倒计时条一定看得见 |
| 2 | 放大后窗口**居中到当前显示器**（不保留左上角） | 从 2080 宽缩到 780 宽时保留左上角会贴在屏幕角落；居中在两个方向上都稳 |
| 3 | 确认条固定在**主窗左下角**（`16, 底边上 16`，560×72） | 见下方"为什么最后落在左下角" |

**倒计时回滚**：

| 项 | 取值 |
| --- | --- |
| 时长 | **10 秒**（2026-11-01 第二轮定为 10，§10.8） |
| 文案 | 「界面缩放已改为 150%（窗口 1560×1080）　这个大小合适吗？」+ 按钮「保留」/「恢复（10）」 |
| 确认 | 点「保留」，或倒计时归零前按回车 → 写盘 |
| 超时 / 点「恢复」 | 窗口尺寸 + `uiScale` + 滑块位置三者**一起**回旧值；**不写盘** |
| 期间能做什么 | 不拦任何操作。用户可以去别的页面点，条就一直在那儿倒数 |

> 为什么是"回滚"而不是"确认后才应用"：用户要看到 150% 到底长什么样才能判断合不合适。
> 先应用、不顺眼再自动撤销，比"先问愿不愿意试"少一次往返。

**为什么最后落在左下角，不是原定的左上角**（实现时改的，实测截图 `tmp/flow_applied.bmp`）：

左上角正好压住页面标题和设置页的页签（当时两枚，现已三枚）。这条要挂 10 秒，而 §10.4.1.1 上表又要求"期间不拦任何操作" ——
压住页签等于把那句话变成空话（用户想切回"通用"看别的设置都点不到）。

左下角同样满足"一定看得见"：**窗口尺寸是我们自己夹到工作区的**，所以底边必然在屏内；
而左上角方案担心的"右下角可能看不见"是另一种情形（窗口比屏幕大时右下角跑到屏外），夹取之后不会发生。
唯一要扣的常数是 `screen.height` 含标题栏（`docs/04` §8.11.2 那条坑），所以 `y = screen.height - 72 - 16 - 30`。

> 为什么"必须"同步放大窗口，不只是"观感更好"：实测 `uiScale=2` 而窗口保持 1040×720 时，
> 逻辑视口变 520×360，工作台按 520 宽重排（卡片 3 列 → 1 列），卡片里版本 pill 与日期直接叠字
> （截图 `tmp/uis_scale.bmp`）。**不放大窗口，2 倍缩放是不可用状态。**

**必须承认的边界**：夹到工作区之后，逻辑视口就不是 1040×720 了。
1920×1080 屏、系统 100%、选 200%：目标 2080×1440 → 夹到 1920×1040（工作区，已扣任务栏）
→ 逻辑视口 = 960×520。**缩放"成功"了，但界面还是只看到一部分。**
这不是 bug，是"窗口不能比屏幕大"的物理限制。所以确认条要把真实尺寸写出来
（「窗口 1920×1040（受屏幕限制，目标 2080×1440）」），否则用户会以为缩放没生效。

### 10.4.2 文本缩放（需要改框架）

这个是本次最需要摊开讲的部分，因为"只放大字"在这套布局里**必然撞墙**。

EUI 的字号落点很干净，就一处：

```cpp
// EUI-NEO-main/core/dsl.h:1151
TextBuilder& fontSize(float value) {
    element_->fontSize = std::max(1.0f, value);
    return *this;
}
```

所以"全局乘一个系数"是一行的事。问题在于**旁边的东西不跟**：

| 会被放大 | 不会跟着放大（因为它们是 `size()` 传的常数） |
| --- | --- |
| `ui.text().fontSize(11.5)` | `lineHeight(26.0)` ← 行框高度 |
| —— | 按钮 `size(88, 26)` |
| —— | 卡片行高 `kRowH = 80` |
| —— | 输入框 `size(w, 35)`、chip 高 26、pill 高 20 |

结果：字号 12 → 18，行框还是 26，`verticalAlign(Center)` 挤得下但两行卡片会重叠；按钮文字贴边。

三个可选做法：

| 方案 | 改动 | 得到 | 放弃 |
| --- | --- | --- | --- |
| **T1. 只乘 `fontSize`** | 1 行 | 最省 | **必翻车**：行高不同步，12 px 以上就重叠 |
| **T2. `fontSize` + `lineHeight` 同乘** | 2 行 | 字和行框一起长，单行文字不重叠 | 控件框（按钮/输入框/卡片行高）不变 → 文字溢出控件 |
| **T3. 全部尺寸都乘** | 等于第二个 uiScale | 完全不溢出 | 和 §10.4.1 语义重复，两套倍率会互相打架（用户看不懂哪个该调） |

**拍板：T2**（用户「文本缩放先按你的建议来」），并且**不加「再大请用界面缩放」那句提示**（用户明确否掉）。

| 项 | 值 |
| --- | --- |
| 范围 | **75% ~ 150%，5% 一档，共 16 档**（存的是**相对基准 1.4 的倍率** 0.75~1.50，见 §10.4.2.2） |
| 实际档位 | `0.75 0.80 0.85 0.90 0.95 1.00 1.05 1.10 1.15 1.20 1.25 1.30 1.35 1.40 1.45 1.50` |
| 默认 | 1.00（索引 5）= 框架原始字号 × 1.4 |
| 绝对字号 | 1.05 ~ 2.10 倍原始字号 |
| 档位**不受**布局约束 | 高段的排版问题（折行、挤压、截断）是**那页的文本内容和阅读顺序**要改，不是砍档位。见下条 |
| 生效 | `onChange` 只量化到档位写进 pending；`onRelease` 才 `applyTextScale`（同 §10.4.1.0） |
| 落点 | `dsl.h` 的 `fontSize()` 和 `lineHeight()` 各乘一次 `textScale()`（内置的是**合成后**的系数） |

**档位范围的口径（2026-11-02，用户拍板）**：范围按用户视角定满 75%~150%、步长 5%，
**不按"哪个档位不破版"来收**。理由（用户原话的意思）：文本截断属于界面设计问题 ——
过长的文本直接摊在界面上本身就是阅读障碍，正确的做法是优化文本内容与排版（阅读顺序），
而不是限制缩放尺寸。所以从此以后：**某档位出现截断/拥挤，是那一页的待办，不是这个滑块的待办**。
绝对字号因此能到 2.10 倍原始值 —— 这会超出 §10.6.3 记录的旧"布局天花板 1.50"，
已知会在高段露出排版问题，按上面这条口径逐个页面优化（不是回退档位）。

#### 10.4.2.1 为什么文本缩放必须是离散档（不是连续滑块）

这条是照上游的踩坑记录回推的，机制在本仓库的 EUI 里逐条对得上：

| # | 事实 | 位置 |
| --- | --- | --- |
| 1 | 字形图集是**全局单例**，灰度页 2048²、彩色页 1024²，一页到底 | `core/render/text.cpp:39-40`、`:200` |
| 2 | 字形缓存键里带**逻辑字号**：`glyphCacheKey(face, style_.fontSize, glyphIndex, colorBitmap)` | `text.cpp:1566` |
| 3 | 光栅化尺寸 `scaledFontSize = fontSize * pixelHeightScale`，而 `pixelHeightScale` 只是字体的 `units_per_EM / (ascender-descender)`，**不含 DPI、不含 uiScale** | `text.cpp:558-563` |
| 4 | `appendToAtlas` 失败时仍然 `cacheGlyph(shaped.key, glyph)` —— 缓存进一个没写进图集的空 UV | `text.cpp:1588-1601` |
| 5 | 图集没有淘汰/清理入口（grep 不到 clear/reset） | — |

第 3 条是这条约束的根：**字号一变就要重新光栅化一批新字形**，而它们全进同一张 2048² 的页。
第 4 条决定后果的严重性：溢出不是"这段文字糊了"，而是**缓存了一个永远命不中的空字形，文字直接消失且不会自愈**
（`findGlyph` 命中就返回，不会再试一次）。

于是：
- **连续滑块（float 直通）= 危险**。拖动一秒能产生几百个不同字号，每次都是一批新字形 → 图集必爆。
  上游原话：`A continuous slider emits a new fontSize per drag tick; the glyph atlas is a SINGLE 2048^2 page
  with no growth/eviction, so it overflows -> appendToAtlas fails -> glyph cached with invalid UV ->
  text vanishes globally and persists.`
- **量化到有限档 = 可控**。占用量从"拖动时长 × 帧率"变成"档数 × 界面字符集"，而且档数可以事后收窄。
- **界面缩放不受这条约束**：`uiScale` 不进字号（第 3 条），它只是渲染变换 —— 换档不产生新字形，
  所以界面缩放按 5% 一档（26 档）是安全的。两边代价不对称，别把规则互相套用。

**判据（实测时看这个）**：先切到 2.00，来回拖十几趟，再切回 1.00 —— 如果某些字**不回来了**（不是糊，是没有），
就是图集溢出。真出现时的兜底：把档数砍到 8~10 档，或按上游的做法把上限收到 1.50。

**为什么把上限放到 2.00 是"先给够、实测再收"而不是"够用"**：1.3 倍时项目里最紧的三处已经临界 ——
26 高的按钮配 12 px 字、24 高的排序 chip 配 11.5 px 字、卡片两行文字挤在 80 高的行内
（1.3 倍时 11.5 → 15，chip 还剩 4~5 px 余量）。到 2.0 倍：11.5 → 23，chip 只剩约 1 px，
pill（高 20、字 11 → 22）直接撑破，卡片两行 17+11.5 → 34+23 必然溢出 80 高的行。

所以 **2.00 在现有控件常数下一定是坏的**。它的用途是先把可达范围给到，拿真机截图当证据再定上限；
实测完最可能的落点是 1.40~1.50。要再高，就得连 `size()` 一起乘 —— 那是 T3，得先解决"两套倍率语义重叠"
的问题（用户看不懂该调哪个）。这段写在这里，是为了将来收窄时不用重新论证一遍。

> `textScale()` 从哪来：`dslAppConfig().textScaleValue`，和 `uiScale` 同一个对象、同一次读取。
> **v4 起这个字段是合成值**（基准 1.4 × 用户倍率），由 `mutableDslAppConfig()` 一次算好；
> 运行期改它必须走 `applyTextScale()`（两处同步写，见 §10.4.2.2）。
> `dslAppConfig()` 每帧被调 20+ 次，所以这里只能是"读一个已经算好的 float"，不能读盘（`docs/03` §7.13 的约束）。

#### 10.4.2.2 字号基准 1.4（v4）：为什么 100% 就是"原来 140% 的大小"

**起因**：EUI 的字号相对控件尺寸偏小（26 高的按钮配 12 px 字），出厂的 100% 看着吃力 ——
用户实测要「界面 115% + 文本 120%」才符合日常浏览习惯。可这两个倍率一起抬，**提示窗也跟着变大**
（提示窗跟文本倍率走），于是"界面舒服了、提示窗太大"。

**做法**：把"默认字号"这件事从**用户旋钮**变成**设计基准**。

```cpp
// store.h
constexpr float kTextBaseScale = 1.40f;          // 设计基准，不落盘、用户不可调
// app.cpp
static float effectiveTextScale(float u) { return pxc_store::kTextBaseScale * u; }
```

| 位置 | 值 | 说明 |
| --- | --- | --- |
| `dsl.h` 的 `fontSize()/lineHeight()` | `值 × textScale()` | 内核只认**合成后**的系数（1.4 × 用户倍率） |
| `launcher.json → ui.textScale` | 用户倍率（0.75~1.50，16 档） | 存相对值，基准不落盘 —— 改基准是改设计，不是改配置 |
| 提示窗 `pxc_toast` | **只吃用户倍率** | 它有自己的设计尺寸，不该跟着 EUI 的基准一起放大 |

**为什么不直接把默认 `textScale` 改成 1.4**：那样提示窗会拿到 1.4（"太大"原样复发）；
要压回去就得在提示窗那边再除一次 1.4 —— 同一个字段两套语义，正是 §10.4.2 否掉 T3 时说的
"两套倍率语义重叠"。基准放在内核调用点、旋钮只表示相对量，语义只有一套：
**100% = 这东西按设计尺寸显示**。

**基准和滑块范围是两件事**（先按"上限只到 106%"实现过一版，被用户否掉）：
基准只决定"100% 长多大"，滑块范围决定"用户能调多宽"。用基准去压缩滑块范围，
等于拿设计常量去实现一个用户不可见的限制 —— 用户看到的是"我调不大字号了"，而不是"设计变大了"。
所以现在两者各管各的：基准 1.40 不动，滑块仍是 75%~150%（绝对 1.05~2.10）。

**代价（摆在明处）**：绝对字号能到 2.10 倍原始值，**超出旧记录的布局天花板 1.50**
（§10.6.3 那条是"高段开始破版"的实测点，不是"不许超过"的许可线）。
高段会看到：品牌字被导航栏裁、页签/筛选 chip 文字撑出圆角底、卡片里"修改时间"与「启动」按钮相撞。
这些按 §10.4.2 的口径逐页改内容与排版，**不靠收窄档位掩盖**。要根治得连 `size()` 一起乘（T3），仍不做。

**配套改动**（1.4 倍字号会把"按字符串估宽"的地方全暴露出来）：

| 位置 | 改法 | 不改的后果 |
| --- | --- | --- |
| `wbTextW()` | 内部先 `fs *= textScale()` | 页签 chip、面包屑、按宽裁字全按它算，估小 40% → 文字撑出圆角底 |
| `wbRealTextW()` | 同乘 | 页签下划线短一截、点击区盖不住字 |
| `setTab()` / Switch 行 `swW` | 量宽用的字号同乘 | 页签下划线、开关行总宽偏窄 |
| `wbFit()` | 先用**真实宽度**判一次"放得下就不截"，再进 em 估算的截断循环 | 版本徽章被截成 `…20.1.0`（"1.20.1.0" 实测 56 px、em 估算 69 px > 62 的可用宽） |

**踩过的那个 bug（用户报的）**：改完文本缩放后关掉重开，字号回到 100%，再动一次滑块才恢复。
根因是**启动路径上没人把配置写进内核**：`applyTextScale()` 会调 `setTextScale()`，
而 `initialize()` 只在启动时读一次 `DslAppConfig::textScaleValue` —— 那个字段一直是默认 1.0。
修法两处同步写：`mutableDslAppConfig()` 里 `cfg.textScale(effective(g_cfg.ui.text_scale))`（冷启动），
`applyTextScale()` 里 `mutableDslAppConfig().textScale(...)` + `setTextScale(...)`（运行期）。
> §10.6.3 里"重启后保持 ✅"那行当时的验法是错的（截图看着像 1.3，实际是 1.0 下的大字号），此处已改。

**v3 → v4 迁移**：旧配置的 `textScale` 是**绝对**倍率，读盘时 `/= 1.4` 再量化到档位
（1.00 → 0.714 → 0.70 档，绝对 0.98，视觉原地不动）。只在**字段真的存在**时迁移 ——
缺字段说明是第一次跑，该走新的 1.0 默认。

**验证**（真机，1040×720，UI 100%）：

| 检查 | 结果 |
| --- | --- |
| 冷启动就是配置值 | 存 0.90 → 首帧字号即 0.90（提示文字比 100% 时每行多塞几个字），滑块读数 90% |
| 默认 100% 的观感 | 与原「UI 115% + 文本 120%」相当；四页无截断、无叠字 |
| 下限 75% | 工作台四列（文件名/修改时间/版本/启动）全放得下，版本徽章 `1.20.1.0` 完整（`tmp/t75_p2.png`） |
| 上限 150% | 文字**全部画得出来、没有空白缺字**（图集没爆）；已知排版问题见 §10.4.2 那条口径 |
| 16 档全部栅格化 | 用 `PXC_LAUNCHER_DEBUG_TEXTSWEEP=0` 让 16 档在一进程内跑一遍，再截图 —— 三页都没有缺字，说明 2048² 灰度页装得下 16 套字号 |
| 提示窗 | 100% → 560×104（**与改前逐像素一致**）；150% → 792×138（两行完整、按钮不压字） |
| 配置 | 落盘 `version: 4`、`textScale: 1.00`（相对值；字段名和语义没变，不需要 v5 迁移） |

### 10.4.3 主题色（默认 `#FF9166`）—— ✅ 已实现

控件用 EUI 自带的 `components::colorpicker`（整屏 overlay：半透明底衬 + 居中面板 + 预览条 + R/G/B 三根滑块 + 8 个色块）。它的交互是「改草稿 → 点完成才提交」，所以不需要额外的确认条，也不该在拖动中就写盘。

**一条链路改完**：`ThemeColorTokens::primary` 是唯一的强调色 token，项目里 40 处组件都从 `uiTheme()` 取主题，所以只改这一个函数：

```cpp
static core::Color g_accent = {1.0f, 145.0f/255.0f, 102.0f/255.0f, 1.0f};   // #FF9166

static components::theme::ThemeColorTokens uiTheme() {
    auto th = components::theme::dark();
    th.primary = g_accent;     // 只换这一个 token
    return th;
}
```

| 项 | 结论 |
| --- | --- |
| 跟随的（实测） | 导航选中项与左侧高亮条、按钮主色、滑块进度条与轨道高亮、开关轨道、页签下划线、下拉箭头、取色面板自己的强调色 |
| 不跟随的 | 自绘灰阶与语义色：面板底、分隔线、正文/说明文字、工作台的卡片底与状态 pill、`启动` 按钮的绿、提示窗（原生 GDI） |
| 写盘 | 选完点「完成」→ `applyAccent()` → `g_cfg.ui.accent = colorToHex(c)` → 立即写盘。只换 token 不动布局，所以**不需要重排、不需要确认条** |
| 恢复默认 | 主题色行上的「恢复默认」按钮（`#FF9166`）。不提供"删除字段"这种隐性操作 |

**两个坑（都踩过）**：

1. **取色面板不会自动跟随主题**。`ColorPickerBuilder` 的 `style_` 默认取 `theme::dark()`（蓝），必须显式 `.theme(uiTheme())`，否则面板里的「完成」按钮和色块选中环还是默认蓝 —— 界面全橙、弹窗里一块蓝，非常突兀。
2. **面板必须挂在根级、且把 zIndex 抬到 1100**。`colorPicker` 与 `dialog` 的默认 zIndex 都是 1000，两层全屏 overlay 嵌套时"谁在上面"退化成创建顺序。所以它跟 `composeOverrideDialog` 平级、排在最后，且 `.zIndex(1100)`。

**框架改动（BUILD n，纯增补）**：`components/colorpicker.h` 的标题与确认按钮原本写死英文 `"Color"` / `"Done"`，加两个可选 setter：

```cpp
ColorPickerBuilder& title(std::string value);     // 默认 "Color"
ColorPickerBuilder& confirm(std::string value);   // 默认 "Done"
```

不传就还是原样，不影响既有调用点。中文界面里弹一个 `Color / Done` 的窗，比不做还糟。

## 10.5 存储

`launcher.json` 新增一段（`version` 2 → 3；缺字段一律取默认，不需要迁移代码）：

```jsonc
"ui": {
  "scale": 1.0,        // 0.75 ~ 2.00，落值量化到 0.05（26 档）
  "textScale": 1.0,    // 0.75 ~ 1.50（5% 一档共 16 档），相对 1.4 基准的倍率（§10.4.2）
  "accent": "#FF9166"  // 只认 #RRGGBB（6 位十六进制），大写，带 #
}
```

> `accent` 存成十六进制字符串而不是三个 0~1 浮点：**肉眼可读、能手改**。
> `"0.999999,0.568,0.4"` 这种写在 json 里既看不懂也改不动，而这一项恰好是用户最可能手改的。
> 老配置读进来时 `version < 3` 直接当 3 处理（只多一个 `ui` 段，缺字段走默认，不需要迁移代码）。
> 非法值在 `initOnce()` 里被夹回合法档：`setUiScaleIndex()` / `setTextScaleIndex()` 各自找最近的档；
> `accent` 格式不对（长度 ≠ 7、不是 `#` 开头、含非十六进制字符）→ 退回默认橙，**不能让界面变成全黑**。

| 时机 | 行为 |
| --- | --- |
| 启动 | 读进 `g_cfg.ui` → 在 `dslAppConfig()` 首次构造**之前**塞给框架（否则第一帧就是错的缩放）；同时按 `scale` 算好初始窗口尺寸一起进 `windowSize()` |
| 滑块拖动中 | **什么都不写**，只更新屏幕上的数字 |
| 滑块脱手 | 应用（窗口 → uiScale → recompose）→ 弹确认条；**确认保留之后**才写盘 |
| 主题色选完 | 点「完成」时写盘（改草稿的拖动过程一次都不写） |
| 读不到 / 非法值 | 夹到合法区间（`std::clamp`），不报错 |

> 启动时按 `scale` 直接建大窗口，意味着**存的 2.0 会在下次启动时立刻生效，没有确认条**。
> 这是有意的：能存下来就说明上次确认过了。但也因此，若用户换了小屏，2.0 的窗口会顶到工作区边界
> —— 所以建窗尺寸也要过一遍 §10.4.1.1 的夹取，不能只在滑块那里夹。

## 10.6 尖峰：两条已定，一条降级

### 10.6.1 `uiScale ≠ 1` 时点击会不会错位 —— **实测：不会，框架不用改**

这条我前后推翻了两次，把过程记下来，因为**两次都只靠读代码**，结论相反：

| 轮次 | 读到的 | 由此推的结论 |
| --- | --- | --- |
| 第一轮 | 布局用 `effectiveScale = dpiScale × uiScale`，指针用 `pointerScale` | 两个 scale 不一致 → 会错位 |
| 第二轮 | `consumePointerEvents` 里是 `event.x = raw.x * pointerScale`（乘，不是除） | 事件出来已经是**物理像素**，命中测试也在物理像素（`toPixelRect(frame, effectiveScale)`）→ **不会错位** |
| 实测 | 2.0 倍下点导航「汉化」的**视觉位置** | 命中，页面切到汉化 ✔ |

把第二轮的账算清楚，这就是为什么不错位：

```
元素逻辑坐标 L
  └─ toPixelRect(L, effectiveScale) = L × dpi × uiScale   ← 命中测试用的矩形（物理）
指针窗口坐标 P（GLFW 报告，dpi=1 时等于物理）
  └─ event.x = P × pointerScale = P × dpi                 ← 事件坐标（物理）
```

两边**都是物理像素**，所以 `uiScale` 只影响"逻辑→物理"的换算，不影响两者的可比性。
第一轮错在把 `pointerScale` 当成"逻辑坐标换算"，实际上它是"窗口坐标 → 物理像素"。

实测环境与做法（`tmp/test_uiscale_click.py`，钩子 `PXC_LAUNCHER_DEBUG_UISCALE=2`）：

| 项 | 值 |
| --- | --- |
| 逻辑视口 | 日志 `compose 首帧 · screen=520x360 · uiScale=2.0` —— 确认 uiScale 真的进了布局 |
| 界面 | 等比放大 2 倍，只显示左上局部（导航 200 逻辑 → 400 物理） |
| 操作 | `SetCursorPos` 到「汉化」的视觉位置（客户区 200,560）→ `mouse_event` 左右键 |
| 结果 | 页面切到汉化、导航高亮跳到「汉化」 |

**所以框架这一处不用改。** 本次的 `onRelease` 也不是新增实现 —— `components/slider.h` 上游已带 `[BUILD k]`，
本仓库已对齐，`core/` 一行不动（§10.4.1.0）。

> 顺带一个只有实测才看得见的收获：`uiScale=2` 而**窗口不放大**时，逻辑视口变成 520×360，
> 工作台会按 520 宽重排（卡片 3 列变 1 列），而且卡片内的版本 pill 与日期**叠在一起**（截图 `tmp/uis_scale.bmp`）。

### 10.9.2 版本库里那个「自动」是什么意思

`ExeEntry.source`，取值 `"auto"` / `"manual"`，界面上显示成「自动 / 手动」—— **它表示这个条目的版本号是怎么来的**：

| 值 | 含义 | 怎么产生 |
| --- | --- | --- |
| **自动** | 版本号是从 exe 的 **PE 版本资源**里读出来的（`GetFileVersionInfo`） | 添加 exe 时自动读，成功即 `auto` |
| **手动** | PE 里没有版本资源 / 读失败，**让你手填**的数字 | 读失败时弹手填，填完记 `manual` |

为什么值得单独显示一列：**版本号是跨版本判定的唯一依据**。

- 决定用哪个 exe 打开这个 `.pxc`（版本不匹配 → 弹协商窗）
- 决定要不要先备份（`shouldBackup` 按版本比对）
- 决定汉化生成时用哪份骨架

自动读出来的基本可信；手动填的可能是打字错误（`1.20.1` 打成 `1.20.l` 就没有任何版本能匹配上）。
所以这一列本质是个**可信度标记**。

现状的不足（这次不改，记一笔）：手填错了**没有编辑入口**，只能删掉重加。
如果将来要补，最省的做法是给这一行加双击改版本 —— 不过那属于版本库那页的事，不在本次范围。

### 10.10.3 页签：文字 + 下划线，不用 pill

左侧导航已经是"选中 = 蓝底圆角"，页面里再来一层蓝 pill 有两个问题：视觉上重了；形状跟按钮一样，让人以为点一下会执行动作。

改成：14 号字，选中 `fontWeight(700)` + 白字 + 下方 2px 主色短线（宽 = 文字宽 + 6），未选中灰字。间距 26。

### 10.10.4 开关：用框架的 `components::switch`

`components/toggleSwitch(ui, id)` — 两处要注意：

1. **必须包在 `ui.stack(...).position()` 里**：`SwitchBuilder::build()` 内部不写 `.position()`，自己排不了位置。
2. **`size()` 的宽度要含 label**：内部按 `trackWidth + gap + 文字宽 + 内边距` 算命中区与标签框。给窄了标签会被压，给宽了命中区比看到的更大（`hitWidth` 取 `min(width_, ...)`）。
3. 轨道尺寸用 `.trackSize(40, 22)`；`metrics.control.switchWidth/Height` 默认是 46×24，偏大。

实测口径（`tmp/interact.py switch`）：点轨道中心 → 轨道 `on` 蓝 / `off` 灰，旋钮贴右 / 贴左各留 3px 间隙，动画 0.18s。

### 10.10.6 顺带纠正一条错结论：合成鼠标能进窗口

之前判「本沙箱合成鼠标送不进窗口（连导航都点不动）」是**错的**，原因是点击坐标算歪了两处：

| 错在哪 | 正确口径 |
| --- | --- |
| y 用窗口外框顶边算 | 客户区原点比外框顶边低一个标题栏（本机 31px）→ 用 `ClientToScreen(hwnd, {0,0})` |
| x 直接当客户区坐标 | 页面画在 `scrollView` 里，**内容坐标原点在 `kNavW`(200) 之后** → 屏幕 x = 客户区原点 x + 200 + 内容 x |

修正后真实拖动滑块可用：界面缩放拖到 165% → 窗口 1716×1001（被屏高夹）→ 松手 10 s 不确认 → 回到 1040×720。
**以后再遇到"点不动"，先算一遍坐标，别先怀疑输入通道。**

## 10.12 头部固定、正文单独滚动（2026-11-04）

原来整页（标题 / 页签 / 控件）都在一个 `scrollView` 里，往下翻的时候「设置」和「通用 / 界面 / 汉化」
会一起滚出屏幕 —— 想换页签得先滚回顶部。现在头部**固定**，只有页签下面的控件滚动。

### 做法

| 步骤 | 实现 |
| --- | --- |
| 拆函数 | `composeSettings` → `composeSettingsHeader`（标题 / 页签 / 分隔线）+ `composeSettingsBody`（页签以下全部控件） |
| 视口下移 | `page.host` 改成 `.position(0, kSetHeaderH).size(contentW, screen.height - kSetHeaderH)` |
| 头部单独画 | 设置页时多画一层 `page.header`（`position(0,0)`, 高 `kSetHeaderH`, `zIndex(4)`） |
| 正文起点 | `composeSettingsBody` 的 `y` 从 **0** 起，不再自己偏移 144（头部已由视口让出来） |
| 总高 | `g_pageH = y + 90` 不用改：内容高和视口高同时少了 144，可滚动距离与原来自动等价 |

`kSetHeaderH = 144.0f` 是**唯一来源**（标题 28→80、页签 80→118、分隔线、间距 →144），
头部排版改了必须一起改它，否则正文要么顶到页签上，要么在分隔线下空出一条。

没有采用"头部画进滚动内容再盖一层不透明底"：那样滚动条会从头部里穿出来，内容也会从页签底下透过去。

### 两个必须知道的连带影响

1. **`g_pageScroll` 仍然是"视口内的滚动量"**，不是"整页的滚动量"。设置页视口起点是 144，
   所以设置页里任何"把页面坐标换算成屏幕坐标"的东西都要**再加 144**。
   目前设置页**没有** `ddField`（下拉只在汉化页，`app.cpp` 的 6188 / 6319 / 6476 三处），
   所以 `f.ay = py - g_pageScroll.get()` 不需要改 —— **但以后要在设置页加下拉，必须加成
   `py - g_pageScroll.get() + kSetHeaderH`**，否则弹层会正好偏上去 144 px。
2. 版本库 / 工程 / 汉化三页**仍是整页滚动**（头部跟着走）。只改了设置页是用户 2026-11-04 的明确范围；
   要统一就把各页 compose 也拆成 header + body 两段，判 `g_page` 换页时不画头部即可。
