## 4. 构建器：维护对照表

### 4.0 角色转变（v2.1，重要）

**不再以"输入一堆汉化包做合并"为日常路径。** 对照表本身变成**唯一长期维护的资产**，  
构建器围绕它工作：

```
导入新版本英文语言包（或选新版 PXC 路径，两者其一）→  与现有对照表比对（结构校验；新键默认标「待翻译」）
        → （可选）导入中文包：给空位预填（进「待校对」），同键不同文只记候选、不改表
        →  勾选/取消「待翻译」→ 导出待翻译 → AI/人工翻译 → 导入译文
        →  改「输出版本」→ 生成对照表文件（另存）/ 生成并覆盖当前对照表（落盘）
```

旧的"多包合并"仍保留，但只作为**首次建表**的一次性动作（2026-10-30 之前就是这样建出 1.22 表的）。  
日常维护的对象是表，不是包。

**构建器操作的就是运行时使用的那一份表**（`data/translation_db.json`）。不引入"多表管理"概念：
要保留旧版就先「导出当前对照表」，要试别人的表就「修改当前对照表」(§4.9)。

### 4.1 维护流程（五步，与界面入口一一对应）

```
按钮行  ①「导入新版英文包骨架」 或 「选择新版 PXC 路径」(换骨架，二选一)   【可选】②「导入已有汉化包」(补空位 + 记冲突)
编辑    ③ 分页浏览 / 搜索 / 筛选 → 逐条改 + 字段级「待翻译」「待校对」开关（在字段标题行右端）
往返    ④「导出待翻译 json」→（外部翻译）→「导入已翻译 json」→ 人工校对
出口    ⑤「生成对照表文件…」(另存) /「生成并覆盖当前对照表」(落盘)
```

| 步骤 | 界面位置 | 输入 | 动作 | 约束 |
| --- | --- | --- | --- | --- |
| ① 换骨架（入口 A） | 按钮行「导入新版英文包骨架」 | 新版 PXC 的英文语言目录（安装 `data/locale/en`、官方 en 包、用户 `Locale/en`） | 作为本次比对基准，重建可译键集合（§4.2） | **只刷 `en` 与键集合，不动任何译文** |
| ① 换骨架（入口 B） | 按钮行「选择新版 PXC 路径」 | `PixelComposer.exe`（或它所在目录） | 由 exe 上溯出安装目录 → 取 `data/locale/en`（没有则 `sample locale`）→ 与入口 A 走**同一段**应用逻辑 | 同上；**两个入口只差"骨架目录怎么来的"**，见 §4.1.1 |
| ② 补空位（可选，旁路） | 按钮行右端「导入已有汉化包」 | 整包汉化（同版本或相邻版本） | 给没有译文的键预填；有译文且文本不同的记入**冲突候选**（§4.8） | **永不覆盖已有译文**；默认保留表内中文；**未导入英文骨架时置灰** |
| ③ 编辑 | 中间编辑区 | — | 逐条改译文；**每个字段的标题行右端**两个开关手动打「待翻译」「待校对」（作用于该字段这一个键） | 手动编辑译文时两个标记都自动摘（§4.10 规则表） |
| ④ 翻译往返 | 按钮行「导出待翻译 json」→「导入已翻译 json」 | 只导出**打了待翻译标**的条目（含已译的老条目） | 外部翻完按 key 导回；导入后**待翻译 → 待校对** | 导入是显式动作，允许覆盖草稿 |
| ⑤ 两个出口 | 底栏 | — | 「生成对照表文件…」另存一份（含未保存改动）；「生成并覆盖当前对照表」写回运行期表 | 覆盖前**二次确认** + 自动备份（§4.7.4） |
| 另：换表（可选） | 标题行「修改当前对照表」 | 任意 `translation_db.json` | 替换运行期那份表（§4.9） | 旧表先备份；结构不合法直接拒绝 |

**主流程是「骨架 → 待翻译 → 外部翻译 → 导入译文 → 人工校对 → 导出」**，整包汉化导入只是兼容旧做法的旁路：
以前没有工具筛选该翻哪些，只能每次把整包翻一遍；有了待翻译队列之后，整包翻译既贵又必然覆盖不了新版本的新键。
所以界面把「导入已有汉化包」放到最右、并前置置灰（没有骨架就没有对齐的尺子），而不是和主流程并排。

**为什么"导出"要分两个**（你确认的语义）：标题行「导出当前对照表」导出的是**磁盘上那份表、原样不动**——
不含本次修改、版本号也不变，是一个纯粹的**备份点**；底栏「生成对照表文件…」导出的是**表与本次改动合并后的新版本**，
版本号取自底栏输出版本。前者"记住现在是什么"，后者"产出一个新的"。

### 4.1.1 换骨架的两个入口（2026-11-01 新增入口 B）

维护者手上可能是"一份英文语言包"，也可能是"刚装上的新版 PXC"。前者要给目录，后者只要给 exe ——
让他自己去翻 `data/locale/en` 是多余的一步，而且容易翻错版本。所以按钮行并排给两个入口，中间用一个
字重 11px、`metaFg` 色的「或」连起来，读法就是"这两个选一个就行，都能换骨架"：

| | 入口 A「导入新版英文包骨架」 | 入口 B「选择新版 PXC 路径」 |
| --- | --- | --- |
| 选什么 | 目录（文件选择器选文件夹） | `PixelComposer.exe`（也可直接选它所在的目录） |
| 拿到骨架 | 选中的目录本身，找不到 `en` 子目录就用它自己 | `installDirOfExe(exe)` → `data/locale/en` → 退 `sample locale` |
| 适用 | 官方 en 包、别人给的语言包、用户 `Locale/en` | 本机已装新版 PXC（最常见） |
| 拿不到时 | 「该目录里没有可用的语言文件（nodes.json / words.json）」 | 「这个 PXC 目录里没找到英文语言目录（data/locale/en）」 |

**入口 B 的连带好处**（这次没做，先记下）：选中 exe 能顺手读它的 `ProductVersion`，也就是**目标版本号**，
可以自动填底栏的「输出版本」。现在底栏是手填的，跟 exe 的真实版本没有强绑定。
做之前得先确认"输出版本"是覆盖式输入还是可被自动填 —— 会动到底栏的语义，不塞在这一轮。

**实现要点**：`onBldPickBaseline()` 的后半段（`locateLangDir` → `load` → 键集合差 → `syncSkeleton` → 回执）
必须抽成一个 `applyBldBaseline(langDir, 来源说明)`，两个入口共用。**不许复制第二份** —— 这段里
「旧键集合要在替换前取」的顺序一旦写错，就会把所有历史空缺误报成"新增"（§4.2 末段的坑）。

#### 4.1.1.1 落地记录（2026-11-02）

`applyBldBaseline(lang, srcLabel)` 已抽好，两个入口都只剩"把目录拿到手"这一步：

| | 实现 |
| --- | --- |
| 入口 A | `pickFolderPath` → `pxc_tdb::locateLangDir(p, "en")`（找不到 `en` 子目录就用选中的目录本身）→ `applyBldBaseline(lang, "目录")` |
| 入口 B | `pickExeFile` → `pxc_base::installDirOfExe(exe)` → `pxc_base::candidates(installDir, {}, {}, "")` 取首个 → `applyBldBaseline(cand.dir, "PXC 安装目录 en" / "… sample locale")` |

三条与文档原先设想不同的地方：

1. **入口 B 只收 exe，不兼收"它所在的目录"**。Win32 的文件选择器与文件夹选择器是两个对话框，
   兼收要么弹两次、要么自绘合并框 —— 都不如"要 exe 就只收 exe"。真给错了有明确回执：
   「这个 PXC 目录里没找到英文语言目录（data/locale/en 或 sample locale）。请改用「导入新版英文包骨架」…」
2. **入口 B 复用 `candidates()` 而不是自己拼 `data/locale/en` 路径**。它内部就是
   install-en → install-sample 的顺序，且只认真有 `nodes.json` 的目录 —— 与版本库页"自动找骨架"同一套判据，
   免得两处口径将来分叉。
3. **两个按钮不同色**。同高同色的并排按钮会读成"两个一模一样的操作"，「或」这个字就白放了；
   入口 A 是主色（默认入口），入口 B 与「恢复草稿 / 丢弃草稿」用次要样式（`theme(th, false)`）。

**回执里加"来源"**：`英文包骨架已导入（756 节点，来源：PXC 安装目录 en）：本次新出现 703 键…`。
同一份骨架从 A 还是从 B 进来，维护者事后要看得出 —— 排查"怎么突然多出 5000 孤儿"时，来源是第一线索。

**验证**（真机，1.20.1 的 `data/locale/en`）：点入口 B → `可译键 12134 | 已译 11160 | 孤儿 5448`，
回执「新出现 703 键｜其余未译 271｜孤儿 5448｜新增节点 3 · 消失节点 189｜英文措辞更新 56 条」。
模态文件对话框没法用合成鼠标点，这里加了 `PXC_LAUNCHER_DEBUG_EXE=<exe 路径>` 钩子跳过它
（只跳过"选文件"这一步，其余仍是完整点按路径）。

### 4.2 结构校验（"结构没变就正常导入，变了要提示"）

比对面是**新骨架 vs 现有对照表所依据的旧骨架**。逐项判定：

| 检查项      | 一致                                         | 变化                                 | 变化时怎么处理                                              |
| -------- | ------------------------------------------ | ---------------------------------- | ---------------------------------------------------- |
| 文件集      | 都有/都没有 `UI.json`、`junctions.json`、`notes/` | 新增或消失某类文件                          | 提示新增/缺失的文件类型；缺失类型在生成时按 §5.6 处理                       |
| 节点 id 集合 | 完全相同                                       | 新增节点 / 消失节点                        | 新增 → 列出来待译；消失 → 该节点译文标为**孤儿**（保留、不删、**仍参与生成**），见下方说明 |
| 节点内端口数   | `inputs`/`outputs` 长度一致                    | 长度不等                               | 该节点端口整段**不可按位对齐**（§4.3 规则）→ 按英文端口名重新锚定；锚不上的列为待译      |
| 下拉项数     | `display_data` 长度一致                        | 长度不等（1.18=13 → 1.22=31 且插入 `-1.0`） | 同上，按**英文枚举值**重新锚定，禁止按下标                              |
| 字段类型     | `name`/`tooltip` 的 JSON 类型一致               | 字符串 → `{}`/`[]`/`bool`             | 提示"该字段在新版已不是文案"，从可译集合里移除（对应 §5.2「类型不动」）              |

**判定结论只影响"是否弹确认"，不阻断导入**：结构变化时构建器把差异清单摊开，维护者确认后仍可合并，  
但必须能看见"我这次改动了哪些结构"。

**节点 id 比的是「骨架 vs 骨架」，不是「骨架 vs 表里有没有译名」**（2026-10-31 修正）。  
表只存有译文的条目，而 `Node_FFT` / `Node_FXAA` / `Node_SDR` 这类**名字本来保留英文**的专名节点  
永远不会进表 —— 按"没有译名"判新节点，每次重新导入同一份包都会报"新节点 13"（1.22 实测正好 13 个）。  
所以 `diff()` 现在要求调用方给出**上一版骨架的键集合**（`oldKeys`），用两边的节点 id 集合求差；  
拿不到上一版骨架时（首次建表）**不报新节点**，只报"表里有译名、新骨架里已没有该节点"的孤儿。

**孤儿为什么不删、还参与生成**：一个用户机器上通常同时装着多个 PXC 版本，新版删掉的节点在老版本里仍然存在。  
生成是按**目标版本的骨架**逐项遍历的 —— 所以把孤儿译文留在表里，生成老版本时它自然被用上；生成新版本时  
骨架里没有这个节点，它自然不会出现在产物里。标记是为了让维护者知道"这键在新骨架里没了"，而不是删除理由。  
真正确认可以清除时，走「导出对照表」留档后再删。

### 4.3 条目键设计（**以英文为锚**，跨版本稳定）

| 类型     | 键                              | 说明                                 |
| ------ | ------------------------------ | ---------------------------------- |
| 词条     | `words.<key>`                  | key 本身是英文标识（`2d_operations`），天然稳定  |
| UI     | `ui.<key>`                     | 同上                                 |
| 节点名/提示 | `nodes.<id>.name` / `.tooltip` | 节点 id 稳定                           |
| 端口     | `nodes.<id>.in.<英文端口名>.name`   | 端口没有 id，**用英文端口名当锚**（`Blend mode`） |
| 输出     | `nodes.<id>.out.<英文端口名>.name`  |                                    |
| 下拉项    | `nodes.<id>.dd.<英文枚举值>`        | 按值不按下标（`Normal`、`Stretch`）         |
| 注释文档   | `notes.<英文文件名>`                | 整篇 markdown，值就是全文（自定义译文层用）          |
| 兜底     | `dd.<英文值>` / `words.<key>`     | 节点级查不到时回退全局词典                      |

**多义词天然成立**：`Normal` 在 `Node_Normal` 是「法线」、在 `Node_Blend` 是「正常」，因为键带节点 id。  
**跨版本迁移成立**：1.22 新增端口「交换」不影响已有端口匹配（按名不按位）。

### 4.4 对齐算法（把新骨架挂到已有译文上）

1. **节点**：按 id 匹配（唯一稳定标识）。
2. **端口**：`inputs` 长度一致 → 按位对应并记为 `英文端口名 → 中文`；长度不一致 → 该节点端口整段跳过，  
   改为按英文端口名在旧表里查（锚一致就沿用），查不到则进待翻译队列（§4.10）。
3. **下拉项**：同上，按 `英文枚举值 → 中文` 对应（跳过 `-1.0` 与非字符串）。
4. **词典兜底**：`words.json` 当英→中词典，试 4 种键形（原样 / 小写 / 小写+下划线 / 去空格）。
5. **增量原则**：**已有译文永不覆盖**，只补空缺与新增键。要改译文是构建器里的人工动作，不是导入副作用。  
   **本次新出现**的键（旧骨架里没有）一律进 `meta.pending_translate`，成为「导出待翻译」的默认队列（§4.10）——  
   不必翻的那些由维护者一轮勾掉，之后**重新导入同一份包也不会再复活**（§4.10 末段）。
6. **不译词表**：`Phong / PBR / Lanczos3 / LUT / SDF / HLSL / FFT / MP4 / SVG / JPEG / PXC / ACE / UV / RGB / HSV / OKLAB`、单字母轴 `X/Y/Z`、`AA`、`BBOX` —— 命中则保留英文。

### 4.5 版本记录（v2.1 简化）

**只记一个版本号**：`meta.version`，形如 `1.22.0.5-机翻版`（对齐 PXC 版本号 + 后缀，后缀是维护者自定的  
质量标记，如 `-机翻版` / `-校对版`）。

不再记"由哪些汉化包合并而来"（旧字段 `meta.sources`、每条目的 `src`）—— 那些包是构建期的中间输入，  
对使用者没有版本语义，却会让人误以为"换个包就能换版本"。旧文件里的这两个字段读取时忽略，写出时不再产生  
（顺带把 1.22 表从 2.7 MB 压到 1.3 MB）。

### 4.6 产物格式（示意）

```jsonc
{
  "meta": {
    "version": "1.22.0.6-机翻版",       // ← 唯一版本标识（= 底栏输出版本）
    "baseline": "1.22 英文原版/en",      // 仅构建期参考
    "built_at": "2026-10-30",
    "pending_translate": [               // 待翻译（§4.10）：决定导出范围
      "nodes.Node_New.name",
      "nodes.Node_New.in.Factor.name"
    ],
    "pending_review": [                  // 待校对（§4.10）：预填/机翻的人工复核队列
      "nodes.Node_Blend.name"
    ]
  },
  "keep_english": ["Phong", "PBR", "SDF"],
  "entries": {                            // 条目恒为两字段，状态一律不放这里
    "words.2d_operations":                 { "en": "2D operations", "zh": "2D 操作" },
    "nodes.Node_Blend.name":               { "en": "Blend",         "zh": "混合" },
    "nodes.Node_Blend.in.Blend mode.name": { "en": "Blend mode",    "zh": "混合模式" },
    "nodes.Node_Blend.dd.Normal":          { "en": "Normal",        "zh": "正常" }
  }
}
```

两个状态字段都是**可缺省**的：为空时不写出（不写 `[]`），旧表读进来就是空的。  
体积代价只在有内容时发生 —— 待翻译几百个 key 约几十 KB，相比 1.3 MB 的正文可以忽略。

**产物里没有冲突字段**：冲突候选（§4.11）只活在内存里，写出时把维护者的选择**材质化**进 `zh`，  
所以落盘的表永远是"已经定稿"的干净表，运行期生成器不需要理解任何候选概念。

### 4.7 构建器界面（v2.3 布局规格）

与自定义译文层**共用同一套浮窗**（`g_ovMode` 0=用户 / 1=构建器）：分页、搜索、虚拟列表、行编辑全部是同一份代码，  
差别只有三处 —— **顶部信息带**（构建器有标题行 / 按钮行 / 元信息行，用户侧只有标题+说明）、**右栏附加控件**（字段级两个标记开关 / 冲突按钮）、  
**底栏出口**。两侧各写一遍界面必然漂移（曾漏过端口提示）。

尺寸：`920 × H`（`H = min(700, 屏幕高 − overlay)`，实测被钳到 672），`pad = 20`，左列 300，右列 `rightX = 336 / rightW = 564`。

#### 4.7.1 顶部：标题行 / 按钮行 / 元信息行

| 带 | y（H=672 时实测） | 内容 | 说明 |
| --- | --- | --- | --- |

**虚拟列表的滚动复位必须换「代次 id」**（v2.7 修，曾表现为"切页后内容消失、滚一下才回来"）：EUI `components::virtualList`

覆盖已存的值 —— 运行时只自己维护。所以切换筛选/搜索/分页/选中条目时，光把 `g_ovScroll.set(0)` **清不掉运行时里的旧偏移**，
运行时仍按旧 offset 平移窗口，把内容整体推出可视区；直到下一次滚动事件才重同步。修法：每次代码层复位滚动时自增代次
（`g_ovListGen` / `g_ovFieldGen`），列表 id 取 `"ov.list." + gen` / `"ov.fields." + gen`，强制运行时为新 id 新建一份
offset=0 的 scrollState，旧 state 该帧自然释放。**别改回固定 id** —— 这是框架语义，不是我们想让就让的。

**标题行与主流程行之间必须留 ≥12px**（现在 37 → 50 = 13px）。两排都是按钮，**且右端都右对齐**（「修改当前对照表」正上方就是「导入已有汉化包」），
贴在一起会读成"一大片六七个按钮"，主流程与旁路就分不出主次了。所以顶部整体下移 8px（标题 6→14、顶栏按钮 3→12）时，主流程行必须跟着一起下移（42→50），
否则这条间隔会从 13px 压到 5px。同时把「表管理」两个按钮缩到 26 高、126/134 宽 —— 它们和下面那排同高同宽是主因。

**为什么「导出待翻译 / 导入已翻译」最后挪到了统计行右端**（v2.6）：放在顶部按钮行时，它们和「导入新版英文包骨架」
并排，读起来是同一类事 —— 可实际上一个是"换基准"，两个是"把活送出去、收回来"。挪到覆盖率旁边之后，
界面自上而下就是维护流程本身：**标题 → 导入骨架 → 浏览/编辑 → 导出·导入 json → 输出版本 + 生成**，
而且数字（还剩多少要翻）和动作（把这批送走）落在同一行，不用在上下两端来回跳。尺寸也降一档（112×22），
不与底栏的"产出对照表"抢主次。

**页签上的数量（v2.6）**

| 位置 | 内容 | 口径 |
| --- | --- | --- |
| 左侧四个页签 | `节点 942` / `词条 2019` / `界面 411` / `注释 3` | **条目数**：当前筛选 + 搜索下还剩几条（和点进去看到的列表严格同口径） |
| 右侧七个 chip | `全部 7506` / `新增 0` / `未译 343` / `已译 7173` / `孤儿 0` / `待翻译 0` / `待校对 1` | **字段数**：本页签下这一档有多少处要填（与当前筛选无关，各档并列） |

- 两个数不是一回事：条目数是"多少条"，字段数是"多少处要填"。节点页 942 条 / 7506 字段，
  只报条目数会让人低估工作量（平均一条 8 个字段）。
- **"全部"那档就是总字段数**（v2.7）：以前把它单独放在筛选行最右端（`字段 N`），既然每个 chip 都要带数字，
  它就重复了 —— 删掉右端那一处，把宽度让给 chip，7 个 chip 才能各带一个 4~5 位数。
- chip 宽度按内容估（汉字 11px、ASCII 6.5px + 16 内边距，`ovChipWidth`）：写死 46/58 两档时，
  `全部 7506` 会挤爆、`孤儿 0` 又留一大条空白。
- 左侧必须跟着筛选和搜索走，否则"待翻译 43"点进去列出 43 条但页签还写着 942，就没人信这个数字了；
  所以计数与列表**共用同一个判定函数**（`ovItemMatches`），不允许各写一份。
- 实现上只算一次：按 `查询串 + 筛选 + 数据版本号 + 当前页签` 缓存，浮窗没开时不算 —— 为了显示几个数字，
  每次开窗把四个分页全建一遍不值当（首帧会多花 30ms 左右，之后都是缓存）。
  **当前页签必须进缓存键**：chip 的数字是本页签口径，切页不重算就会把上一页的数字留在那儿。

**所有 y 必须由同一条链派生**：`tabsY` 往下推搜索/列表/右栏标题/字段列表，`tabsY` 本身由元信息行 + 回执行行数推出 ——
**禁止在构建器分支里写死任何一行的 y**。历次"页签下方奇怪的空白"都是同一种错误：某几行按一个基准排、另几行按另一个基准排。
已经踩过两次：①分页写死 `102`、`top` 写死 `180`，中间 48px 死空白；②分页改成 `top-36` 后搜索/列表仍按 `top+38` 排，
左列在分页和搜索之间多出 44px。判据：改完必须能用一条公式从 H 推到每一行，出现"这个值刚好合适"就是下一个坑。

#### 4.7.2 右栏：字段行的三种形态

行高统一 78（虚拟列表要求固定行高）。**行高恒定、内容自适应**：只有存在冲突候选的那一行才在底部留
一条 24px 的裁决按钮带，其余行把这 24px 让给输入框（中文译文换行时更易读）。

| 形态 | 标题行（h 16） | 输入框 | 底部按钮带 |
| --- | --- | --- | --- |
| 普通 | `分类名   英文锚`<br>右端：`待翻译` `待校对`（各 58×18） | 19 → 行底，h 52 | 无（整行都归输入框） |
| 改过 | `分类名   英文锚   表内：混合模式`（琥珀）<br>右端：`已改` + 两个开关 | h 52 | 无 |
| **冲突**（§4.11） | `分类名   英文锚`<br>右端：`新包另有译文：混合模式`（琥珀 11px）+ 两个开关 | h 32 | `替换为新包文本` `恢复对照表原文`（96×22，右对齐） |

**两个状态开关是字段级的，位置在每个字段的标题行右端**（`待翻译` / `待校对`，§4.10）：

| 元素 | x（rightW = 564 时） |
| --- | --- |
| 标题文本 `分类名 + 英文锚[ + 表内：…]` | `0 → width − 76`（无冲突）/ `width − 248`（有冲突） |
| `已改` / 冲突候选文本（右对齐） | 止于 `width − togW − 8` |
| `待翻译` `待校对` | `togX = width − 124`，各 58 宽、间隔 8 |

- **为什么必须是字段级**（v2.4 曾短暂改成条目级，2026-10-31 回退）：一个节点里"节点名要翻、端口提示不翻"是常态（`Phong`/`SDF`/单字母轴这类专名、
  纯占位符、示例文本都不该翻）。条目级开关会把这种差异抹平 —— 整条一起标，不想翻的字段也跟着进导出队列，
  等于把"该翻的几十条"重新稀释成"该翻的几百条"。
- 开关宽度 58 = 13（方块）+ 7（间距）+ 36（3 个汉字 @11px），再窄文字会被裁。
- 标题行本来就空着右半截（`英文锚` 很少超过 200px），开关放这儿**不占任何额外行高**；
  早期放在每个字段行底部那一版，每行白吃 24px，一屏少看两条。
- 点击**不重建列表**（理由见 §4.7.3）—— 只改数据、重画当前行、重算当前条目的聚合标记。

**左列表的 `待` / `校` 标记是字段级标记的聚合**：该条目下**任一个键**打了标，左列表就显示标记、
「待翻译 / 待校对」筛选就能筛到它。聚合按 id 归并一次（骨架全部键 + 表全部键），
不是"每个条目各扫一遍全量键"（942 × 17000 是三次方级的浪费）。

#### 4.7.3 筛选：七段 + 刷新时机

`全部 7506 / 新增 0 / 未译 343 / 已译 7173 / 孤儿 0 / 待翻译 0 / 待校对 1` —— 每段 = 标签 + 本页签下的**字段数**，
宽度按内容算（`ovChipWidth`），7 段合计约 470‑520px，正好落在右栏 564 里。

**档位顺序（v2.7 调整）**：「待翻译」「待校对」两个**标记档相邻、排在最右**，孤儿挪到它们左边。
结构事实类（新增/未译/已译/孤儿）在左，可编辑标记类（待翻译/待校对）在右 —— 维护者"打标 / 摘标"时来回复查的就是最右这两个，
相邻排布少跳一格。注意**数组顺序即显示顺序、筛选逻辑也按同一套下标**（`case 4=孤儿 / 5=待翻译 / 6=待校对`），
改顺序必须同步改 `kBldFilterName`、`ovItemMatches` 的 switch、以及 `g_ovFltField` 的计数分支三处，漏一处就会"点了 A 筛出 B"。

| 筛选 | 判定 | 性质 |
| --- | --- | --- |
| 全部 | — | |
| **新增** | 当前骨架里有、对照表里**没有译文**（或根本没这键） | 结构事实，**不可编辑** |
| 未译 | `zh` 为空 | 结构事实 |
| 已译 | `zh` 非空 | 结构事实 |
| 孤儿 | 表里有、当前骨架里没有（按分类判定，§4.2） | 结构事实 |
| **待翻译** | key 在 `meta.pending_translate` | **可编辑标记** |
| 待校对 | key 在 `meta.pending_review` | 可编辑标记 |

**「新增」与「待翻译」看着像，但不是一个东西**：新增是"新骨架里有、表里没有"这一**事实**（导入英文包后自然变化，  
人工无法增删）；待翻译是维护者**决定"这条要翻"**的标记（可以手动取消，也可以给老键重新标上）。两者初始高度重合  
（新键默认就标待翻译），但维护者把一大堆不必翻的键取消标记后，二者就会明显分叉 —— 这正是本特性的意义。

**刷新时机（重要，防误触）**

| 事件 | 列表重算？ |
| --- | --- |
| 搜索词变化 / 切换分页 / 切换筛选 / 重新打开浮窗 / 任一导入动作完成 | ✅ 重算 |
| **字段标题右侧切换「待翻译 / 待校对」开关**（尤其**取消**） | ❌ **不重算** |

理由：在「待翻译」筛选下取消标记，如果立刻重算，当前条目会从列表里瞬间消失、选中项跳到别的条目 ——  
维护者刚发现"这条其实不用翻"，结果它跑了，还得重新搜回来。所以取消标记后**列表原地不动**（该行的状态字符变掉而已），  
等切换页签或换搜索词时自然刷新。实现上就是：开关只改数据 + 重算当前条目的聚合标记（`ovRefreshItemFlags`），
**不调用 `ovRefreshView()`、不动 `view`**。

**「导出待翻译 / 导入已翻译」= 上行右端那两个小按钮**（v2.6）：它们和覆盖率数字是一件事的两面 ——

「导入已翻译」始终可点：它按 key 覆盖，不依赖队列是否为空。

**「清除全部待翻译 / 清除全部待校对」= 上行最左两枚（v2.7）**：把整张表的对应标记一次性摘掉 —— 与「导出」是相反方向的两件事
（导出是"把这批送走"，清除是"这批不用管了、别再来烦我"）。两者都**不可撤销**，故走 `openConfirm` 二次确认，文案里带上受影响的字段数；
当前没有对应标记时两枚都 `btnOff` 置灰。命名必须带「全部」，是为了和右栏标题行的**按条目清除**（`清除待翻译`/`清除待校对`，只摘当前条目）
区分开 —— 两处按钮长相相近、作用范围却差一个量级，文字就得自解释，不能指望用户记住位置。

**两段底色把"编辑"和"产出"分开（v2.6；v2.7 边距微调）**：编辑区（`y = 44` 到 `covY + 24`，即导入按钮行 → 导出 json 行）
铺一层比面板底亮一档的底衬（`0.175/0.185/0.215`，圆角 8，1px 暗边），最下面那行「输出版本 + 生成 + 关闭」留在面板底色上。
之前整屏一个底色，抬头、编辑区、输出区三段的边界全得靠留白去猜；现在从上到下就是
**标题 → 编辑区（导入 / 浏览 / 导出 json）→ 输出区**，底色一换，结构自己就出来了。

- **值必须比面板底亮，且要采样验证**：面板底实测 `(38,38,46)`；初版写 `0.132/0.142/0.170` 出来是
  `(34,36,43)` —— 比面板**更暗**，看着像给内容区挖了个坑。现取 `0.175` 一档 = `(45,47,55)`，才是"提亮"。
  "稍微提亮"这种描述不能靠脑内换算，改完必须抓图取像素比对。
- **这块底衬必须写在 `dialog.content()` 的第一句，且用 `ui.stack` 包裹**：内容层按声明顺序绘制，
  后声明的盖住先声明的；底衬从 y=44 铺到大半屏高，一旦排在分页/筛选之后，就会把标题行以下的
  导入按钮、元信息行、回执、页签、筛选 chip **整片盖掉**（v2.6 就是这么坏过一版，见 §9）。
  裸 `ui.rect` 直接 `.position()` 还会参与内容层的流式布局，包在 stack 里才是绝对定位。

**统计行放在生成按钮正上方**，不是顶部信息带：这几个数字唯一的作用就是决定"要不要导一批出去、还差多少"，
贴着自己影响的那排按钮读起来才顺；反过来放顶部时眼睛要在上下两端来回跳。构建器底栏因此比用户侧高 30（86 vs 56）。

顶部那条位置改放**动作回执**（上一次导入干了什么），只在有回执时占一行 —— 见 §4.7.1 的 ③.5。

**统一置灰（`btnOff`）**：不可用的动作**保留按钮外形**（同样的位置、尺寸、圆角），只把底色调到背景色附近、
文字降到 45% 亮度，并 `disabled(true)` 让点击穿透。不要把它换成一行灰字 —— 用户看不出那里原本是个按钮，
只当成一句提示，下次想点的时候还去别处找。两个置灰点：

- `生成并覆盖当前对照表`：没有未保存改动时（本来没什么可覆盖），悬浮提示说明"改了内容后即可点击"
- `导入已有汉化包`：还没导入英文骨架时（没有对齐的尺子），悬浮提示见 §4.7.1 ②

**置灰按钮不加描边**（`border(0, 透明)`）。按钮组件默认带 1px 边框，边框 + 与面板底几乎同色的填充，
整体读起来就是个**空输入框**（实测被直接指认"像输入框"）。置灰要表达的是"这里有个按钮，但现在按不下去"，
靠"填充比面板亮一档 + 文字降到 45%"就够了；边框一加，反而把"这是输入框"的视觉线索也带上了。

**悬浮提示为什么自绘**：`components::tooltip` 靠 `hoverOpacityFrom` 挂在"源元素"的 hover 状态上，
而置灰按钮不接收指针事件、压根没有 hover 状态可挂。做法：按钮上叠一层透明 `mouseArea` 探 hover
（光标设 `Arrow`，不给可点的手型），提示框画在浮窗内容的最末尾（最后画 = 最上层，面板不裁剪）。
关闭浮窗时主动清空提示 —— 指针停在置灰按钮上直接关窗，`onHover(false)` 不会再来一趟。

**「生成并覆盖当前对照表」必须二次确认** —— 它会把编辑区内容写回 `data/translation_db.json`，覆盖错一次就丢正确内容：

- 弹第二个 `dialog`（460×184，zIndex 400 叠在构建器上），标题 `生成并覆盖当前对照表？`
- 正文：`会用编辑区当前内容重写 data/translation_db.json，版本号为「1.22.0.6-机翻版」。`  
  `覆盖前旧表会复制一份到 data/.db_backup/（文件名带版本号与时间）；已经生成出去的语言文件不回滚。`
- **备份必须真做**（v2.6 修正）：之前只有「修改当前对照表」走 `replaceDbFile` 才备份，
  「生成并覆盖」是裸写 —— 确认框里承诺了 `.db_backup/`，盘上实际只有 `.draft/` 里那份草稿，
  提示与事实不符（用户直接指出来了）。现在 `onBldSave` 先调 `pxc_dbe::backupDbFile()`（与切表共用一份实现），
  再把备份的真实路径写进回执：`旧表备份：…\\data\\.db_backup\\db_1.22.0.5_20261031-043326.json`。
- 按钮 `取消`（左，默认焦点）/ `确认覆盖`（右，低饱和）
- 阻断条件：编辑区无任何改动时按钮置灰（没什么可覆盖的，也就没必要让人确认一次）
- 「改动 37 条」从哪来：现在是 `g_dbDirty` 一个 bool，要改成**改动键集合**（`set<string> dirtyKeys`，编辑/导入时增删），  
  这样既能报数量，也能在确认框里让维护者知道"这次动得比想象多"

**「生成对照表文件…」不碰运行期表**：`IFileDialog` 另存，默认文件名 `translation_db_<输出版本>.json`，  
内容 = 编辑区当前状态（含未保存改动）。它和顶栏「导出当前对照表」的区别见 §4.1 末段。

**两个出口写出的内容完全一致**（`entries` + `keep_english` + `meta` 的四个状态字段 + `version` = 底栏输出版本），  
唯一区别是落点：一个写到用户选的路径，一个写回 `data/translation_db.json`。

#### 4.7.5 导出/导入格式

导出待翻译与导入译文沿用用户偏好那套 `key -> 文案` 差异集合，只是多了 `en`（AI 需要看英文原文）：

```jsonc
{
  "format": "pxc-translate-queue", "format_version": 1,
  "db_version": "1.22.0.6",
  "count": 43,
  "items": [
    { "key": "nodes.Node_Blend.in.Blend mode.name", "en": "Blend mode", "zh": "" }
  ]
}
```

`zh` 是**导出时已有的译文**（重翻的老条目会带值，AI 可以拿来对齐术语），不是"要求填成什么"。  
导出集合 = `meta.pending_translate` 里的全部键，与有没有译文无关。

导入译文时按 key 写入（跳过空值），并做状态转移：**待翻译 → 摘掉、待校对 → 加上**（§4.10）。  
结果是 `写入 N / 跳过空 M / 未知键 K`，不静默吞掉。

### 4.8 导入中文包（预填 + 记录冲突，仍走"差异"通道）

新版本出来时，常常已经有一个（可能翻不全的）中文包。构建器可以直接吃它，但**只当候选来源**：

| 情形 | 处理 | 落在哪 |
| --- | --- | --- |
| 表里该键**没有**译文，包里有 | 用包里的译文预填，记入 `meta.pending_review` | 待校对 |
| 表里该键**已有**译文，包里**文本相同** | 无动作 | — |
| 表里该键**已有**译文，包里**文本不同** | **不动表内译文**，把包里的文本记入冲突候选（§4.11） | 待校对 + 冲突按钮 |
| 包里的键在新骨架里不存在（旧版本残留） | 一律不采用，计入"被忽略 N 条" | — |
| 包里条目的字段类型与新骨架不符（字符串 ↔ `{}`/`[]`） | 不采用，计入结构校验报告 | — |

**默认保留表内中文**是硬规则：表里的译文本就是人工校对过的产物，导入一个陌生包不该让它悄悄变样。  
有更好的译法时由维护者在右侧手动点「替换为新包文本」（§4.11）—— 决策留在人手里，而不是导入的副作用。

结果落在"待校对"筛选里：维护者可以只过这些条目，逐条跟英文比对、改掉机翻腔，确认后清除标记。  
标记存在 `meta.pending_review: ["nodes.X.name", ...]` 这个**键列表**里，而不是给每条目加字段 ——  
17000 条里可能只有几百条待校对，逐条加 `src`/`reviewed` 会让表重新膨胀（这正是 §4.5 删掉 `src` 的原因）。

**与其它通道的关系**：`导出待翻译 → AI 翻译 → 导入译文` 和 `导入中文包预填` 是同一条差异通道的两种来源  
（人 / 机器 / 别人的包），最终都只是 `key -> 译文` 的补空动作。这也是为什么用户偏好文件、待翻译队列、  
中文包预填三者能共用一套读写代码。

### 4.9 当前对照表的管理（三个出口，不必去软件目录替换文件）

构建器管理的就是运行时用的那一份表。围绕它有**三**个动作，两个在标题行（快照 / 换表），一个在底栏（产物）：

| 位置 | 按钮 | 行为 | 用途 |
| --- | --- | --- | --- |
| 标题行右 | **导出当前对照表** | 复制**磁盘上那份表原样**到任选目录（默认 `translation_db_1.22.0.5.json`）：不含本次修改、**版本号也不变** | 纯备份点；覆盖前的回退点；给别人看"我现在这份" |
| 标题行右 | **修改当前对照表** | 用选中的 json 替换 `data/translation_db.json`（旧文件移到 `data/.db_backup/<版本>_<时间戳>.json`） | 试别人给的表、回到旧版本的表、多机器搬运 |
| 底栏 | **生成对照表文件…** | `IFileDialog` 另存**表 + 本次改动合并后的新版本**（`meta.version` = 底栏输出版本） | 产出新版本；交付、评审、给 AI 之前留底 |

三者语义不同，别混：**前两个面对"已经生效的表"，第三个产出"新的表"**。前者是快照（原样、版本不变），  
后者是结果（合并、版本更新）。顶栏那对按钮加只读的版本号文本凑成一组，维护者一眼能看出"我现在用的是哪份表、能换成哪份"。

导入时校验：顶层有 `entries` 对象、`meta.version` 可缺省（缺了就按骨架猜）、条目值至少含 `zh` 字段。  
不合法直接拒绝并说明原因，**不做"尽力而为"的部分导入** —— 半个表比没有表更危险。  
版本号不同不影响使用：表自带版本，运行期只显示 `meta.version`（生成页状态行会跟着变）。  
换表后顶栏的「当前对照表版本」立刻跟着变，但**底栏输出版本不会自动跟随**（它代表"这次要发布成什么版本"，  
是维护者的决策，不该被换表动作悄悄改掉）。

### 4.10 状态标记总览（待翻译 / 待校对写进表，新增 / 孤儿实时算）

17000 条里，任何一个"状态"如果逐条存进条目，表就会膨胀到不可读。所以状态一律**集中存放在 `meta`**，  
条目保持 `{en, zh}` 两字段不变。

| 标记 | 存哪 | 谁写入 | 谁清除 | 作用 |
| --- | --- | --- | --- | --- |
| **新增** | 不存，实时算 | — | — | 筛选用：骨架里有、表里没译文。**结构事实，不可编辑** |
| **待翻译** | `meta.pending_translate: [key]` | ① 导入英文包时**本次新出现的键**默认全标（=`meta.added_keys` 那个集合）<br>② 字段标题右侧开关（**字段级**，任何键都能标） | 手动编辑该键译文时自动摘；导入译文时**转为待校对**；开关手动关 | 决定「导出待翻译」的范围；跨会话续翻 |
| **待校对** | `meta.pending_review: [key]` | 导入中文包预填的键、冲突键、**导入的译文**；开关手动标 | 手动编辑译文时自动摘；冲突按钮裁决时摘；开关手动关 | 筛选用：机器或他人译文的复核队列 |
| **冲突** | **仅内存**（§4.11） | 导入中文包时发现同键不同文 | 下次导入中文包时重建；落盘时材质化 | 右侧两个按钮的候选来源 |
| **孤儿** | 不存，实时算 | — | — | 筛选用；**保留且仍参与生成**（§4.2） |

**两个标记都是维护者亲手打的，不是系统算出来的结论** —— 所以它们必须是**显式开关**（§4.7.2），一直可见、随时可改。  
系统只在几个**明确的时刻**替人动手：

| 事件 | 待翻译 | 待校对 | 为什么 |
| --- | --- | --- | --- |
| 导入英文包，**本次新出现**的键 | ＋（默认全标） | — | 新增内容天然要翻；不必翻的由人一轮勾掉 |
| 导入英文包，老键仍无译文 | **不动** | — | 见下"为什么不能给所有未译键打标" |
| 导入中文包，空位预填 | －（有标记就摘，因为它已经被填上了） | ＋ | 别人/机器的译文，必须人看一眼 |
| 导入中文包，同键不同文 | — | ＋ | 同上，另外还有两个按钮要裁决 |
| **导入译文** | **－** | **＋（转移，不是清空）** | 机翻产物：已经不是"要翻"，但"翻得对不对"要人确认 |
| **手动编辑译文** | **－** | **－** | 人亲手写的，既翻完了也校过了，再挂标记等于逼他点两次 |
| 冲突按钮裁决 | — | － | 明确做了选择，这条的复核就结束了 |
| 任一条的显式开关 | 手动切换 | 手动切换 | 常态：维护者就是靠它把一批老字段塞进队列重翻 |

**标记的粒度是「键」，不是「条目」**（v2.5 修正）：同一个节点下每个字段各自有开关。左列表与筛选看到的是
**聚合**结果（任一个键打了标就算），但落盘的是那个具体的键 —— 否则"这个节点名要翻、它的端口提示不用翻"
这种最常见的判断就没法表达，而导入英文包默认打标本来就是按**键**算的（`meta.added_keys` 是键集合）。

**"值没变"绝不能动标记**（v2.7 修的真 bug）：`ovSaveAll` 是每次切条目 / 切页签 / 切筛选时
**无条件**跑一遍的（把右栏编辑框里的值写回表），而 `setTranslation(..., reviewed=true)` 早期在
`zh == 当前值` 时也会顺手摘掉 `pending_review`。于是刚打上的「待校对」在切页那一瞬间被自己摘掉：
**字段开关不亮、chip 上的待校对变 0，只有左列表那条聚合标记因为没重算还留着** —— 看起来就是"标记跑了"。
判据很朴素：**值没变 = 用户什么都没做**，那就什么都不该改；"改过译文 = 校过"由 `zh != cur` 那条分支表达。
回归断言：`编辑：值没变时不许动待校对标记（切页不能把标记悄悄摘掉）`（`tmp/gen_test.cpp`）。

**左列表的标记必须归到"它自己那一条"上**（v2.6 修的真 bug）：切换条目/页签时是先把 `pd.sel` 指向新条目、
再调 `ovBuildRows`，而里面的 `ovSaveAll` 用 `pd.sel` 定位"这批编辑框属于谁" —— 于是旧条目的汇总结果
（`zh` / 已改 / 待翻译 / 待校对）被写进了新条目。现象很好认：给 A 打「待翻译」后点 B、再点回 A，
A 的「待」不见了，B 却顶着一个打不开的「待」（右侧开关读的是表本身，当然是灭的）。
现在 `g_ovRowsOwner` 记着这批编辑框属于哪个下标，保存时只往它身上汇。

**为什么不能给所有未译键打标（曾经就是这么写的，被实测推翻）**：表里只存有译文的条目，所以"从没翻过"
和"维护者判定过不翻、把标记取消了"这两件事在表里**长得一模一样**（都是"没有 zh、不在队列里"）。
早期实现按"所有未译一律补标"来写，结果维护者每重新导入一次同一份英文包，上一轮手工取消掉的上百个标记
就原地复活一次 —— 队列一边取消一边长回来，而"新增"筛选又是空的（结构上确实没有新键），现象很难解释。

判据只能是**这一次导入里骨架新出现的键**（键集合差集，落盘在 `meta.added_keys`）：只有它们默认进队列。
老键要翻，用右侧开关手动勾 —— 那才是维护者的显式意图。`syncSkeleton` 因此收一个 `newlyKeys` 参数，
传 `nullptr` 表示"全部未译都标"（仅首次建表用）。

**为什么"导入译文"是转移而不是摘掉**：AI 交回来的东西恰恰最需要人看（术语漂移、语序僵硬、把 `Blend` 翻成"混合模式"而表里统一叫"混合"）。  
如果导入即摘，那批译文就再也没人过一遍；转进待校对，明天打开还剩多少条要复核一目了然。

**为什么"待翻译"和"待校对"是两个标记**：前者问"**要不要翻**"，后者问"**翻得对不对**"。  
一条刚预填的机翻译文是"不用翻、待校对"；一条新增键是"要翻、无译文"；两者要同时存在。

**为什么要"待翻译"这个标记，而不直接导出全部未译**：PXC 语言文件里大量条目本就不该翻  
（单字母轴、`Phong`/`SDF` 之类的专名、`%s` 纯占位、示例文本）。导出全部未译 = 把几千条噪音丢给 AI 和人工，  
真正该翻的几十条形不成队列。有了标记，维护者只需要在开始前扫一遍、把"该翻的"勾上（新键默认全勾已经接近答案），  
之后每次导出都只带这些。**已经译好的条目同样可以打进队列**（想重翻、统一术语时），导出时带上现有 `zh` 供参考。

**为什么标记要写进表**：翻译一份 1.7 万条的表往往要跨好几天。标记写进 `meta.pending_translate`，  
下次打开就知道"上次还剩 43 条没翻/几号没校"，不必自己记。

### 4.11 冲突候选：只存新包文本 + 一个选择位

导入中文包时，若某键**表里有中文、包里也有中文、两者不同**，构建器不替维护者做决定：

| 值 | 在哪 | 说明 |
| --- | --- | --- |
| `zh` | 条目本身 | 表内原文，**编辑期间永不改动** —— 所以"原文"根本不需要另存 |
| `pack` | `conflicts[key].pack` | 新包里给的文本（候选，仅内存） |
| `use` | `conflicts[key].use` | 显示/输出用哪一份：`false`（默认）= 表内中文，`true` = 新包文本 |

右侧字段行因此多出两个迷你按钮（位置见 §4.7.2）：

| 按钮 | 动作 | 何时可用 |
| --- | --- | --- |
| 替换为新包文本 | `use = true` | `use == false` |
| 恢复对照表原文 | `use = false` | `use == true` |

输入框显示的是 `use ? pack : zh`。维护者直接在框里改字 → 视为人工裁决：`zh = 新值`，删掉该条冲突记录，摘掉待校对。

**为什么不存 `base`（你定的）**：因为"替换"**不改 `zh`**，只改 `use`。原文就是 `zh`，它一直在那儿，  
所以没有"原文已被覆盖、只能靠备份找回来"的那一天 —— 少存一段文本，也少一条会在半年后咬人的失效路径。  
两个按钮都是纯内存开关，来回点多少次都安全。

**落盘时材质化**：`use == true` 的键把 `pack` 写进 `zh`，然后**清空整份 conflicts**，再写出文件。  
所以产物里没有任何候选概念（§4.6），运行期生成器不需要知道这件事。

**代价（说清楚）**：`conflicts` 只在内存，关掉软件后候选就没了，下次要重新导入中文包。  
可接受——导入是一次点击，而"这条用谁的译法"本来就是当场该做的判断，不是能拖三天的事。
