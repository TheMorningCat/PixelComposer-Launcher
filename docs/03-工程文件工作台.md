## 7. 工程文件工作台（v3）

> 本章解决三件事：**让 .pxc 双击直接落到对应版本**、**版本不在本机时给一条不毁文件的路**、**把"找工程"收进一个真能用的列表**。
> 前两件是行为，第三件是界面。三者的数据源**都不归启动器所有**（PXC 自己的 `recent.json` 与 `Autosave/`、用户手工拖入的文件），
> 所以本章有一半篇幅在讲"怎么读别人的数据而不改它"。

### 7.0 范围

| 做 | 不做 |
| --- | --- |
| 注册 / 取消 `.pxc` 关联（只写 HKCU） | 篡改 Windows 的 `UserChoice` 哈希（属规避系统机制，且随系统更新失效，见 §7.2） |
| 双击 → 识别 → 匹配版本 → 启动 | 自动下载 / 安装缺失版本的 PXC |
| 缺版本时协商：推荐 + 副本启动 | 把工程"升级 / 降级转换"（那是 PXC 保存时自己的行为） |
| 五个页签（近期 / 全部 / 导入 / 收藏 / 自动恢复） | 删除 `Autosave/` 里的历史快照（不碰用户数据） |
| 收藏、导入、启动历史（启动器自己的数据） | 替代 PXC 的工程浏览器（不做缩略图、不做工程内容预览） |

### 7.1 数据源（实测，2026-10-31 本机）

| 页签 | 位置 | 谁写 | 实测规模 |
| --- | --- | --- | --- |
| 近期文件 | `<用户目录>/recent.json` 的 `Recents`（字符串数组，最新在前） | **PXC 写，启动器只读** | 26 条，26 条路径全部有效 |
| 自动恢复 | `<用户目录>/Autosave/*.pxc` | PXC 写，只读 | **3486 个 / 191 MB**；**全量展示、按 mtime ↓、不折叠不去重**；最新一份落在 7 天内 10 个、30 天内 14 个、90 天内 51 个 |
| 全部 | `data/projects.json → history` | 启动器写 | 初始 0 |
| 导入 | `data/projects.json → imported` | 启动器写 | 初始 0 |
| 收藏 | `data/projects.json → favorites` | 启动器写 | 初始 0 |

**用户目录怎么定位**（复用 `pxc_base::findUserDirs()`，见 `baseline_scanner.cpp:210`）：

1. 读 `%LOCALAPPDATA%\PixelComposer\persistPreference.json` 的 `"path"`（**PXC 自己的重定向记录**）；
2. 再退回 `%LOCALAPPDATA%\PixelComposer` / `%APPDATA%\PixelComposer`。

> 本机的实际情况正好说明了为什么不能偷懒：`persistPreference.json` = `{"path":"D:\\我的文档\\软件\\PixelComposer用户目录\\"}`，
> 真正的 `recent.json`（26 条）与 `Autosave/`（3486 个）都在 **D 盘那份**；而 `%LOCALAPPDATA%\PixelComposer\` 下还躺着一份
> **2026-09-24 的旧 `recent.json`（46 条）**。硬编码 `%LOCALAPPDATA%` 会让用户看到几个月前的工程列表，且没有任何报错 —— 这种
> "静默读到过期数据"比崩溃更难查。

**自动恢复的命名规则**：`<工程名>_autosave<YYYY-MM-DDTHHMMSS>.pxc`。
未命名工程的名字为空（`_autosave2026-05-17T015235.pxc`，本机 **176 个**）—— 列表里显示为 `未命名工程`，与其它快照一样按时间排列（不折叠、不去重）。

### 7.2 文件关联（`.pxc` → 启动器）

只写 **HKCU**（不需要管理员，也不影响其它用户）：

```
HKCU\Software\Classes\.pxc
    (默认)                          = PXCLauncher.pxc
    OpenWithProgids\PXCLauncher.pxc = (空值)
HKCU\Software\Classes\PXCLauncher.pxc
    (默认)                          = "PXC 工程文件"
    FriendlyTypeName                = "PXC 工程文件"
    DefaultIcon                     = "<launcher.exe>,0"
    shell\open\command              = "\"<launcher.exe>\" \"%1\""
```

写完必须 `SHChangeNotify(SHCNE_ASSOCCHANGED, SHCNF_IDLIST, nullptr, nullptr)`，资源管理器才会立刻刷新图标与双击行为；
不通知的话要等下次登录（用户会以为"没生效"）。

**三态 + 自检**：

| 状态 | 判据 | UI |
| --- | --- | --- |
| 未关联 | `HKCU\Software\Classes\.pxc` 默认值不存在或为空 | 「关联 .pxc 文件」可点 |
| 已关联 | 默认值 == `PXCLauncher.pxc`，且 `UserChoice` 缺失或等于我们 | 「已关联」+「取消关联」 |
| 被其它程序占用 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\FileExts\.pxc\UserChoice\ProgId` 存在且 ≠ 我们 | 「已被其它程序占用」+ 引导「打开方式 → 始终使用启动器」 |

> **为什么不直接抢默认程序**：Win8+ 的 `UserChoice` 带哈希（扩展名 + ProgId + 用户 SID + 时间戳），程序自己写会被系统判为无效并重置；
> 网上流传的"算哈希"依赖未公开算法，随系统更新失效，而且是在绕过系统的默认程序保护 —— 这条不做。
>
> **正确的做法**：把我们的 ProgId 写进 `OpenWithProgids`，让 `.pxc` 出现在「打开方式」里，然后**引导用户点一次「始终使用」**。
> 那一步由系统自己写 `UserChoice` 哈希，永久有效。所以我们能保证的只有"出现在候选里"，不能保证"自动成为默认" ——
> 这是代价，但比一个随时会被系统重置的假成功要好。

**取消关联**：删 `HKCU\Software\Classes\.pxc`（**仅当默认值仍是我们**，否则不动别人的）、删 `PXCLauncher.pxc` 子树；
若当初记了 `previous_progid` 且非空，写回。不写 `HKCR`（那是 HKLM+HKCU 的合并视图，写它会落到 HKLM，要管理员）。

### 7.3 双击启动链路

```
双击 a.pxc
  └─ shell 执行：  "<launcher.exe>" "D:\...\a.pxc"
        ├─ 单实例检查（CreateMutexW(L"Local\\PXCLauncher.Instance")）
        │    ├─ 已存在 → 找到已有窗口，WM_COPYDATA 传路径 → 本进程立刻退出(0)
        │    └─ 不存在 → 继续
        ├─ detectPxc(a.pxc) → version / confidence
        ├─ findMatching(registry, version)
        │    ├─ 命中 → 静默启动（不显示主窗，见下）
        │    └─ 未命中 / 版本未知 → 显示主窗（工程文件页）+ 打开协商弹窗（§7.4）
        └─ 写 history（projects.json，节流 500ms）
```

**为什么必须单实例**（三条独立成立的理由，不是"顺便统一一下"）：

1. `projects.json` / `launcher.json` 都是**整文件改写**，两个实例同时写必然互相覆盖 —— 后写的赢，前一个刚收藏的条目就没了；
2. 双击 5 个文件会开 5 个启动器窗口，用户得挨个关；
3. 同一个工程被两个 PXC 实例打开，PXC 自己的 autosave 会互相覆盖 —— 这不只是界面问题，是**用户的文件风险**。

窗口查找方式：EUI 的窗口类名由框架内定，`FindWindow(className)` 不可靠 →
`RegisterWindowMessageW(L"PXCLauncher.Activate")` 广播 + `EnumWindows` 里匹配
`GetWindowThreadProcessId` → `QueryFullProcessImageNameW` 的 exe 名。找不到就自己开窗（退化为多实例，但不死锁）。

**静默启动（默认开）**：建窗 → `ShowWindow(hwnd, SW_HIDE)` → 启动 PXC → `PostQuitMessage(0)`。
配置项 `assoc.silent_launch`，关掉后总是显示启动器（调试用）。
> 风险：EUI 初始化可能在 hide 之前画出首帧（白闪一帧）。实现时先试"创建即隐藏"，若实测有闪，退路是接受 1 帧
> （不影响功能，只影响观感）。

#### 7.3.1 「让 PXC 真的打开这个文件」—— 实测结论（2026-10-31）

实测环境：PXC 1.18.5（工作目录副本）、1.20.1（安装目录）；工程用 `工程文件样本/1.18.5` 复制到 `tmp/proj_test` 的副本，
测试前后备份并恢复了 `recent.json`，未污染用户数据。

| 级 | 做法 | 实测结果 |
| --- | --- | --- |
| **R0** | `CreateProcessW(exe, "\"<exe>\" \"<pxc>\"")` —— 命令行传路径 | **可行**。窗口出现后 `recent.json → Recents[0]` 即为目标文件，无需任何额外操作 |
| **R1a** | 构造 `HDROP`，用 `SendMessageTimeout` / `PostMessage` 投 `WM_DROPFILES` | **无效**。消息被接收（返回 1、err 0），PXC 无任何反应；4 个落点（节点图中心、窗口中心、左上、二次投递）全部无效 |
| **R1b** | **真实鼠标拖拽**（OLE）到节点图区 | **有效**，且是**同进程新增文件标签**（见 §7.3.2） |
| **R1c** | `Ctrl+O` 打开 PXC 自己的文件对话框，程序化填入路径并确认 | **可行**，且是**同进程新增文件标签**；对话框可纯消息驱动（详见 §7.3.3） |
| **R2** | 兜底文案 | 保留 |

四条必须记住的硬事实：

1. **要等 ≈18.5 秒，不是 8 秒**。`CreateProcess` → 主窗可见实测 **18.2 / 18.3 / 18.4 / 18.5 / 18.7 s**（第二次启动更慢，43 s）。
   PXC 自己日志的 `init Font 278ms`、`init Nodes 424ms`…… 合计 2.7 s 是**引擎内**耗时，exe 加载 + GameMaker 初始化占掉另外 15 秒。
   → 启动器等待上限 **30 s**、250 ms 轮询；超时后仍按"已启动"处理（进程在、窗口没出，属 PXC 自身慢，不是启动失败）。
2. **不能用窗口标题判定**。Win32 标题恒为 `Pixel Composer 1.18.5 itch`（GameMaker 把类名当标题），用户看到的
   `AAA_first.pxc` 是 PXC 在**客户区内自绘**的标题栏 —— 两者不是同一个东西。
3. **`WM_DROPFILES` 无效的根因**：PXC 的 `file_dropper_x64.dll` 走 **OLE 拖放（IDropTarget）**，不处理传统拖放消息。
   所以"程序化投递文件"必须走 OLE，发消息这条路已经封死。**这条已在源码里定案**（`file_dropper.cpp` 只调
   `RegisterDragDrop`、全程没有 `DragAcceptFiles`）—— 见 §7.3.5 ④。
4. **`Ctrl+O` 那一下必须是真实按键**（`SendInput` / `keybd_event`），不能用 `PostMessage(WM_KEYDOWN)` 顶替：
   PXC 是 GameMaker 程序（主窗类名 `YYGameMakerYY`），修饰键靠 `GetKeyState` 读**本线程键盘状态**，
   `PostMessage` 只把消息塞进队列、不改那个状态 —— Ctrl 会被判成"没按下"。
   而这也是全链路里**唯一**依赖"PXC 在前台"的一步，所以发键前必须校验 `GetForegroundWindow() == pxcHwnd`。

**判定仍用数据**：`recent.json → Recents[0] == 目标路径`。但要先看 mtime —— PXC 不是原子写，
读取时若 mtime 在 1 s 内变过，退 200 ms 再读一次，避免读到半截文件。

#### 7.3.2 同版本第二个工程：复用已有进程（实测可行）

| 尝试 | 结果 | 说明 |
| --- | --- | --- |
| 已有实例，再 `CreateProcess(exe, B)` | **新进程**（1 → 2） | PXC 没有单实例转发，两个进程互不知道 |
| `exe A.pxc B.pxc`（多参数） | 只打开**最后一个** | `Recents[0]` = B，A 未加载；不是"多开" |
| 拖 B 进 A 的节点图区 | **同进程并存**：`Panel_Graph` 底部出现两个文件标签 `AAA_first` / `BBB_second` | 切标签即切工程（标题栏 / Inspector / Preview 全跟着变） |
| **`Ctrl+O` → 文件对话框 → 选 B** | **同进程并存**：标签栏出现 `AAA_first` + `中文测试工程` | 与布局无关，对话框可完全程序化（§7.3.3） |

**结论**：PXC 是**多文档 + 文件标签**。外部入口有两个：**`Ctrl+O` 文件对话框**与**拖放**，两者都能同进程追加标签。
命令行只认一个文件，也没有实例转发 —— 所以"复用已有进程"只能靠这两条外部入口。
（源码依据：`Create_0.gml` 无任何转发代码、`LOAD()` 是唯二的按路径打开入口，见 §7.3.5 ⑤。）

**落点约束是真的**（用户判断正确）：

| 落点（1920×1040 全屏，Normal 布局） | 结果 |
| --- | --- |
| `Panel_Graph` 内部，`(1300, 900)` | ✅ 同进程新增标签 |
| 窗口中心 `(960, 520)`（当时是 `Panel_Preview`） | ❌ 无反应 |

但不必靠猜坐标：PXC 的布局就写在 `<用户目录>/layouts/<布局名>.json`，是 `split` + `width` 的树，
`Panel_Graph` 是其中一个叶节点（本机 Normal 布局：Graph 在左下、Preview 在左上、Inspector 在右）。
启动器读这棵树算矩形；算不出就退到**像素探测**（Graph 面板的网格底色是特征色，取窗口内该色最大连通矩形的中心）。

#### 7.3.3 复用已有进程：`Ctrl+O` 首选，拖放备选

**首选 `Ctrl+O`（实测全通，2026-10-31）**：

```
判定是否有同版本实例
  EnumWindows → GetWindowThreadProcessId → QueryFullProcessImageNameW
  → 按 exe 路径归一比对（不比版本串：同一版本可能装在两个目录）
  取该进程里「可见 + 还原后宽 > 400」的顶层窗为主窗
      ↑ 尺寸必须取 GetWindowPlacement.rcNormalPosition，不能用 GetClientRect
        （最小化时 GetClientRect 返回 0×0，主窗会被下面这条 >400 的判据筛掉，见 2026-11-01 修正 #3）

有实例：
  if IsIconic(pxcHwnd) → ShowWindow(SW_RESTORE) 并轮询到 !IsIconic（≤1.5 s，还站不起来就放弃）
                         // ShowWindow 是投递给目标线程的异步动作，调完立刻查状态还是旧的
  SetForegroundWindow(pxcHwnd)            // 失败则 AttachThreadInput 后重试（最多 4 次）
  置前后压 150 ms，再发按键              // 目标进程要先处理完还原/激活才读键盘
  if GetForegroundWindow() != pxcHwnd → 放弃复用，走新进程   ← 必须校验，否则按键打到别的程序
  SendInput: Ctrl↓ ⏸120ms O↓ ⏸120ms O↑ ⏸120ms Ctrl↑     ← 必须分帧，见下方「2026-11-01 修正」
  轮询 ≤ 5 s 找对话框，认的特征 = #32770 + 有可见 Edit + 按钮含「打开」/ Open
      ├─ 没等到              → 放弃复用（日志 reuse=no_dialog）
      └─ 等到 → SendMessage(edit, WM_SETTEXT, 目标路径)
                SendMessage(btnOpen, BM_CLICK)
  校验 ≤ 6 s：**目标对话框消失** → 成功（reuse=ctrl_o；recent.json 命中只当额外佐证）
             否则 → WM_CLOSE 关掉残留对话框 → 走新进程（reuse=failed）
```

实测证据：

| 项 | 结果 |
| --- | --- |
| `Ctrl+O` 弹不弹对话框 | ✅ `#32770`，标题 `Open`，960×540，模态 |
| 能否纯消息填框 | ✅ `WM_SETTEXT` 到文件名 `Edit`（`ComboBox > Edit`），读回与目标完全一致 |
| 能否纯消息确认 | ✅ `BM_CLICK` 到 `打开(&O)` 按钮（返回 0 但有效：对话框关闭、工程打开） |
| 中文路径 | ✅ `中文测试工程.pxc` 正常打开、标签显示中文名 |
| 新增还是替换 | ✅ 标签栏 `AAA_first` + `中文测试工程` **并存**，进程数保持 **1** |
| 外部已有实例（不跟踪 pid，按进程 + exe 路径找主窗） | ✅ 同样成功 |
| PXC 不在前台（前台被记事本占着） | ✅ `SetForegroundWindow` 真正生效（返回 True 且 `GetForegroundWindow()` 已切过去），全链路成功 |

**2026-11-01 修正：三个让"已有实例复用"失效的问题**

这一支在 1.18.5 上分解动作都验过，但没和启动器串起来跑过（见 §7.13.6）。在 PXC 1.20.1 上真跑，先后撞到三处死路：

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 日志 `reuse=no_dialog`：找不到对话框 | **4 个按键事件一次 `SendInput` 全落下**（彼此 <1ms）。PXC 是 GameMaker 程序，**按帧轮询键盘状态**；等到下一个逻辑帧，Ctrl 与 O 都已抬起，`Ctrl+O` 的按下沿从未被观测到。`SendInput` 返回 4（"成功"），但等于没按 | 拆成 4 次 `SendInput`，每步间隔 120ms。实测：一次全发 6 秒内无对话框；分帧后 **0.3 秒弹出** |
| 2 | 就算弹了框也会判失败 | 两个校验依据在 1.20.1 上都是死的：① `recent.json` **只在 PXC 正常退出时写**（实测当天整个用户目录零写入，文件停在 9-24）；② **窗口标题不随标签切换变化**（新开标签后 `GetWindowText` 仍是旧工程名） | 改成**以「目标对话框消失」为准**（点取消要人手动点，我们没发过 `WM_CLOSE`），`recent.json` 命中只当佐证 |
| 3 | PXC 缩在任务栏时**流程卡住不动**，手动点开任务栏窗口才继续（表现为"启动器叫不醒 PXC"） | **找主窗的尺寸判据用错了 API**。`enumWinProc` 用 `GetClientRect` 的宽度做 `> 400` 过滤，而**窗口最小化时它返回 0×0**（实测 1.20.1：正常 1040×720 → 最小化 0×0，`GetWindowRect` 变成 160×28）；主窗因此被当成"启动画面/小工具窗"筛掉，`mainWindowOf` 返回空，调用方以为"进程在但主窗还没出来（正在冷启动）"，去空等 **20 秒**轮询。用户手动点开的那一瞬窗口才有尺寸 —— 所以看起来像"只有点开它才继续"。注意 `IsWindowVisible` 最小化时仍是真，不会被这条筛掉 | 改用 `GetWindowPlacement().rcNormalPosition` 判尺寸（**还原后**的矩形，最小化时照样 1056×759），并新增 `waitRestored()` 把「还原」从一次性调用改成轮询到 `!IsIconic`；还原失败直接返回 `ForegroundFailed`（文案区分"缩在任务栏且无法还原"），不再往下发键 |

实测（1.20.1，窗口最小化态）：修复前日志停在"等主窗"，手动恢复后才 `reuse=ctrl_o`，全程 4–8 秒且依赖人工；修复后**启动器 3.1 秒退出**、`静默复用成功 | reuse=ctrl_o`、PXC 窗口被自动还原到前台、原实例里新增目标工程标签。

顺带：同一 exe 可能有多个实例（复用失败退化成新进程就会积一个），现在**优先取前台那个**的 pid。

**为什么默认不选"多开一个进程"**：`Ctrl+O` 复用在 1.20.1 上实测不到 3 秒就完成（启动器随即退出），
比冷启动一个 PXC（≈18.5 s）快一个数量级 —— 这才是值得修它的原因，不是"锦上添花"。

**为什么它比拖放好**（选它的理由，不是"顺便试了一下"）：

| | `Ctrl+O` | 拖放 |
| --- | --- | --- |
| 依赖布局吗 | **不依赖** —— 用户怎么改面板都行 | 依赖 `Panel_Graph` 矩形，读不到要退像素探测 |
| 动不动鼠标 | **不动**（纯键盘） | 移光标 + 按住拖 1–2 s |
| 失败残留 | 一个文件对话框 → 我们主动 `WM_CLOSE` | 无残留，但可能把窗口拖歪 |
| 落点打空 | 不存在 | 存在 |
| 总依赖 | 真实按键 + 前台 | 真实按键 + 真实鼠标 + 前台 + OLE + 布局解析 |

**拖放降级（R2，只在 `Ctrl+O` 反复失败时开）**：程序化 OLE 拖放 ——
`SHCreateDataObject(CF_HDROP)` + 专用 STA 线程 `DoDragDrop`，并行用 `SendInput` 把光标移到 `Panel_Graph` 中心并释放左键。
落点从 `<用户目录>/layouts/<当前>.json`（`split` + `width` 的树，`Panel_Graph` 是叶节点）算；
算不出退**像素探测**（Graph 面板网格底色是特征色，取窗口内该色最大连通矩形中心）。
实测落点约束是真的：`(1300, 900)`（Graph 内）成功，`(960, 520)`（当时是 Preview）无反应。

**两条路共同的风险**：

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| PXC 以管理员运行、启动器不是 | UIPI 拦 `SendInput` / OLE | 先比进程完整性级别，高于自己就放弃复用 |
| PXC 不在前台 / 被遮挡 | 按键打到别的程序，**可能误触对方快捷键** | 发键前强制校验 `GetForegroundWindow() == pxcHwnd`，不成立就不发 |
| 用户此刻正在 PXC 里按键 / 拖东西 | 抢输入 | 查 `GetAsyncKeyState(VK_LBUTTON)` + 最近输入时间，忙则放弃复用 |
| 弹的是别的对话框（如"是否保存"） | 误点 | 只认【`#32770` + 可见 `Edit` + 按钮含「打开」/ Open】，其余一律 `WM_CLOSE` 并放弃 |
| PXC 正忙（模态 / 长任务）不响应 `Ctrl+O` | 等不到对话框 | 8 s 超时即退新进程 |

**开关**：`assoc.reuse_instance`（默认开）。关掉 = 永远新进程。

**为什么不直接接受多进程**：PXC 本身支持多文档，能做就用；但复用失败**不阻塞用户** ——
退新进程只是"多一个窗口"，不是错误，所以整条链路允许随时降级。

**首次启动仍走命令行（R0）**：没有同版本实例时，`CreateProcess(exe, "\"<路径>\"")` 一步到位，
不需要对话框、不需要前台 —— 这是最短路径。`Ctrl+O` 只用于"已有实例"这一种情况。

#### 7.3.4 失败分支

| 情形 | 处理 |
| --- | --- |
| 登记的 exe 不存在（被删 / 移动） | 版本库里该条目标红；协商弹窗里该候选置灰并注「exe 已丢失」；提示去版本库重新登记 |
| 工程文件不存在 | 主窗 + 提示 + 该行标「已丢失」（**不自动删**，移动硬盘接上就回来） |
| 同版本已在运行、开的就是这个工程 | `SetForegroundWindow` 聚焦，**绝不重发打开**：`LOAD_PATH` 对同名工程会先 `closeProject` 再开，而已修改的工程 `closeProject` 会弹保存框打断用户（`panel_graph.gml:5733`）。判定用 `projects.json.running`，不猜 `recent.json` |
| 同版本已在运行、开的是别的工程 | 先 `Ctrl+O` 复用（§7.3.3）；等不到对话框 / 校验不过则新进程 |
| 复用途中留下文件对话框 | 立刻 `WM_CLOSE` 关掉（不让用户收拾）|
| PXC 不是前台且置前失败 | 不发按键，直接新进程（避免误触别的程序）|
| 不同版本已在运行 | 与本次无关，不处理 |
| `CreateProcessW` 失败 | 回执带 `GetLastError()`，日志记 ERROR + 目标路径 |

#### 7.3.5 源码考证（Pixel-Composer 开源仓库，2026-10-31）

本机 `Pixel-Composer-main/` 是 PXC 的 GameMaker 工程（2157 个 `.gml`）。把"打开工程"的所有入口都追到了源码，
结论与 §7.3.1–7.3.2 的实测**逐条对应**，下面每条都能落到文件与行号。

**① 工程打开只有一个汇聚点**

```
命令行 ──┐
拖放   ──┼──▶ load_file_path(path, x, y) ──▶ LOAD_PATH ──▶ LOAD_AT
Ctrl+O ──┘                                    （APPEND 则追加进当前图）
```

| 函数 | 位置 | 作用 |
| --- | --- | --- |
| `load_file_path(path, _x, _y)` | `scripts/panel_graph/panel_graph.gml:5752` | 分发器：`.pxc`/`.cpxc` → `LOAD_PATH`；`.pxcc` → `APPEND`；图片 / `txt` / `csv` / `json` / `obj` / `svg`… → 建节点；按住 `Shift` → 弹对话框 |
| `LOAD_PATH(path, readonly, safe_mode)` | `scripts/load_function/load_function.gml:92` | 打开工程，并决定「新标签 / 复用面板」 |
| `LOAD_AT(path, params)` | 同上 `:144` | 真正解析文件内容 |
| `LOAD(safe)` | 同上 `:67` | 弹 `get_open_filename_compat` 对话框 → `LOAD_PATH`。**这就是 `Ctrl+O`** |
| `APPEND(path, context)` | 同上 | 追加进当前图（`.pxcc` 用） |

> `load_file_path` 第一行就是 `if(!is_array(path)) path = [path];` —— **原生支持数组**。
> 所以**拖放是唯一能"一次开多个"的外部入口**：一次拖 N 个 `.pxc` → 循环 `LOAD_PATH` → N 个标签。

**② `LOAD_PATH` 的三分支 —— 解释了"为什么有时不新增标签"**

`load_function.gml:92–125`：

| 条件 | 行为 |
| --- | --- |
| `PROJECTS` 里已有**同路径**工程 | 先 `closeProject(那个)` 再打开 → **重载，不会出现两个同名标签** |
| 当前工程是**空白未修改**（`path == ""` 或 `readonly`，且 `!modified`） | `PROJECTS[ind] = 新工程` + `PANEL_GRAPH.setProject()` → **复用同一个面板**，标签数不变 |
| 其余（正常已打开的工程） | `new Panel_Graph(...)` + `array_push(PROJECTS, ...)` → **新增标签** |

对启动器有两条直接用处：

- 双击「已经在 PXC 里打开的工程」→ 不会重复开标签，而是重载（未保存的修改会触发 PXC 自己的保存询问）。
  所以启动器**不需要**再自己做"这个工程是否已打开"的去重判断，交给 `LOAD_PATH` 就行。
- 若 PXC 刚启动、还停在空白页 → 打开工程会**占用那个空白页**，标签数不变。这与 §7.3.2 的截图一致。

**③ 拖放为什么必须落在节点图区 —— 有明确代码**

`panel_graph.gml:4336–4341`（在 `Panel_Graph` 自己的绘制流程里）：

```gml
if(FILE_DROPPED && !array_empty(FILE_DROPPING)) {
    if(_node_hover && _node_hover.dropPath != noone)
        _node_hover.dropPath(FILE_DROPPING);                    // 落在节点上 → 交给节点
    else
        run_in(1, load_file_path, [FILE_DROPPING, _gx, _gy]);   // 落在空白 → 打开工程
}
```

这段前面有 `_mx = mouse_mxs - x` 的面板坐标换算，**只有落点落在该面板矩形内才会执行**。
而 `scripts/mouse_input/mouse_input.gml:74–75` 是配套：

```gml
#macro mouse_mxs (FILE_IS_DROPPING? FILE_DROPPING_X : mouse_mx)
#macro mouse_mys (FILE_IS_DROPPING? FILE_DROPPING_Y : mouse_my)
```

拖拽期间整个 UI 的"鼠标位置"被虚拟成**落点坐标**，面板的 `pHOVER` 才会为真。
→ 落点必须在 Graph 内**不是运气，是命中系统的机制决定的**。

**④ `WM_DROPFILES` 为什么必然无效 —— 源码证据**

`extensions/file_dropper/file_dropper.cpp`：

```cpp
struct GMDropTarget : IDropTarget { ... };              // :481  只实现 OLE 回调

dllg bool file_dropper_init(GAME_HWND hwnd) {
    OleInitialize(0);                                   // :613
    dropTarget = new GMDropTarget();                    // :619
    hr = RegisterDragDrop(hwnd, dropTarget);            // :620  只注册 OLE 拖放目标
}
```

全文**没有 `DragAcceptFiles`**，也没有任何 `WM_DROPFILES` 分支。投这条消息必然是"有人收、没人处理"，
与实测（返回 1、err 0、无反应）完全吻合。**这条定案，实现里不必再留任何尝试。**

**⑤ 官方没有"单实例转发"**

`objects/o_main/Create_0.gml:39–68` 就是全部命令行解析：

| 参数 | 含义 |
| --- | --- |
| `-h` / `--headless` | 无界面（`draw_enable_drawevent(false)`） |
| `-p` / `--persist` | 常驻 |
| `-t` / `--trusted` | 可信模式 |
| `-s` / `--server` | `useTCP = true`（见 ⑥，已废弃） |
| `-l` / `--lua` | Lua 模式 |
| `-nd` / `--nodir` | 不改工作目录 |
| 其它裸参数 | 只有"像工程文件"的才收：`:63` `if(path_is_project(path)) PROGRAM_ARGUMENTS._path = path;` |

`:63` 是**循环内覆盖式赋值** → `exe A.pxc B.pxc` 最终只留下 B，与实测"多参数只开最后一个"一致。
全仓库**没有任何"检测已有实例并把路径转过去"的代码** —— 官方确实不做单实例，这是设计如此，不是缺配置。

> 参数写法的坑：`-xxx` 只是把 `paramType` 切过去（`:55` `default : paramType = string_trim(param, ["-"]);`），
> 真正的值在**下一个**参数里。所以端口要写 `-s -port 22499`；写 `-s port=22499` 会被当成路径去判
> `path_is_project`，静默丢掉。

**⑥ `-s` 服务端是死代码（源码 + 实测双证）**

`Create_0.gml:91–96` 确实建了 TCP 服务：

```gml
if(useTCP && struct_has(PROGRAM_ARGUMENTS, "port")) {
    TCP_PORT   = PROGRAM_ARGUMENTS.port;
    TCP_SERVER = network_create_server_raw(network_socket_tcp, TCP_PORT, 32);
}
```

但**同一个 `Create` 事件**在后面 `:296–300` 又写了一遍：

```gml
#region server
    globalvar TCP_SERVER, TCP_PORT, TCP_CLIENTS;
    TCP_SERVER  = false;        // ← 把上面刚拿到的 server id 覆盖掉
    TCP_PORT    = noone;
    TCP_CLIENTS = [];
```

`Create` 从上往下执行，所以 server 的 id 刚建好就被 `false` 顶掉；`objects/o_main/Other_68.gml:10`
的 `if(_id == TCP_SERVER)` 永远不成立 → 即便有连接也没人处理。

**实测**：`PixelComposer.exe -s -port 22499` 启动（本次，2026-10-31 14:2x），
主窗 10.8 s 可见，`netstat -ano -p TCP` 查 `:22499` **无任何监听**。
→ 这条路彻底放弃，实现里不要留。

**⑦ 唯一的官方远程命令通道：`Remote Terminal` addon（不采用）**

`scripts/__initAddon/__initAddon.gml:72` 注册的内置 addon，官方描述：

> *"Open webSocket port for receiving and executing terminal commands."*

实现 `objects/addon_remote_terminal/Create_0.gml`：默认 `port = 22400`、`type = 2`（websocket），
收到数据按行交给 `cmd_submit()`。而 `cmd_submit`（`scripts/console_commands/console_commands.gml:31`）
的**内建命令只有** `flag` / `set` / `render` / `exit` / `print` / `netlog` / `patreon` —— **没有"打开工程"**。

菜单注册表里确实存在按路径打开的项（`scripts/panel_menu/panel_menu.gml:43`）：

```gml
registerFunction("", "Open At", "", n, LOAD_AT).setMenu("open_at", ...)
    .setArg([ ARG("path",""), ARG("readonly", false), ARG("override", false) ])
```

但它**调不通**，这一点读代码就能定死：`callFunction`（`scripts/function_register/function_register.gml:160–167`）
取的是 `_f.fn`，而注册时写进 `CMD_FUNCTIONS` 的键是 `action`（`:67` `{ action: _action, args: [] }`），名字对不上 ——
`call(undefined, args)` 走不到 `LOAD_AT`。`LOAD_AT` 的第二个参数要 `__loadParams` 实例、注册的却是裸 `false`，是第二处对不上。

**实测（2026-10-31 14:26–14:35，PXC 1.18.5）**：按官方方式启用 ——
写 `<用户目录>/Addons/__init.json = ["Remote Terminal"]` → 冷启动 PXC → 主窗 **18.5 s** 可见 →
此后 **150 秒内每 1.2 s 探一次 `127.0.0.1:22400`，始终没有监听**（`netstat` 同结论）。进程正常存活，
PXC 日志里 `init Addons | complete in 524` 也在，说明 `__initAddon()` 跑完了；但 addon 的 `refreshServer()`
没把端口建起来 —— `network_create_server_raw(network_socket_ws, 22400, 16)` 是在初始化阶段调用的，
而 `activate()` 开头 `if(active) return` 意味着**这次失败之后不会重试**。测试完已删 `__init.json`、复原 `recent.json`。

所以它在三个层次上都不成立：

1. **端口起不来**（实测），而且没有重试入口 —— 用户还得自己去 Addons 面板关一次再开。
2. **即使起来，`open_at` 也执行不到**（`_f.fn` / `action` 键名不符，源码定死）。
3. 它是**无认证的本机 websocket**，任何本机程序（包括浏览器页面）都能发 `exit` 把用户的 PXC 关掉。
   启动器没有理由劝用户开这个口子，更没有理由去改用户的 `Addons/__init.json`。

> 结论：**不采用**。复用进程仍按 §7.3.3 —— 无实例走命令行，有实例走 `Ctrl+O`。

**⑧ 对 §7 方案的净影响**

| 原结论 | 源码核对后 |
| --- | --- |
| `WM_DROPFILES` 无效 | **确认并知道原因**（只注册 `IDropTarget`）→ 定案，不再试 |
| 落点必须 Graph | **确认**（`Panel_Graph` 自己消费，靠 `mouse_mxs` 虚拟坐标命中）→ 定案 |
| 没有单实例转发 | **确认**（命令行无转发、多参数只留最后一个）→ 这是官方设计 |
| `Ctrl+O` 是最佳外部入口 | **加强**：`LOAD()` 是唯一的"按路径打开"菜单项，不依赖布局、不动鼠标 |
| `-s` 可作静默通道 | **否决**：死代码，实测端口都没起来 |
| `Remote Terminal` 可当远程命令通道 | **否决**：按官方方式启用后 22400 不监听（150 s 实测），且 `open_at` 的键名对不上、跑不到 `LOAD_AT` |
| 「同工程重复打开」要自己去重 | **不必**：`LOAD_PATH` 已先 `closeProject` 同名工程 |
| 一次开多个 | **只有拖放能做到**（`load_file_path` 收数组）；`Ctrl+O` 一次只能选一个 |

**结论**：§7.3.3 的「无实例 → 命令行；有实例 → `Ctrl+O`；对话框等不到 → 拖放；再不行 → 新进程」
这条链在源码层面是**最优解**，不需要改。源码只帮我们把若干"实测现象"变成了"机制定案"，
并额外确认了「同名重载」与「拖放可批量」两点行为。

### 7.4 跨版本协商

**触发**：`findMatching()` 为空；或检测置信度为 `LOW/NONE`（版本串是空的或猜出来的）。

#### 7.4.1 「结构类型相同」的可计算定义

文件侧 = **容器格式 × 版本整数代**：

| 结构族 | 判据 | 对应产品版本 |
| --- | --- | --- |
| `A@11.6` | 纯 JSON，`version` 整数 ≤ 11700 | 1.16.1.0 / 1.17 |
| `A@11.71` | 纯 JSON，整数 ≈ 117100 | 1.18.5 |
| `B@11.80` | zlib 容器（头 `78 9C / DA`），整数 118xxx | 1.19.x |
| `C` | PXCX 容器，`META` 里直接是版本字符串 | ≥ 1.20 |

exe 侧 = "这个已登记版本能读哪些结构族"，两个来源：

1. **内置校准表** `data/calibration.json`（随程序分发，维护者可改）：
   `1.16.1.0→A@11.6`、`1.17→A@11.6`、`1.18.5→A@11.71`、`1.19.0.11→B@11.80`、`1.20+→C`
2. **经验画像**（运行时学到的）：每次**启动成功**后，把该文件的结构族记进该 exe 的 `families`；
   判据是 R0 之后 `Recents[0]` 确实变成该文件（§7.3.1）；`CreateProcess` 失败、或 30 s 内没变，则不计入。

> **为什么还要经验画像**：校准表只有本机实测过的 5 个锚点，用户装的可能是任意小版本（`1.20.0.10`、`1.21.rc2`）。
> 按"整数段"代推能覆盖大多数，但官方换容器是真实发生过的（1.19→1.20 就从 zlib 换成了 PXCX），代推必然会有一次踩空。
> 经验画像让"用过而且打开了的就是对的"，且维护成本为零。
>
> 代价：画像依赖 `recent.json` 判据 —— 用户若在同一个 PXC 里紧接着又拖入别的工程，`Recents[0]` 会被覆盖。
> 所以只在启动后 3–5 s 读一次并落盘，之后不再采信；这一次学不到就等下次。

#### 7.4.2 版本距离

```
seg("1.22.0.5")  → [1,22,0,5]
seg("1.21.rc2")  → [1,21,0,0]  (pre = rc2)
dist = 10000*|Δmajor| + 100*|Δminor| + 10*|Δpatch| + |Δbuild|
```

`rc / alpha / beta` 只在**同 major.minor** 时作为次序（正式版优于预发布），不参与"安不安全"的判断。
距离只用于排序，不用于决定风险等级 —— 风险等级由「结构族是否相同 + 是否跨 major」决定。

#### 7.4.3 推荐规则

排序键：`(结构族不同? 0/1, 距离, -成功次数, 版本号降序)`，取第一个为推荐。

**推荐理由必须让人看懂为什么推它**：

| 情形 | 理由文案 |
| --- | --- |
| 同族 + 同 major.minor | `同为 1.19 代结构，只差一个小版本 —— 风险最低` |
| 同族 + 跨 minor | `结构相同（都是 zlib 容器），但跨了一个小版本` |
| 无同族，距离最近 | `本机没有同结构的版本；这是版本号最接近的一个（差 0.02）` |
| 无任何候选 | 不给推荐，只留「去版本库登记」按钮 |

### 7.7 性能：3486 条的现实

实测（2026-10-31 本机，抽样 120 个文件 + 单点测量）：

| 量 | 实测值 |
| --- | --- |
| `Autosave` 规模 | **3486 个 `.pxc` / 191 MB**（中位 14 KB，均值 47 KB，最大 474 KB） |
| 全量 `stat` 一轮（只取 name/size/mtime） | **113 ms** |
| 单文件识别（读 + deflate + 扫 `"version"`） | **均值 9.5 ms**；1000 KB 的文件：读 0.5 ms + inflate 6.2 ms |
| 推算全量识别（3486 × 9.5 ms） | **≈ 33 秒** |
| **PXC 冷启动 → 主窗可见**（不属本节，但同样影响观感） | **≈ 18.5 s**（1.18.5；已有实例时第二次启动 43 s）—— 见 §7.3.1 |

也就是说：**列表能秒出，版本列不能**。所以：

| # | 做法 | 理由 |
| --- | --- | --- |
| 1 | **扫描与识别分离**：目录扫描只取 `name / size / mtime`（113 ms，一次），版本列初始留空 | 列表必须先出来，否则用户以为卡死 |
| 2 | **懒识别**：只识别"可见且无缓存"的行，限流按**时间预算**：每帧最多花 **12 ms**（至少推进 1 个） | 文件大小差 30 倍（12 KB ↔ 474 KB），按"个数"限流会让帧时间忽 5 ms 忽 40 ms；按时间限流帧时间稳定 |
| 3 | **落盘缓存** `data/.cache/detect_cache.json`，key = `path + size + mtime`，上限 5000 条 LRU | 第二次打开即有版本，不再解压 |
| 4 | 点「启动」时该行还没识别 → **当场同步识别一次** | 实测均值 9.5 ms、最大 ~40 ms，用户感知不到 |
| 5 | 其它四个页签条目少（26 / ≤500 / ≤2000 / 不限）→ 首次进入批量识别 | 沿用 `collectFrom` 的批量能力；超过 200 条自动转懒识别 |

> **为什么不开后台线程**：EUI 是单线程渲染模型，跨线程改 `Signal` 要加锁 + 帧同步，漏一处就是随机的界面撕裂。

> 还有一个"慢"不在启动器这边：双击 `.pxc` 到 PXC 画面出现要 **18 秒**。这段时间启动器能做的不多，
> 但**必须给反馈**（主窗状态行 / 托盘气泡「正在启动 PXC 1.18.5…」），否则用户以为没反应会连点两下，直接开出第二个进程。
> 为了省几帧引入并发不划算 —— 懒识别最坏情况也只是"版本列晚几帧填满"。
>
> **为什么按时间预算而不是按个数**：单个文件的识别成本差 30 倍（12 KB 的 0.09 ms 到 474 KB 的几十 ms），
> 固定"每帧 4 个"在遇到大文件时会突然出现 40 ms 的帧，滚轮一顿；按 12 ms/帧限流后，
> 一屏 10 行约 8 帧（≈130 ms）填满，视觉上仍是"立刻出现"，但帧时间不再跳变。

#### 7.13.3 只有真跑才会暴露的三个 bug

**① 静默启动会变成"隐藏僵尸"，并攥住单实例互斥体**

原实现是「`compose()` 末尾藏窗 → 等 `g_wbSilentResolved` 为真或 25 s 超时 → `PostQuitMessage(0)`」。两处致命：

- `g_wbSilentResolved` **全文件从未被置真**（只声明、只读），永远只能走 25 s 兜底；
- 窗口一藏，`glfwWaitEvents()` 就再没有事件可等，**`compose()` 不会被调用**，那个 25 s 兜底也永远评估不到。

实测后果：进程永不退出（隐藏着、占 3 MB），而它握着 `Local\PXCLauncher.Instance` ——
之后**每次双击 `.pxc` 都被转发给这个僵尸进程，它却再也不打开任何东西**，等于关联功能整体失效。
这条不真跑就发现不了：headless 测不到，静态读代码也只看到"有个 25 s 兜底"。

修法三处：

- 静默时复用改**同步**（`pxc_reuse::openInExisting`）：窗口已经藏了，没有界面要保持响应，阻塞 5–11 s 用户看不见；
- 退出条件改成「`g_wbInbox` 已空 + 不在复用 + 没有协商窗」→ **同一帧**就退，不再依赖后续帧；
- 退出前同步 `wbSaveStoreNow()`：`wbTick` 的 500 ms 节流保存原本靠后续帧，立刻退出就没人写盘，`history` 会丢。

**② "白闪一帧"其实是 273 ms**

藏窗放 `compose()` 末尾时，从建窗到藏起来隔了整整一帧（含首帧布局 + 首帧绘制）：
实测可见 **273 ms**（20 ms 采样命中 10 次）。挪到 `compose()` **第一句**后降到 **≤20 ms**（命中 1 次）。

> 教训：§7.3 当初把这件事写成"可能白闪一帧"，是**没量过**的估计。帧内时序这种问题要么量，要么别当成结论写进文档。

**③ 第二次点图标"没反应"**

`acquire()` 失败后只调了 `notifyExisting(argvPaths)`，而它在 `paths.empty()` 时直接 `return false` ——
没有文件要转发时（用户只是又点了一次图标），第二实例静默退出、**已有窗口原样留在后面**。
用户看到的就是"双击图标没反应"，然后反复点。实测：第二个实例 0.71 s 退出、`exit=0`，前台还是别的程序；
修好后同一实验里前台切到了已有窗口。

修法：`notifyExisting` 失败时调新增的 `pxc_single::activateExisting()`（`IsIconic` → `SW_RESTORE`；
`SetForegroundWindow` 受前台锁限制，先 `AttachThreadInput` 到当前前台线程再调，失败再 `SW_SHOW` 重试一次）。
顺带把"找已有窗口"加了 **2 秒重试** —— 已有实例正在启动的那一秒窗口确实还不存在，原来会直接把路径丢掉。
