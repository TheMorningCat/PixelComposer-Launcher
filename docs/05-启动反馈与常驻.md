## 9.1 四条机制约束（它们决定了架构，不是实现细节）

这四条都是**代码里能指到行**的事实，任何方案都必须先满足它们，否则功能写着能跑、真机上必然失效。

**① 主窗最小化后，`compose()` 根本不会被调用。**

`EUI-NEO-main/core/app/glfw_app_main.cpp:319-327`：`updateManagedWindow()` 一开头就判 `GLFW_ICONIFIED`，为真时
只做 `releaseRenderCache() + requestFullPaint() + resetTiming()` 然后 **`return true`** —— 后面那段
`managed.content.update(...)` 被跳过，`compose()` 一次都不跑。

> 这不是理论风险。2026-10-31 已经踩过一次同类事故（§7.13.3 ①）：窗口 `SW_HIDE` 之后 `glfwWaitEvents()` 再没事件、
> `compose()` 不再被调用，那个"25 秒兜底退出"永远评估不到，进程变成**隐藏僵尸并攥着单实例互斥体**。
> 换成"最小化"只是把"没有事件"变成"有事件但没有帧"，**帧依赖的逻辑一样会死**。

**结论：启动状态机不能长在帧上。** 阶段推进必须是"线程 + 自己的驱动源"。

**② 真正的等待都是阻塞轮询，而且现在根本没"等窗口"这一步。**

- `pxc_reuse::openInExisting()` 同步执行 3–11 s（内部 `sleepMs(50~120)` 轮询对话框/校验）；
- `pxc_launch::launchExe()`（`launcher/launcher.cpp:12-40`）只 `CreateProcessW` 就返回，**连 PID 都丢掉了**
  （`CloseHandle(pi.hProcess)` 后直接 `return true`）——所以"等到 PXC 窗口出现"这个能力目前**不存在**，
  得先把它做出来（见 §9.8.2 的 `launcher/launcher.{h,cpp}` 一行）。

**③ 第二实例的转发是 3 秒同步消息，主线程忙 3 秒就丢单。**

`launcher/single_instance.cpp:128` 用 `SendMessageTimeoutW(..., SMTO_ABORTIFHUNG, 3000, ...)`。
常驻之后这条会变成常态路径：用户在 PXC 冷启动的 18 秒里又双击了一个 `.pxc`，如果那时主线程正阻塞在启动流程里，
转发会超时失败、退回 `activateExisting()`（只把窗口提上来，**不会再打开那个文件**）——用户看到的就是"双击了但没反应"。

**结论：「接单」必须与「干活」分离**：窗口过程里只入队 + 起线程，立即返回（<50 ms）。

**④ 右下角提示窗绝对不能抢焦点。**

复用链路唯一依赖"PXC 在前台"的一步是 `Ctrl+O`（§7.3.1 硬事实 4，`pxc_reuse.cpp` 里 `bringToFront()` 失败就**不发键**）。
如果提示窗弹出来把自己激活了，`GetForegroundWindow()` 变成提示窗 → 复用当场判 `ForegroundFailed` → 退化成新进程。
所以提示窗必须 `WS_EX_NOACTIVATE`，全程不 `SetFocus`（§9.6）。

## 9.2 目标流程

### 9.2.1 双击 `.pxc`（首启：本机没有同版本实例）

```
shell  "<launcher.exe>" "a.pxc"
  └─ 第二实例？── 是 ──▶ WM_COPYDATA 转发（<50 ms）→ 本进程退出
        │否
        ▼
  建窗 → 首帧第一句：SW_SHOWMINNOACTIVE（不激活、最小化，任务栏留下按钮）
        ▼
  后台线程：识别版本 → 定 exe ─────────────────────┐  提示窗：「PXC 启动中」
        ▼                                          │
  CreateProcess(exe, a.pxc) → 拿到 pid ────────────┤  提示窗：「PXC 已拉起，正在等窗口」
        ▼                                          │
  轮询 pid 的主窗出现（≈18.5 s，250 ms 一次）──────┤  提示窗：「启动中（已 12 秒）」
        ▼                                          │
  主窗出现 ───────────────────────────────────────▶┘  提示窗：「已启动 a.pxc」→ 3 秒后关闭
        ▼
  主线程落库（history）+ 同步写盘；启动器保持最小化驻留
```

### 9.2.2 复用已有实例（本机已有同版本 PXC 在跑）

```
后台线程：找同版本实例（按 exe 路径归一）
   ├─ 没有 ─────────────────────────────▶ 回落 9.2.1（提示窗显式说明「改为新开一个 PXC」）
   ▼
 找主窗（还原矩形判据）→ 若最小化则 SW_RESTORE 并轮询到 !IsIconic   「正在把 PXC 调到前台」
   ▼
 抢前台（AttachThreadInput + 4 次重试）                            「正在切换前台窗口」
   ▼
 SendInput：Ctrl↓ / O↓ / O↑ / Ctrl↑（每步 120 ms，必须分帧）       「正在发送打开快捷键」
   ▼
 轮询 ≤5 s 找 #32770（有可见 Edit + 按钮含「打开」）               「正在等待文件对话框」
   ▼
 WM_SETTEXT 填路径 + BM_CLICK 点「打开」                          「正在确认打开」
   ▼
 轮询 ≤6 s 等该对话框消失                                          「正在确认打开结果」
   ▼
 成功 → 「已在 PXC 里打开 a.pxc（新增标签）」→ 3 秒后关闭
```

> 两个流程的**成功判据不同**，必须写清楚，否则提示窗会撒谎：
> · 首启：**只能**以"PXC 主窗出现"为准。工程是否真的加载完，启动器观测不到（`recent.json` 只在 PXC 正常退出时写，
>   见 §7.3.3 修正 ②）——所以文案说「已启动」而不是「已打开」。
> · 复用：以"目标对话框消失"为准（现有判据，不变）。

## 9.4 取消语义

原则：**只有"还没把决定交给 PXC"的阶段能取消**。一旦 PXC 开始按这个路径加载，取消不是"撤销"，而是"杀掉一个正在写文件的进程"，不做。

| 阶段 | 取消按钮 | 点了之后 |
| --- | --- | --- |
| `Resolve` | **可用** | 立即停止，什么都没动 |
| `Copy` / `Backup` | **可用** | 立即停止；**本次刚建的副本删掉**（2026-11-04 改判，原为"保留"），备份保留 |
| `Spawn`（`CreateProcess` 已发出） | 置灰 | 文案「PXC 已开始启动，无法取消」 |
| `WaitWindow` | 置灰 | 同上（进程已在跑，杀掉可能留半截 autosave） |
| `ReuseFind` / `ReuseRestore` / `ReuseHotkey` | **可用** | 停止，不发键 |
| `ReuseDialog` / `ReuseFill` | **可用** | 先 `WM_CLOSE` 关掉我们弹出的对话框，再停止 |
| `ReuseVerify`（已点「打开」） | 置灰 | 文案「工程正在加载，无法取消」 |

> 置灰而不是隐藏：按钮位置固定，避免宽度跳变；置灰时鼠标悬停给一行说明，用户才知道为什么点不了。
> 用户原话里「首次启动在确认进程出现后无法取消」正好对应 `Spawn` 之后这一列。

**关闭主窗 = 退出启动器**；启动流程还在跑也不拦着（进程直接退，worker 随之结束）——
已拉起的 PXC 不受影响（不是我们的子进程语义，也不去杀它）。`pxc_runner::shutdown()` 目前
**没有调用点**，见 §9.14.4 的更正。

### 9.4.1 复用失败：停下来问，不自动开新进程（2026-11-01 拍板）

| 项的 | 结论 |
| --- | --- |
| 触发条件 | 有同版本实例，但复用没走通（抢不到前台 / 等不到对话框 / 点了打开没生效 / 发键失败） |
| 不触发 | `NoInstance`（本来就没实例）→ 直接首启，不打扰用户；`Busy`（实例在冷启动）→ 只提示"等它出来"，**既不复用也不新开**（新开会让两个 PXC 抢同一个 autosave） |
| 询问方式 | 就在右下角那个提示窗上问，不另起对话框（再弹一个窗会抢焦点，把复用刚抢到的前台顶掉） |
| 按钮 | 主按钮「开启新进程」、次按钮「取消」 |
| 不点怎么办 | 等 5 分钟；超时按取消处理（提示窗一并收起，不留一个永久浮层） |
| 原因怎么显示 | 只放**短原因**（"抢不到前台"）；带解释的长句只进日志 —— 长了会折行，把"吗？"顶到第二行 |

## 9.5 异常与超时

"远超预期"必须能量化，否则只能靠感觉。基于实测数据取阈值：

| 阶段 | 实测预期 | 预警（黄） | 判失败（红） | 判据来源 |
| --- | --- | --- | --- | --- |
| 识别 / 定 exe | 均值 9.5 ms | 1 s | 3 s | §7.7 单文件识别实测 |
| 建副本 / 备份 | <500 ms（样本 275 KB） | 3 s | 10 s | §7.13.2 |
| `CreateProcess` | <300 ms | 2 s | 5 s | 实测拉起进程 0.7 s 内 |
| **等主窗出现** | **18.2 / 18.3 / 18.4 / 18.5 / 18.7 s**（1.18.5）；第二次启动曾 43 s | **25 s** | **60 s** | §7.3.1 硬事实 1 |
| 复用整体 | **3.1 s**（1.20.1） | 8 s | 20 s | 2026-11-01 实测 |
| 复用等对话框 | 0.3 s | 3 s | 5 s（现有 `kDialogWaitMs`） | §7.3.3 |
| 复用等对话框消失 | <1 s | 3 s | 6 s（现有 `kVerifyWaitMs`） | §7.3.3 |

**超时不等于失败，这一点必须体现在文案里**：PXC 冷启动 43 秒是真实发生过的（§7.3.1），那时进程活着、窗口还没出，
报"启动失败"是错的。所以：

| 情形 | 判定 | 提示（副行） | 按钮 |
| --- | --- | --- | --- |
| 等主窗 >25 s | 预警（黄） | 比预期慢（已 25 秒），PXC 仍在启动 | 取消（置灰）/ 关闭 |
| 等主窗 >60 s | 失败（红） | 60 秒仍未出现窗口，可能卡住了 | 「打开日志」/「关闭」 |
| 进程已退出但窗口从没出现 | 失败（红） | PXC 启动后立即退出了（退出码 N） | 「打开日志」/「关闭」 |
| `CreateProcess` 失败 | 失败（红） | 无法启动 PXC（错误码 0x…） | 「打开日志」/「关闭」 |
| 复用等不到对话框 / 校验不过 | 停下来问（黄） | 复用没成功 <短原因>，要开新进程吗？ | 「开启新进程」/「取消」 |
| 抢不到前台 | 停下来问（黄） | 复用没成功 抢不到前台，要开新进程吗？ | 同上 |
| 阶段停滞（单阶段 > 上表"判失败"的 1.5 倍） | 失败（红） | 启动流程卡在「<阶段名>」 | 「打开日志」/「关闭」 |

> **2026-11-01 用户改判：不再自动退新进程，改为问一句**（见 §9.4.1）。
> 理由：多开一个 PXC 会抢同一个工程的 autosave，代价比"多点一次"大得多；
> 而"抢不到前台"往往意味着环境异常（管理员权限、UIPI），自动重来大概率还是失败。
> 唯一的例外是 `NoInstance`（本来就没有同版本实例）—— 那不是失败，直接走首启，不该问。

## 9.6 提示窗规格

### 9.6.1 形态

```
┌──────────────────────────────────────────────────┐  ← 400~560 × 104（无标题栏）
│  ◯   正在启动 飞弹爆炸.pxc                 [取消] │  ← 主行 16 / 图标 22；按钮 26 高
│      版本：1.20.1  PXC 启动中　已 12 秒          │  ← 次行 12.5
└──────────────────────────────────────────────────┘
```

| 项 | 值 |
| --- | --- |
| 尺寸 | **400~560 × 104**（宽度按两行文字 + 按钮实测算出，夹在上下限之间）；**高度与字号随「文字大小」放大**，见 §9.6.4 |
| 位置 | **主显示器工作区**右下角，右边距 / 下边距各 16 px（`SystemParametersInfo(SPI_GETWORKAREA)`，避开任务栏） |
| 层级 | `WS_POPUP` + `WS_EX_TOPMOST` + `WS_EX_NOACTIVATE` + `WS_EX_TOOLWINDOW`（不占 Alt+Tab、不显在任务栏） |
| 圆角/阴影 | `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)`；不支持时用区域裁剪，不做假阴影 |
| 底色 | 与工作台面板同族：`(45,47,55)`；不自创第三套配色 |
| 描边 | **2 px 主题色**（`pxc_toast::setAccent` 由 app 转交 `g_accent`，换主题色时在屏的提示窗立即重绘）。原来是 1 px 灰 `(65,70,82)`，在深色桌面上几乎看不见 —— 用户反馈"没注意到有弹窗"。GDI 画笔以路径为中心，2 px 必须把路径内缩 1 px，否则外半边被窗口边缘裁掉、看起来仍是 1 px |
| 进场 | 从屏幕右缘滑入，220 ms `easeOutCubic`（起点 = 工作区右边界，整块在屏外）。**只在「隐藏 → 显示」那一次做**：等窗口时每秒刷「已 N 秒」，每次刷新都重放会像抽搐 |
| 字体 | `data/fonts/NotoSansSC-Medium.ttf`（`AddFontResourceExW(..., FR_PRIVATE)` 私有挂载，不污染系统） |
| DPI | 按 `GetDpiForWindow` 缩放（96 → 100%，144 → 150%），不做逐显示器 v2 |
| 交互 | 只有按钮可点；其余区域**不响应点击，也不做点击穿透**（整个窗口是硬命中区）。不做穿透的原因见 §9.14.5 |
| 消失 | 成功 3 秒后**直接隐藏**（淡出还没做）；失败/预警保留到用户关闭；鼠标悬停时暂停倒计时 |

### 9.6.2 三条硬性限制

1. **绝不激活自己**（§9.1 ④）。`WS_EX_NOACTIVATE` + 不调 `SetFocus` + 不调 `SetForegroundWindow`。
   验证方法：弹窗出现后打印 `GetForegroundWindow()`，必须仍是原来的窗口。
2. **绝不挡住 PXC 的打开对话框**。对话框 960×540 居中（§7.3.3），右下角提示窗与之不重叠 —— 但要在 1024×768 这类小屏上复核一遍。
3. **绝不叠在自己头上**。多个工程连续双击时只允许一个提示窗，后来的覆盖前一个（队列里合并，见 §9.8）。

### 9.6.3 图标为什么改成 SVG 光栅化（2026-11-01 收尾）

**原来的做法**：GDI 的 `Ellipse` + `LineTo` 描边画"圆 + 符号"。两个毛病：

1. **不抗锯齿**。20 px 的圆圈在 125% / 150% 缩放下毛边明显，和窗口里其他抗锯齿文字差一个档次。
2. **状态区分不出来**。进行中是一个空心圈，成功也是同一个空心圈（只换了颜色），
   用户看到的是"这个圈到底在转还是转完了？"—— 他管这个叫"环形进度条看不出效果"。

**现在的做法**：SVG 字符串 → `nsvgParse` → `nsvgRasterize` 到 32bpp → `AlphaBlend` 贴到 GDI。
每个 tone 一份 `HBITMAP` 缓存，只有 DPI 变了（窗口被拖到另一块屏）才重建。

| 选型 | 结论 |
| --- | --- |
| 图标字体（工作台用的是 FA7） | **不行**。提示窗是原生 GDI，不在 EUI 的 text 渲染管线里；在 GDI 里要自己 `CreateFont` + `DrawText`，字形取整和 DPI 缩放都不如矢量 |
| GDI+ 路径 | 能用但没必要：要 `GdiplusStartup` + 额外链接，且路径 API 和 SVG 是两套描述，将来加图标要写两遍 |
| **nanosvg（选这个）** | 工程里已经有（`EUI-NEO-main/3rd`，EUI 根目录在 `eui::neo` 的 PUBLIC include 里），只 include **声明**即可 —— 实现体在 EUI 的 `image_source.cpp` 里已经编进库，自己再 `#define NANOSVG_IMPLEMENTATION` 会 LNK2005 重复符号 |

两个必踩的坑：

- **预乘 alpha**。`nsvgRasterize` 输出的是**非预乘** RGBA，而 `AlphaBlend(AC_SRC_ALPHA)` 要求源位图
  **已预乘**。不乘会在半透明边缘出现黑边（深色背景上特别明显）。实现里逐像素 `rgb *= a / 255` 顺手换 BGR 序。
- **行序**。`CreateDIBSection` 用**负 `biHeight`** 拿 top-down，和 nsvg 的输出行序一致，省一次翻转。

### 9.6.4 文字大小跟随「设置 → 界面 → 文字大小」（2026-11-02）

提示窗是**原生 GDI**，不在 EUI 的 text 渲染管线里 —— 设置页那个字号系数（`core::setGlobalTextScale`）
对它**完全无效**。所以倍率必须显式传进来，不能指望"全局缩放一把盖住"：

- **入口**：`pxc_toast::setTextScale(float)`，`std::atomic<float>` 存、限幅 0.7–2.0、任意线程可调。
  app 层不直接碰这个模块，走 `pxc_runner::setToastTextScale()` 一个口子 ——
  `initOnce()` 首帧传一次（冷启动就是配置里的值），`applyTextScale()` 每次松手再传（运行期改）。
- **生效时机**：提示窗**每次 `show()` 都重建字体**（DPI 也可能变过），所以改完字号下一次启动提示就是新字号，不用重启。
- **换算**：`textPx(dip) = round(MulDiv(dip, dpi, 96) × 倍率)`。主行高度、次行起点、按钮高度、窗口高度
  全部由它派生，不再有写死的行高。

| 量 | 100% | 150% | 推导 |
| --- | --- | --- | --- |
| 主行字号 | 16 | 24 | `textPx(16)` |
| 次行 / 按钮字号 | 13 | 20 | `textPx(13)` |
| 主行行高 | 24 | 36 | `textPx(24)`（原为定值） |
| 窗口高 | 104 | 138 | `16 + textPx(24) + 4 + textPx(44) + 16` |
| 窗口宽上限 | 560 | 840 | `560 × 倍率` |
| 窗口宽下限 | 400 | 400 | **不跟着放大**：它是"别缩成窄条"的兜底 |
| 图标 | 22 | 22 | **不跟着放大**：它是视觉标记不是文字，放到 33 反而头重过正文 |

**高度为什么必须现算**：原来 `kHeightDip = 104` 写死，150% 时两行字要占 138 px ——
写死就只有两种结果：次行被窗口底边裁掉，或两行叠在一起。实测 792×138，两行完整、按钮不压字；
短文案 421×138 也不裁。100% 时新算式的结果仍是 104（与旧版逐像素一致），这是回归判据。

## 9.7 常驻：任务栏还是通知栏

用户说"最小化收到任务栏或通知栏"，两条路差别不小：

| | A. 最小化到**任务栏**（推荐，默认） | B. 收进**通知栏**（托盘） |
| --- | --- | --- |
| 实现 | `ShowWindow(hwnd, SW_SHOWMINNOACTIVE)`，一行（不激活，避免抢焦点；实测建窗到首帧 ≤20 ms 的痕迹，见 §7.13.3 ②） | 需要 `EUI_ENABLE_TRAY=ON`（当前构建是 **OFF**）+ `dslAppConfig().tray(true)` + 一个 16×16 图标 |
| 恢复 | 点任务栏按钮，Windows 标准行为 | EUI 只暴露 `consumeTrayShowRequested()`（左键显示）/`consumeTrayExitRequested()`，**没有右键菜单**，要菜单得自己在原生层做 |
| 用户感知 | 底部多一个按钮，明确"启动器还开着" | 更干净，但容易被忘在托盘里 |
| 风险 | 无 | 构建开关 + 图标资源 + 托盘消息泵，都是新增面 |

**结论**：P0 用 A，配置文件留 `assoc.resident_mode`（取值 `taskbar` / `tray`），B 放 P2 再做（且 B 也要先开构建开关）。
**并且保留退路**：`assoc.stay_resident = false` 时回到现在的行为（拉起就退出）——万一常驻引入僵尸/内存问题，用户有开关可退。

> 为什么敢常驻：单实例互斥体由这个进程长期持有，后续每次双击都是"转发 + 退出"（0.7 s 级），
> 不再每次重新建窗、加载 518 个字体、读 17019 条对照表。代价是常驻内存（隐藏态实测 3 MB 是纯进程；
> 最小化态还会持有 GL 上下文与字体缓存，**具体数字待测**，见 §9.12）。

## 9.8 架构与线程模型

### 9.8.1 三个线程，边界写死

```
                 ┌──────────────────────────── 主线程（EUI / GLFW）──────────────────────────┐
 WM_COPYDATA ──▶ │ 窗口子类过程：只做「入队 + 唤醒」，不碰复用、不碰 PXC（< 50 ms）              │
 （第二实例）     │                                                                          │
                 │ compose()：窗口可见时才跑（最小化时框架直接跳过，见 §9.1 ①）               │
                 │ 收到 WM_APP_RESULT：落库（history）+ 同步写盘 + 状态行                      │
                 └──────────────────────────────────────────────────────────────────────────┘
                        │ 入队（mutex 保护的 path 队列）
                        ▼
                 ┌──────────────── 启动线程（worker，每单一个或长期一个）─────────────────────┐
                 │ 读队列 → 逐阶段执行 → 每阶段前：检查取消标志 / 报阶段给提示窗            │
                 │ 不碰 g_wbStore / 不碰任何 EUI 对象（结果只写进 Result 结构体）             │
                 └──────────────────────────────────────────────────────────────────────────┘
                        │ PostMessage(hudHwnd, WM_APP_STAGE, ...)  + 快照
                        ▼
                 ┌──────────────── 提示窗线程（自己 CreateWindowEx + 自己的消息泵）─────────┐
                 │ 收到阶段 → 重绘；按钮点击 → 置原子取消标志 → 回报                               │
                 └──────────────────────────────────────────────────────────────────────────┘
```

三条纪律：

1. **worker 不碰 UI 状态**。`g_wbStore` / `g_wb.status` / `g_wb.loaded[]` 全部由主线程在 `WM_APP_RESULT` 里改。
   理由：主窗随时可能被用户点回前台，那时 `compose()` 会读这些字段，跨线程写就是随机撕裂。
2. **提示窗线程只用 Win32 + GDI**，不引入 EUI。理由：EUI 是单线程渲染模型（§7.7 的"不开后台线程"原则），
   而提示窗必须独立于主窗状态存活——放在 EUI 里就得改框架（`DslWindowRequest` 没有 decorated/alwaysOnTop/x/y 参数，
   见 `EUI-NEO-main/core/app/glfw_app_main.cpp:246-252`，二次窗口一律带标题栏、不置顶）。
3. **取消是原子标志，不是消息**。worker 在每个阶段边界和 `pxc_reuse` 的轮询循环里检查，所以 `pxc_reuse` 要开一个
   `CancelToken` 参数（新增），不能只靠阶段边界（`ReuseDialog` 内部要轮询 5 秒，期间必须能中断）。

### 9.8.2 新增 / 改动文件

| 文件 | 性质 | 职责 |
| --- | --- | --- |
| `launcher/launch_stage.h` | 新增 | 阶段枚举 + 文案模板（纯函数：给"文件/版本/阶段/秒数"出两行字）。**headless 可测** |
| `launcher/launch_toast.{h,cpp}` | 新增 | Win32 无边框置顶窗 + 独立线程消息泵 + GDI 绘制 + 按钮命中 + 淡出 |
| `launcher/launch_runner.{h,cpp}` | 新增 | worker：队列、阶段推进、取消、超时/看门狗、把结果回投主线程 |
| `launcher/pxc_reuse.{h,cpp}` | 改动 | `openInExisting()` 增加 `CancelToken` + `StageSink`（阶段回调）；`mainWindowOf()` 提成公共工具 |
| `launcher/launcher.{h,cpp}` | 改动 | `launchExe()` 返回 **pid**（等窗口要靠它）；新增"等主窗出现"（250 ms 轮询，上限 60 s） |
| `launcher/native_ui.{h,cpp}` | 改动 | 主窗子类过程增加 `WM_APP_RESULT` 处理；新增 `minimizeToTaskbar()` |
| `launcher/app.cpp` | 改动 | 静默路径不再 `PostQuitMessage`；转发路径改为"入队 + 起 worker"（不走 `compose`）；`g_wbInbox` 语义改成"主线程待落库的结果" |

### 9.8.3 必须一起改的三处（漏一处功能就是假的）

1. **转发路径不能经过 `compose`**。现在 `WM_COPYDATA` 回调只往 `g_wbInbox` 里塞，真正的处理在
   `compose()` 里的 `wbTick`（`app.cpp:3685`）。主窗最小化后 `compose` 不跑 → **第二次双击永远没反应**。
   改成：窗口过程里直接交给 worker 队列。
2. **`wbSaveSoon()` 的 500 ms 节流靠后续帧**（`app.cpp` 里的节流保存）。最小化态没有帧 → 启动历史永远不落盘。
   改成：`WM_APP_RESULT` 里调用 `wbSaveStoreNow()`（同步写）。
3. **退出条件重写**。现在是 `g_wbInbox.empty() && !g_wbReuseBusy && !g_pick.open → PostQuitMessage(0)`
   （`app.cpp:5145`）。常驻后没有"退出"这一步，改成：只有用户关窗才退；关窗时若 worker 在跑 → 置取消 + 等 2 s。

### 9.12.1 追加验证：静默启动的窗口闪烁（这条是用户提的，原计划里没有）

**现象**：双击 `.pxc` 能看到启动器窗口闪一下。

**实测（`tmp/probe_flash.py`，8 ms 采样）**：

| 时刻 | 窗口状态 |
| --- | --- |
| t=309 ms | `GLFW30` 主窗创建完成，但 `WS_VISIBLE=0`（GLFW 建窗时并没 show） |
| t=983 ms | **`vis=1`**，1056×759 完整可见 ← GLFW 在**首帧**才 show |
| t=1043 ms | `vis=0` ← 我们的 `hideMainWindow()`（compose 第一句）执行 |

也就是说闪烁窗口约 **60 ms**，跨了整整两帧。原来代码注释里写的"建窗就可见、等一帧才藏"是**错的**：
GLFW 建窗时窗口是隐藏的，show 发生在首帧渲染时，而我们的 hide 比它晚两帧。

**结论：不在"藏得更快"上做文章，而是让窗口从一开始就不可见。**

改了 EUI 的 `WindowCreateRequest.visible`（默认 `true`，零行为变化），透传到 `glfwWindowHint(GLFW_VISIBLE, ...)`。
静默启动时 `dslAppConfig().visible(false)`，首帧再 `SW_SHOWMINNOACTIVE` 交给任务栏。
改后实测：主窗从创建到进程退出**全程 `vis=0`**，再没有 `vis=1` 的帧。

> 顺带踩到一个坑：`native_ui::findMainWindow()` 原来用 `IsWindowVisible` 筛窗口，窗口不可见就找不到自己的主窗 →
> `minimizeToTaskbar()` 静默失败。已改成"类名 `GLFW30` 优先、不看可见性"。

### 9.12.2 EUI 能不能生成无边框弹窗（用户问的）

| 层 | 能力 | 能不能用 |
| --- | --- | --- |
| `DslAppConfig`（主窗） | `decorated(false)` / `alwaysOnTop(true)` / `windowPosition` / `windowSize` **四个都有**，链路完整 | 能，但**用不上**：一个进程只有一个主窗，它是 1040×720 的工作台，且要最小化常驻任务栏，不能同时是 400×104 的角标 |
| `DslWindowConfig`（二次窗口） | 只有 `title/pageId/clearColor/windowSize/modal/onKeyEvent`，**没有任何装饰/位置/置顶参数** | 要加得改框架 4 处（字段 + 透传 + `DslWindowRequest` + `createManagedWindow` 赋值） |
| 关键缺口 | `WS_EX_NOACTIVATE` **不在 EUI 的能力面里**，改框架也拿不到，必须拿 HWND 自己 `SetWindowLongPtr(GWL_EXSTYLE)` | 一旦要写这段原生代码，EUI 省下的只有 GDI 绘制 |
| 更致命 | 主窗最小化时主循环 `continue`，**二次窗口跟着一起停**（`glfw_app_main.cpp` 的 iconified 分支在 `childWindows.updateAll()` 之前就跳过了） | 提示窗必须在最小化时也活着 —— 这一条直接判死 |
| 结论 | 无边框**能**做（仅主窗）；"右下角不抢焦点、最小化时也活着"的提示窗**做不了** | 提示窗走原生 Win32（`launch_toast.cpp`，约 450 行） |

## 9.13 本轮不做

| 不做 | 为什么 |
| --- | --- |
| PXC 内部真实进度（加载到第几个节点等） | PXC 不暴露，任何百分比都是编的。只用"已 N 秒"这种可观测的量 |
| 用 Windows 系统通知（WinRT toast / `Shell_NotifyIcon` 气泡） | 系统气泡不能常驻、不能带按钮，且样式不可控；与本册的"阶段滚动 + 取消"冲突 |
| 改 EUI 框架加二次窗口参数 | 二次窗口要"无边框 + 置顶 + 指定位置 + 不激活"，`DslWindowRequest` 一个都没有，改框架的维护成本高于写一个 300 行的原生窗 |
| 记住"上次用哪个版本"，跳过协商 | 与跨版本风险原则冲突（§7.4 的推荐规则要用户确认） |
| 启动失败自动重试 | 失败原因分不清（exe 权限 / 磁盘 / 版本），自动重试会把一次错误变成两次 |

## 9.14 连开多个工程（2026-11-04）

用户原话：能不能支持连续开启，「例如连续开启 2 个同一版本的项目时，更新窗口状态，等待 PXC 启动后，再进行第二个项目的启动流程」。

### 9.14.1 结论：队列本来就有，缺的是反馈和归属

| 层 | 之前 | 现在 |
| --- | --- | --- |
| 调度 | `launch_runner` 的 worker 早就 FIFO 排队，第二个任务不会插队 | 不变（这是对的：第一个任务"等到主窗出现"才结束，正好等于"PXC 起来了"，第二个才能走复用） |
| 提示窗 | 只显示**正在跑的那一个**；排队中的第二个点了像没反应 | 次行追加 `　·　还有 N 个在排队`（`State::queueLen`），提交瞬间就重画，不等阶段 tick |
| 结果回传 | 单格 `Result` + 单格 `g_wbPendingPath` | `Result` 改队列，且**路径随结果回来**（`Result::path`）—— 否则第二个会把第一个盖掉，历史记错文件 |
| 版本库卡片 | 直接 `ShellExecuteW`，**一个字都不提示** | 走同一条队列（`Job::pxcPath` 留空 = 空启动，跳过复用直接首启），右下角滚阶段，失败有原因 |

### 9.14.2 三条必须守住的细节

1. **排队数只并进"正在跑的那一个"的次行** —— 提示窗同一时刻只允许一个（§9.6.2 第 3 条），
   给排队任务单独弹一个会把进度盖掉，用户看到的是"进度没了，界面在说别的"。
   次行本来留了两行余量（`preferredHeightPx` 里的 `textPx(44)`），加这一截不用改布局。
2. **空启动必须 `allowReuse = false`** —— 没有工程可交给已有实例，走复用只会白等一轮窗口查找。
3. **每个任务开始时清掉提示窗上残留的按钮点击** —— 队列里任何点击都属于上一个任务
   （它的取消，或询问窗的答案），不清掉会被本轮第一个阶段当成"刚点的"。

### 9.14.3 取消：从"死按钮"到真的能停（2026-11-04）

原状：`cancelable()` 把 `ReuseXxx` 标成可点，但**没有任何地方轮询** `pxc_toast::takeAction()`，
`pxc_runner::cancel()` 全工程无人调用 —— 点了不会停，按钮只是个装饰。

现在：

| 环节 | 做法 |
| --- | --- |
| 谁读点击 | `pxc_runner::pollCancel()`：取一次 `takeAction()`，`Cancel` → 置 `s.cancel` 并返回 true。**只认 Cancel**，`NewProcess` 留给询问窗自己读 |
| 在哪读 | ① 复用链路每一步之间（`pxc_reuse` 的 cancel 谓词）② 建副本前 / 建副本后 / 拉起前（`startProject` 的三个检查点）③ **拉起前那一次是最后一道闸** |
| 拉起之后 | 不再读。`Spawn` 阶段按钮置灰，worker 也不再问 —— 双保险，避免"按钮点不动但流程还能被另一个入口停掉"的后门 |
| 副本 | 取消时 `startProject` 自己删掉本次刚建的副本（它建的它清，不交给调用方判断）；删失败（被占用）留日志并在提示里说明 |
| 阶段顺序 | `Spawn` 不再抢跑：`startProject` 按 真实顺序 报 `Copy → Backup → Launch`，报 `Launch` 才置灰，否则用户在"正在创建副本"时点不到取消 |

### 9.14.4 更正：关窗不会顿

上一版这里写"`shutdown()` 要 `join`，最坏 60 秒，关窗会顿"——**这是错的**，两个依据都反了：

1. `pxc_runner::shutdown()` **根本没有调用点**（全工程只有 `submit` / `takeResult` / `init` 被调）。
   关窗就是进程退出，worker 线程随之消失，不存在 `join`。
2. 即便调了，`waitMainWindow` 每 250 ms 检查一次取消、复用链路每 80–200 ms 一步、询问窗 120 ms 一循环，
   最坏也就是等当前那次 `copy`（同步、不可打断，通常 <500 ms）。60 秒是"等主窗超时"，不是"停下来的时间"。

真要做关窗收尾（比如想让提示窗淡出），再谈；在那之前别按"会顿"去做设计。

### 9.14.5 复用 Ctrl+O 偶尔没反应：重发一次（2026-11-04）

现象：连开两个工程时，第二个（同版本、走复用）有时打不开，提示窗停在"正在等待文件对话框"。

**根因未明。** 目前只确定一件事：第一次 Ctrl+O 没反应时，**再按一次就出来了**。先前给出的两个解释都已证伪，一并记在这里，避免下次顺着它们再推一遍：

| 曾经的判断 | 结论 |
| --- | --- |
| 右下角提示窗吃掉双击，导致第二个文件点不开 | 用户判定不需要这个能力，点击穿透已整段回滚（`launch_toast.cpp`）；§9.6.1「交互」随之改成"不做穿透"，不留永远不实现的规格 |
| PXC 启动页握着键盘焦点，Ctrl+O 打不到主窗 | **错**。用户实测：启动页不关也能触发 Ctrl+O。据此加的 ESC 步骤已删除 —— 那一步本身还有副作用：ESC 落在主窗上会取消一次画布选区 |

做法：先按正常路径等 2.5 秒（`kDialogFirstWaitMs`；正常 0.3 秒就弹，2.5 秒等不到本就不正常），没等到才重发一次**完整** Ctrl+O，再等 5 秒。

| 要点 | 说明 |
| --- | --- |
| 重发前确认前台 | `foregroundIs(pid)`：SendInput 发给当前前台窗口，前台被抢走时重发等于替用户打开别的程序的文件对话框 |
| 重发完整组合键 | 只补一个 `O` 不行 —— 主窗那边没有"Ctrl 按住"的状态 |
| 分帧慢发 | 每步 120 ms，理由见 `tapCtrlO` 注释（GameMaker 逐帧读键盘状态，一次发完等于没按） |
| 阶段 | `ReuseRetry`，文案「PXC 已启动，正在重试打开快捷键」，可取消（此时还没交给 PXC） |
| 日志 | `[Reuse] retry`（真重发了）/ `retry_skip`（前台不是 PXC）/ `retry_failed`（SendInput 失败）—— 命中率数这三行 |

**重试不是修复**。它只是把"第一次没反应"的代价从"这次开不起来"降到"多等 2.5 秒"。真正的原因还不知道，下次复现时先抓这几样再判断：第一次 Ctrl+O 时 PXC 是不是刚启动完（等主窗那 18 秒的尾巴）、主窗焦点在两次按键之间有没有变过、`[Reuse]` 行前后有没有别的对话框被关掉。

保留的一处（与本问题无关、独立成立）：`single_instance.cpp` 枚举"已有实例窗口"时跳过 `WS_EX_TOOLWINDOW`。提示窗同属本进程、可见、无 owner、还 topmost，不筛掉会让 `activateExisting()` 把提示窗提到前台，等于没激活主窗。

### 9.14.6 复用判据的四个漏洞 + 协商窗不入前台（2026-11-04）

第三方反馈：用文件关联启动工程时"在已开窗口里打开失败，再按一次变成多开 PXC"。本机复现不出来，
所以这一轮把**判据本身**的漏洞逐个堵掉，并补上"失败时必须说清为什么"。

#### 一、谁在跑 ≠ 偏好选的是哪份

同版本登记多份（Steam + 便携 / 手动登记）时，`choosePreferred` 只决定"用哪个 exe 启动"，
从不检查"哪个正在跑"。于是偏好指向 A、实际跑的是 B → 判成"没有实例" → 静默再开一个 B。

改法：`Job::altExes` 带上同版本其余已登记 exe（主线程取快照，worker 不读 `g_cfg`），
`openInExisting` 按"主 exe 优先、其余顺延"找进程，谁在跑就复用谁；`Outcome::usedExe` 回报实际复用的是哪一份。

#### 二、同一路径的字符串形式不止一种

`normPath` 原来只做 `absolute` + 转小写。可同一个 exe 可以写成 `D:/x/a.exe`、`D:\x\a.exe`、
8.3 短名 `D:\x\A.exe`→`AX8F2~1.EXE`、junction / 符号链接（Steam 库常见）—— 字符串互不相等就判成"没有实例"。

改法：统一分隔符 → `weakly_canonical`（解析短名 / 链接）→ 小写。**canonical 失败就退回 absolute**：
宁可少归一化，也不能因归一化失败把"有实例"判成"没实例"。

#### 三、读不到路径的进程不能当成"没有"

`OpenProcess` 失败（典型：PXC 以管理员运行，UIPI 拦了查询）时原来直接 `continue`，等于"没有实例"。
现在单独计数（进程名叫 `PixelComposer.exe` 但读不到路径），命中就返回新增的 `Result::Undetermined`，
由 worker 走**询问**分支 —— 判不准的时候绝不能自作主张多开一个。

#### 四、"直接开新进程"只留给一种情况

| 判据 | 收场 | 理由 |
| --- | --- | --- |
| `NoInstance`（同版本每一份都没有进程） | 直接首启，仍有阶段提示 | 这是首次启动，问"要开新进程吗"纯属添乱 |
| `Undetermined` / `ForegroundFailed` / `NoDialog` / `VerifyFailed` / `CallFailed` | **先告知原因，再问是否开新进程** | 有实例但没连上，多开会让两个进程抢同一份 autosave |
| `Busy`（进程在、主窗未出） | 报"等它窗口出来后再试" | 冷启动中开第二个更糟 |

关闭「复用已打开的 PXC」（设置项，默认开）属于用户显式选择：直接首启，但**照样有提示**（`Spawn` 阶段），不静默。

#### 五、诊断缺口补上

复用链跑完无论成败都写一行，这是下次排查的第一手证据（以前 `reuse_find` 之后直接 `spawn`，
"没有实例"和"有实例没连上"在日志里长得一样）：

```
[Reuse] reuse=<resultName> | <detail> | pid=<pid> | exe=<实际复用的 exe> | file=<工程>
```

同版本另有多份时，提交那一刻还会有一行 `[Launch] 同版本另有 N 份安装，一并作为复用候选`。

#### 六、缺版本协商窗必须入前台

从文件关联 / 命令行静默启动时，启动器是隐藏的。缺版本要用户选，`showMainWindow()` 只做
`ShowWindow(SW_SHOW)` + `SetForegroundWindow` —— 而后者在"调用者不是前台进程"时会被系统**静默拒绝**
（没有错误码，窗口就是不上来）。用户看到的是"双击了没反应"，实际是协商窗开在后台等一个永远没人做的选择。

改法（`native_ui.cpp::forceForeground`）：`SW_RESTORE`/`SW_SHOW` → `AttachThreadInput` 挂到当前前台
线程与目标线程的输入队列 → `BringWindowToTop` + `SetForegroundWindow` + `SetFocus`（最多连试 3 次）→ 摘钩子。
**仍抢不到就闪任务栏**（`FlashWindowEx`）并写一条 `[UI] 窗口抢不到前台，已改为闪烁任务栏` —— 前台是全屏程序
或 UAC 提示时只能这样提醒，但至少不再是"什么也没发生"。

#### 七、创建副本也复用（先建副本、再判断复用）

旧行为：「创建副本并启动」走的是一次全新的 `CreateProcess`。理由是"复用会让那个实例打开原文件" ——
**这个理由是错的**：复用链拿到哪个路径就打开哪个路径，先建副本就能打开副本。代价是用户明明开着
同版本的窗口，跨版本打开时却又多出一个 PXC 进程（2026-11-04 用户实测）。

新顺序（`runJob`）：

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | `Job::buildCopy` 建副本（`Step::Copy`，可取消） | 副本才是要交给 PXC 的文件；Ctrl+O 打不开还不存在的文件，所以必须排在复用之前 |
| 2 | 用**副本路径**走复用链 | 版本对得上（副本就是要给这个版本打开的），可以塞进用户正在用的那个实例 |
| 3 | 复用成功 → 保留副本 | 它已经被 PXC 打开，删了等于删掉用户正在编辑的文件 |
| 4 | 复用失败且用户选择不开新进程 / 目标实例还在冷启动 / 需要协商版本 → **删掉副本** | 用户从没用过它；留着只会在工程目录里越堆越多 |

删除走 `runJob` 的 `dropUnusedCopy()`，`startProject` 那边只在"自己建的"才删（`prebuiltCopy` 为空）——
**同一份文件不能有两处删除责任**，否则一边删掉、另一边再删一次会把"已删除"报成"删失败"。

### 9.14.7 复用失败给「重试」（2026-11-04）

复用失败最常见的原因是**目标 PXC 还没缓过来**（冷启动 ≈18 s，最长 43 s；或正在建工程、按键被卡顿吞掉），
一次失败并不能说明"复用不了"。旧询问窗只有「开启新进程 / 取消」，两条都不是用户想要的：
前者会多开一个 PXC 抢同一份 autosave，后者等于白点一次。

现在询问窗是**三个按钮**，从左到右：`取消` / `开启新进程` / `重试`。
重试放最右的主位 —— 它才是默认动作。按钮**单独占一行**而不是挤在文字右侧：
三个按钮合计 ≈205 px，和文字同行时「重试」会和「开启新进程」紧挨着，
点错一次就是凭空多一个 PXC 进程。

| 场景 | 按钮 | 理由 |
| --- | --- | --- |
| `Busy`（进程在、主窗还没出来） | 重试 / 取消 | 这种时刻开新进程正是要避免的事 |
| 其余有实例但没连上（`no_dialog` / `no_foreground` / `call_failed` / `failed` / `undetermined`） | 取消 / 开启新进程 / 重试 | 用户自己判断：等一等再试，还是干脆另开 |

点「重试」后**先等目标实例的主窗出来再重试**（`waitInstanceReady` → `Stage::ReuseWaitWindow`，上限 30 s）：
刚失败就立刻再发一次 Ctrl+O，多半还是失败，用户会以为按钮坏了。等到了再试，成功率高得多。
超时不拦路 —— 照样再试一次，让复用链自己给结论，失败就再弹询问窗，决定权仍在用户手里。

重试**不重建副本**（`copyBuilt` 已经为真）：副本已经在那儿了，重建只会多留一份孤儿文件。

失败注入钩子：`PXC_LAUNCHER_DEBUG_REUSE_FAIL=<n>` 让前 n 次复用尝试直接判失败
（`Result::NoDialog`，**不抢前台、不发按键、不碰 PXC 窗口**）。这是端到端验「重试」的唯一干净办法 ——
见下面这条教训。

#### 教训：测试不许改动被测之外的东西

第一版端到端测试是"把真实 PXC 窗口最小化 / 改尺寸，让主窗判据认不出来"来造失败。
代价是把 GameMaker 的窗口状态搞坏：`rcNormalPosition` 被撑成接近全屏、最大化后盖住任务栏、
**点击落点跟着偏移**（画布尺寸和客户区对不上），只能改回普通窗口尺寸才恢复。
造失败要造在启动器自己身上（注入钩子），不能靠折腾别人的窗口。

### 9.14.8 复用成功后连跳几个「导入工程」窗（2026-11-04）

用户复现「PXC 卡在建工程、Ctrl+O 被吞」后，这次**开成功了**，但随后连着跳出好几个导入工程窗口。

#### 根因：按键没有丢，是排队了

`SendInput` 把按键送进**前台线程的输入队列**。PXC 卡在建工程时主循环不消费队列，但键还在里面；
等它缓过来，队列被逐条处理 —— **按了几次就是几个对话框**。

一次启动里最多会按 4 次：第 1 次尝试（首发 + 2.5 秒没等到就重发）2 次，用户点「重试」后再 2 次。
所以「复用成功之后又冒出来几个」不是玄学，是这几发的余数。

#### 三道闸

| 闸 | 做法 | 位置 |
| --- | --- | --- |
| ① 卡着不发键 | `SendMessageTimeoutW(hwnd, WM_NULL, …SMTO_ABORTIFHUNG, 400ms)` 两次回话才认为能收键；卡着就等（上限 20 s，`Stage::ReuseWaitIdle` 每秒报数） | 发键前 |
| ② 有对话框就用它 | 发键前先 `findOpenDialog(pid)`；屏幕上已经有「打开」窗就直接填它（日志 `adopt_dialog`），绝不再按 | 发键前 |
| ③ 收尾扫残留 | `g_pendingPress` 是**跨尝试**计数（发一发 +1，见到对话框 −1）。离开复用链时仍 > 0 → 1.2 秒内反复关掉多余的「打开」对话框 | 每条出口（RAII） |

闸③ 的判据必须和填表那套完全一致（`#32770` + 可见 `Edit` + 按钮含「打开」/Open）。
顺手关掉「是否保存」这类提问框等于替用户做了决定 —— 那种框一个都不能碰。

#### 抢前台必须紧挨着发键

顺序从「抢前台 → 等 150 ms → 发键」改成「**等它不卡 → 抢前台 → 150 ms → 发键**」。
原来那一版在加入闸① 之后出过事故：抢到前台后要等 0.8 秒探活，这段空档里前台被拿走
（包括我们自己的提示窗），两次 Ctrl+O 全部打空，日志只显示"没等到对话框"。
现在 `bringToFront` 的返回值就是唯一的"能不能发"判据，不再单独判 `foregroundIs`。

#### 新增日志与结果

- `pre_key | fg=… fgPid=… target=… iconic=… match=…` —— 发键前那一刻谁在前台。**这一行是这类问题唯一的复盘证据**。
- `idle_timeout`（卡着没发键）、`adopt_dialog`、`closed_stray_dialogs | 关掉 N 个`、`retry_skip`（卡着/抢不到前台，未重发）。
- `Result::NotResponding` → 询问窗原因「PXC 一直没响应（卡在建工程）」，仍是三按钮（取消 / 开启新进程 / 重试）。

#### 代价

卡住的 PXC 现在会让提示窗**等到 20 秒**（带秒数、可随时取消）才问用户，换来的是不弹多余对话框。
正常路径没有额外开销：只发一发、且立刻见到对话框时，`g_pendingPress` 归零，收尾不扫描。

`tmp/t_adopt_dialog.py`（① 正常复用不 adopt 不留残留 ② 预置一个对话框 → adopt → 复用成功、结束后 0 个残留）PASS；
`tmp/t_retry_e2e2.py`（注入失败 → 重试成功）PASS；连续 3 次复用 3/3；`pxc_project_test` 158 passed。

### 9.14.9 对话框开着时 PXC「动不了」（2026-11-04）

用户复现：Ctrl+O 的「导入工程」窗还开着，PXC 被叫到前台 —— 之后 PXC 完全动不了（对话框在后台），
那段时间跑了几次测试全部失败。

#### 根因：主窗被顶到对话框前面，两头都点不动

那个「打开」窗是**独立顶层窗：既没有 `parent` 也没有 `owner`**（2026-11-04 实测），
所以主窗**不会被禁用**——`IsWindowEnabled(主窗)` 始终是 True。真正发生的是：
GameMaker 在对话框打开期间**挂起主窗的消息处理**（窗口还画着最后一帧，但不再处理输入）。

于是「把主窗顶到前面」= 前面那个点不动、后面那个够不着，用户只看到 PXC 死在那儿。

代码里怎么产生：闸①（发键前查有没有「打开」窗）原来只在 `waitPumping` **之前**查一次。
等它不卡最长要 20 秒，**之前那几发按键恰好在这段时间里落地**，屏幕上就多了一个对话框；
接着照常 `bringToFront(主窗)`，冻住。

#### 改法

| # | 做法 | 位置 |
| --- | --- | --- |
| 1 | **三处复查**对话框：入口、等完不卡之后、抢到前台 150 ms 之后（发键前最后一眼）。查到就走 adopt | `openInExisting` |
| 2 | adopt 抢的是**对话框**（`raiseToFront`），不是主窗 | `raiseToFront` |
| 3 | `bringToFront` 加守卫：目标有可见 `#32770` 就**拒绝**提主窗（日志 `bring_blocked`）；按路径上再判一次，给 `Result::DialogOpen` | `bringToFront` / 发键前 |

判据教训：**不能用 `IsWindowEnabled`**。我先按"模态框会禁用父窗"写，结果测试里那个状态根本造不出来
（主窗一直 enabled），差点把一个错判据当成防御。**判据只能是"有没有对话框"**。

`hasVisibleDialog(pid)` 故意放宽到"任何可见 `#32770`"：它只回答"能不能碰主窗"，
所以"是否保存"这种提问框也必须算（那种框更不能碰）。真正的"能不能复用"仍由
`findOpenDialog`（`#32770` + 可见 `Edit` + 按钮含「打开」）判。

#### 自愈

已经冻住的状态（主窗在前面、对话框在后面）不需要用户手动收拾：复用链一进来就 `findOpenDialog`
认到它，adopt → `raiseToFront(对话框)` → 填表 → 点「打开」→ 对话框关闭、模态结束 → 主窗自己活过来。
测试里专门造了这个状态验过。

#### 测试脚本的坑：keybd_event 发不进去

`tap_ctrl_o()` 原来用 `keybd_event`，从后台进程发常常**一个键都进不了 PXC**，
表现为"预置对话框失败 → 该用例跳过"，被误读成产品问题。启动器用的是 `SendInput`，
测试也必须用 `SendInput`（`keybd_event` 走的是调用线程的输入状态，后台进程没有那个前提）。

3. 造出"主窗盖在对话框前面"：复用链 adopt → `reuse=ctrl_o`、0 残留、主窗恢复可用。
