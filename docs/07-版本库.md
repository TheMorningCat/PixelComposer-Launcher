## 11.1 两个渠道：决定整页形态的两条事实

| | itch 版 | Steam 版 |
| --- | --- | --- |
| 发放形态 | **压缩包**，用户自己解压到任意位置 | Steam 客户端装到 `<库>/steamapps/common/...` |
| 典型用法 | 一个人会有**多个**版本，各在各的目录里 | **只有一条路径** |
| 版本会不会自己变 | 不会，目录里的 exe 就那样躺着 | **会**：Steam 自动更新，或在 Steam 里切回旧版本（**同一路径原地替换**） |
| 能否自动发现 | **不能**（解压位置无法穷举，扫盘也不该做） | **能**（注册表 + `libraryfolders.vdf` + `appmanifest`，见 §11.2） |

于是：

- **itch 组**是用户自己攒的收藏，卡片可以有 N 张、版本号可以重复；
- **Steam 组**是"本机当前那一份"，**常态只有一张卡**（用户保留旧副本时允许不止一张，见 §11.10）；
  它的版本可能今天 1.20、明天 1.22 → 它需要「版本变化提示」，itch 不需要
  （这就是"Steam 变化可能需要提示"的真正理由）。

## 11.2 Steam 自动获取：先问「库在哪」，再问「游戏在不在」

**已核实的事实**：Pixel Composer 的 Steam App ID = **2299510**（`store.steampowered.com/app/2299510`）。

关键顺序：**不要**去 `steamapps\common` 下猜哪个目录像 PXC。游戏可以装在任意一个库里，
而库的位置是**能精确问出来的**：注册表给出 Steam 根，Steam 根里的 `libraryfolders.vdf` 列出所有库。

### 11.2.1 读取链

| 步 | 动作 | 失败退路 |
| --- | --- | --- |
| 1 | `HKCU\Software\Valve\Steam\SteamPath` → Steam 根（本机 `e:/steam`，注意**正斜杠**） | `SteamExe` 取父目录；再退 `HKLM\SOFTWARE\WOW6432Node\Valve\Steam\InstallPath` |
| 2 | 读 `<root>\steamapps\libraryfolders.vdf`，取**所有** `"path"` | 缺失或解析出 0 个库 → 读 `<root>\config\libraryfolders.vdf`；仍没有 → 只探 Steam 根这一个库 |
| 3 | 库列表规范化去重（大小写不敏感、去尾分隔符）；每个库 `L` 查 `L\steamapps\appmanifest_2299510.acf` 在不在 | 没有 acf（用户只拷了游戏目录）→ 仍试第 4 步的固定名兜底；两种都无 → 跳过这个库，**不扫 `common`** |
| 4 | 读 acf 的 `installdir`（本机 `"Pixel Composer"`）、`StateFlags`、`LastUpdated` → `<L>\steamapps\common\<installdir>\PixelComposer.exe` | 没有 acf（用户只拷了游戏目录）→ 退化为 `<L>\steamapps\common\Pixel Composer\PixelComposer.exe` 这**一个固定名**的探测 |
| 5 | 读 PE 版本（与 itch 同一套 `readExeVersion`），登记为 Steam 条目 | 读不到 → §11.8 的弹窗 |

**为什么不去解析 vdf 的 `apps` 段**：它确实会写 `"2299510" "373768382"`（本机就有），
但要把这个 appid 归属到某一个库，得先把 vdf 按 `0/1/2` 的嵌套括号切块 —— 那是个不完整的 VDF 解析器，
而**直接 `Test-Path` 一个 acf 的成本可以忽略**（3 个库 = 3 次 `is_regular_file`）。
判断依据只留一个（acf 文件），出错的可能就少一半；vdf 只承担它擅长的部分：给出库路径列表。

### 11.2.2 本机实测（三个库，PXC 只在其中一个）

| 项 | 实测值 |
| --- | --- |
| `SteamPath` | `e:/steam`（正斜杠；`SteamExe` = `e:/steam/steam.exe`） |
| `libraryfolders.vdf` 里的库 | `E:/steam`、`D:/SteamLibrary`、`G:/SteamLibrary` —— **3 个库、跨 3 个盘** |
| `"2299510"` 在 vdf 里出现次数 | **1**，只在 `G:/SteamLibrary` 那一段的 `apps` 里 |
| `appmanifest_2299510.acf` | 只有 `G:/SteamLibrary/steamapps/appmanifest_2299510.acf` 存在 |
| acf 关键字段 | `name = "Pixel Composer"`、`installdir = "Pixel Composer"`、`StateFlags = "4"`、`LastUpdated = 1792878517` |
| exe | `G:/SteamLibrary/steamapps/common/Pixel Composer\PixelComposer.exe`，`ProductVersion = 1.22.0.5`，192 MB |

> 这张表就是「必须支持多库」的证据：主库在 E 盘，PXC 装在 G 盘。
> 任何"只看 Steam 根下一个 `common`"的实现在这台机器上都会**报告没装 Steam 版**。
> 上一版本文档正是这么错的（只看了 `e:/steam/steamapps/common`，看到 PixelOver Demo 就下了结论），此处更正。

### 11.2.3 解析上的坑（全部实测）

| 坑 | 实测值 | 处理 |
| --- | --- | --- |
| `SteamPath` 是**正斜杠** | `e:/steam` | 先转 `std::filesystem::path` 再拼，别做字符串相加 |
| vdf 里是**转义反斜杠** | `"path"  "E://steam"` | 逐字符解析：`\\` → `\`，`\"` → `"`；不能用引号 split |
| 有两份 libraryfolders | `steamapps\libraryfolders.vdf` 与 `config\libraryfolders.vdf` | 先前者；缺失或解出 0 个库再看后者 |
| `installdir` 含空格 | `"Pixel Composer"` | 用 `path /` 拼，别 `snprintf` |
| 库可能在移动硬盘 | — | 探不到 = 这次没装，**不删**已登记条目（§11.10） |

### 11.2.4 代价（摆在明处）

| 得到 | 放弃 |
| --- | --- |
| Steam 版零配置出现；换盘、加库、库搬家都能跟上 | 依赖 Steam 的注册表与 vdf 格式；将来格式变了要跟改解析 |
| 能读到 `LastUpdated`，可解释"这次为什么变了" | 不处理 demo / 别的 appid；**不在 Steam 库里的副本一律当 itch** |
| 全程只读，不碰 Steam 目录 | Steam 开着时 acf 可能正被改写 → 读失败就沿用旧值，不报错 |

### 11.2.5 落地记录（2026-11-02）

`steam_locator.{h,cpp}` 已落地，解析（纯函数）与真机链都过了 —— `pxc_backend_test` 的 `[6]` 段：

```
[6]  parseLibraryPaths n=3  p0='E:\steam'  p2='G:\SteamLibrary'
[6b] parse=1  acf=1  underCommon=1
[6c] steamRoot='e:\steam'  libs=3   (E: 主库 / D: / G:)
[6d] hits=1
```

三条断言各自钉的是什么（都踩过或差点踩到）：

| 断言 | 做法 | 若写错会怎样 |
| --- | --- | --- |
| `parse` | 读**本机真实 vdf**，用 `fs::equivalent` 与 `steamRoot()` 比对 | 用字符串比会栽在盘符大小写（注册表 `e:/steam`、vdf `E:\steam`）；转义没解开则路径带双反斜杠，equivalent 也会失败 |

| `underCommon` | 正例 + 反例（`E:\other\...` 在 G 库之外） | 只测正例的话，前缀比较漏掉尾分隔符也能过 —— 会把 `G:\SteamLibrary2` 误判成在库里 |

### 11.2.6 便携版自动发现（2026-11-03）

**用途**：把启动器和 PXC 摆在一起打包时，不用手动登记 —— 启动器一刷新就自动把"身边的 PXC"收进版本库，且路径写成**相对**，打包后相对位置不变即有效。

**检测范围**：启动器目录 + 父级目录，各含一层子目录（即"两层 + 递归一层"，见 §11.2.6.1）。在这些目录里找 `PixelComposer.exe`（精确文件名，大小写无关）。落在登记表里没有的就登记。

**为什么归 itch 不另开渠道**：便携打包带走的本来就是 itch 版（本地解压/复制的）。发现的条目 `channel` 留空，刷新时 `detectChannel` 按"不在 Steam 库下"自然归为 `itch`，与用户手动拖入的 itch 同源 —— 渠道标签、跨渠道偏好逻辑全部复用，UI 零改动。

**相对路径（关键）**：

| 项 | 规则 |
| --- | --- |
| 落盘 | `store::save` 时，落在启动器目录（`baseDir`）或其父级下的 exe_path，转成**相对 baseDir** 写（`../` 表示在父级）；其它（Steam / itch 绝对安装）保持绝对 |
| 读盘 | `store::load` 时，非绝对（不以盘符开头）的 exe_path，用启动器目录解析回绝对 |
| 内存态 | 始终是绝对路径 —— 相对↔绝对的转换只收敛在 `store` 两层，所有消费逻辑（`scanInstalled` / 启动 / 刷新）零改动 |
| 基准 | 启动器 exe 所在目录（`g_exeDir`）；判定"可相对"的祖先范围 = `g_exeDir` 及其父级（与检测范围一致） |

**权衡**：

| 得到 | 放弃 |
| --- | --- |
| 启动器 + PXC 一起打包，换机器/换盘符仍有效（绝对路径会失效） | 若 PXC 被挪到启动器目录/父级之外，相对路径解析失效（但那时绝对路径也失效，无所谓） |
| 转换只在一处（`store` 两层），风险最低 | 落盘的 exe_path 不能直接肉眼看出"是不是便携版"——但非盘符开头本身就是标记，且 `channel` 字段已区分 |

#### 11.2.6.1 检测深度（为什么是"两层 + 递归一层"）

覆盖的打包布局：

| 布局 | 例子 | 是否覆盖 |
| --- | --- | --- |
| PXC 与启动器同级 | `工具箱/启动器.exe` + `工具箱/PixelComposer.exe` | ✅ 启动器目录自身 |
| PXC 在启动器上层 | `工具箱/launcher/启动器.exe` + `工具箱/PixelComposer.exe` | ✅ 父级目录 |
| PXC 在父级的版本子文件夹 | `工具箱/PixelComposer 1.20.1/PixelComposer.exe` + `工具箱/launcher/启动器.exe` | ✅ 父级 + 一层子目录 |
| PXC 在启动器目录内的子文件夹 | `工具箱/launcher/PixelComposer 1.20.1/PixelComposer.exe` | ✅ 启动器目录 + 一层子目录 |

不递归更深，避免扫到无关 exe（名字 `PixelComposer.exe` 虽特异，但 `data/`、`userdata/` 等子目录仍会进一层 —— 这些目录里不会有该 exe，误伤概率极低）。

#### 11.2.6.2 托管条目的右键「删除」（2026-11-03）

**规则（Steam 与便携共用一条判据）**：由自动发现托管的卡，**文件还在时不画「删除」**；**已丢失时保留「删除」**。

| 卡 | 文件在 | 文件丢了 |
| --- | --- | --- |
| itch（未被托管） | 有「删除」 | 有「删除」 |
| Steam | **无** | **有** |
| 便携范围内 | **无** | **有** |

**为什么文件在时不给**：这类卡由扫描维护，删掉后下一次刷新（启动就刷新）照样被找回来 —— 点了没反应的菜单项比没有更糟（§11.15.2 第 1 条的最初口径只写了 Steam，漏了丢失态）。

**为什么丢失时必须给**：两条扫描链都只收**磁盘上存在**的文件——Steam 重发现只登记命中的 exe，便携发现也只扫存在的文件——条目一旦丢失就都不会被加回（实测：移除便携 PXC 后刷新输出 `便携新增 0 / 丢失 1`）。此时"删了会回来"这个前提不成立，而「删除」是清掉这张卡的**唯一**手段。原实现按 `if (!steam)` 一刀切，卸载一个 Steam 版本就会**永久留一张删不掉的红色丢失卡**，这是本条要修掉的问题。

**判据（一处定义，两处复用）**：`pxc_reg::isPortablePath(exe, g_exeDir)` 与 `discoverPortable` 共用同一套目录集合（抽成 `portableDirs()`）。两处各写一份必然漂移，漂移的结果就是 UI 判成便携、扫描却不认（或反之），删除项该藏不藏。`isPortablePath` **只判"落在不在范围内"，不判文件是否存在** —— 存在性由调用方按场景决定（存在→藏、丢失→留）。

## 11.3 状态刷新：三处触发，一个动作

「刷新」= **让登记表追上磁盘事实**，不是重新扫全盘。

| 触发 | 位置 | 为什么必须在这里 |
| --- | --- | --- |
| 启动 | `initialize()` 末尾（读完配置后一次） | 上次退出后 Steam 可能更新过、库可能搬过 |
| 点刷新按钮 | 版本库页 `reg.refresh` | 刚装完新的 itch 版、或 Steam 刚落完更新，要能立刻看到 |
| 启动工程之前 | `wbLaunchPath()` 与 `openVersionPicker()` 之前 | 版本号是跨版本判定的**输入**，用它之前必须是新鲜的 |

一次刷新做五件事（便携发现 + 原四件），**顺序有讲究**：

0. **便携版重发现**（在 `refreshAll` 之前，§11.2.6）——扫描启动器目录 + 父级目录（各含一层子目录）下的 PixelComposer.exe，登记表里没有的就登记；
1. **Steam 重发现**（先做）——它可能新增条目或改掉 Steam 那一条的路径；
2. **存在性校验**——exe 不在了 → 条目标「丢失」（红字），**不删**（盘可能只是没插）；
3. **逐条重读 PE 版本**——与登记值不同就更新；**`source = "manual"` 的条目跳过这一步**（版本号是用户显式裁定的，§11.8.1）；Steam 条目的 `acked_version` **不动**（角标由"当前 vs 已确认"自然算出，§11.7）；
4. **重建版本索引**（原来 `refreshVersionList()` 的职责，保留）。

**不做**：不遍历非 Steam 目录、不算哈希、不进帧循环。三处触发都是用户动作，
每次成本 = 一次注册表读 + 几个文件读，量级在毫秒。

**实测（2026-11-04，本机 5 条登记 / 3 个 Steam 库）**：热态 **4~5 ms**，冷态（开机后首次、文件不在系统缓存）
**546 ms**，差距全在首次触盘。日志末尾现在带这个数（`… / 5ms`），判"能不能更频繁地调"就看它，别估。
另有一个"首次才有"的成本：版本探测（§11.8.2），换 PXC 版本或删缓存后的第一次刷新会叠加 0.2~0.6s，
之后走缓存为 0 —— 日志里的 `探测 N` 就是这个。

> 框架禁忌复述：`dslAppConfig()` 每帧被调 20+ 次，任何读盘都不能放进去。
> 刷新只挂在上面的三个**动作**上。

**调用点全表**（全部是用户动作，无一自动触发）：

| 类别 | 调用点 | 走哪条 | 为什么 |
| --- | --- | --- | --- |
| 启动 | `initialize()` 末尾 | **全量** | 上次退出后 Steam 可能更新/搬库 |
| 刷新按钮 | 版本库页 `reg.refresh` | **全量** | 用户主动要"现在磁盘上都有什么" |
| 缺版本协商 | `openVersionPicker()` | **全量** | 候选要全，包括还没登记的 |
| 启动工程前 | `wbLaunchPath()` | **单条**，没匹配上才全量 | 见 §11.3.1 |
| 添加 exe | `registerExe()` | **单条** | 新登记的只有这一条 |
| 手动登记 | `onConfirmManual()` | **单条** | 同上 |
| 重新读取版本 | `onRereadVersion()` | **单条** | 就是这一条的事 |
| 删除条目 | `onRemoveExe()` | **只收尾**（不刷任何条目） | 条目已经没了；**绝不能**跑 Steam 重发现 |
| 兜底 | `launchExeNow()` 发现 exe 不在 | **单条** | 只需标这一条丢失 |

### 11.3.1 单条刷新（`pxc_reg::refreshEntry`）

**为什么要有**：全量刷新顺带做 Steam 重发现与便携扫描，在"只关心一条"的场景里那两件事是**副作用**——
删掉一个 Steam 条目后立刻全量刷新，重发现会把它原样加回来（用户看到的就是"删不掉"）。
单条刷新只做全量的 ②存在性 / ③重读 / ④渠道，①②一概不碰。

| 项 | 规格 |
| --- | --- |
| 入口 | `pxc_reg::refreshEntry(cfg, exePath)`，返回 `EntryRefresh{found, changedPath, missing, channel_filled, reread, changed}` |
| 共用逻辑 | 全量与单条共用 `refreshOne()` 这一份实现，禁止各写一遍（两份必然漂移） |
| 收尾 | app 层 `commitRegistryEdit()`：重建版本索引 / 骨架失效 / 重算变化列表 / 重算偏好待问 / 按指纹落盘 / 落盘探测缓存 |
| 变化列表 | 由 `pxc_reg::pendingChanges(cfg)` 从**当前状态**推导（`steam && acked != product`），不再由刷新过程收集 |
| 「启动工程前」的策略 | 先只刷"版本号 == 目标版本"的条目；仍匹配不上才全量（磁盘上可能刚出现一个没登记的版本） |
| 删除条目 | 只调 `commitRegistryEdit()`；**不刷新**，否则重发现复活 |

## 11.5 卡片交互（已定）

| 操作 | 行为 |
| --- | --- |
| 单击 | **选中**：描边换 accent，同一时刻只有一张被选中 |
| 双击 | 用**这一张的 exe** 启动 PXC（空工程），走与工作台相同的启动链 |
| 右键 | `打开所在文件夹` / `设置版本号` / `重新读取版本` / **`设为默认启动 ▸`**（仅当该版本存在跨渠道同版本，§11.6.2）/ `删除` |
| 悬停 | 完整路径（tooltip）。参考图不显示路径，这是"两张卡片看起来一样"时唯一的区分手段 |
| 拖入 exe | 添加（现有能力，保留；提示文案里承诺过） |

为什么单击是选中、不是启动：启动是个会拉起另一个进程、还会触发"复用已有实例"逻辑的重动作，
误点一次的代价远大于多点一次。而选中是纯视觉的、可撤销的，适合放在最容易误触的单击上。

删除**不放在卡片上**：参考图没有删除按钮，四个操作里只有删除是破坏性的，收进右键能少误触。

**「删除」的出现条件**（一条判据管两类，§11.2.6.2）：
由**自动发现托管**的卡（Steam 卡 / 落在便携扫描范围内的卡），**只要文件还在**就不给「删除」——删了下次刷新照样回来；
一旦**丢失**就给——两边扫描都只收磁盘上存在的文件，不会把它加回来，此时删除是唯一的清理手段，
否则卸载一个 Steam 版本就会永久留一张删不掉的红色丢失卡。未被托管的 itch 卡始终有「删除」。

## 11.6 数据模型

```cpp
struct ExeEntry {
    std::string exe_path;
    std::string product_version;   // 磁盘上当前读到的版本
    std::string display_name;
    std::string source;            // "auto" | "manual" —— 保留，界面上不显示
    std::string registered_at;
    std::string channel;           // 新增："itch" | "steam" | ""（空 = 还没判定）
    std::string acked_version;     // 新增：用户已确认过的版本（Steam 变化角标用）
};

struct Registry {
    std::vector<ExeEntry> entries;
    std::map<std::string, std::string> prefer;   // 新增：四段版本号 -> "itch" | "steam"
};
```

| 项 | 决定 | 原因 |
| --- | --- | --- |
| `channel` 默认空 | 读盘时**不碰文件系统**，因此不在 `store::load` 里判 Steam 库 | 配置解析不该有 IO 副作用 |
| `channel` 何时填 | 刷新时按"路径是否落在某个已知 Steam 库的 `steamapps\common\` 下"回填 | 一条规则同时覆盖"自动发现"和"用户手动添加的 Steam exe" |
| `acked_version` | **用户已确认过的**版本，不是"上一次读到的版本" | 连续更新两次而用户没点角标时，`prev_version` 会被第二次覆盖成 1.21，用户就看不到"从 1.20 来的"；`acked` 只在点「知道了」/重新读取时推进 |
| `acked_version` 初值 | Steam 条目首次发现 = 当前版本（这不算"变化"） | 否则第一次出现就带角标 |
| 角标条件 | `channel == "steam" && !sameVersion(acked, product_version)` | 不需要额外布尔位，一个字段自洽 |
| `prefer` 键是**版本号**不是渠道 | 偏好只对"这一个版本同时有两条"有意义 | 渠道级偏好会在"itch 1.22 + Steam 1.20"时把 1.20 也拉去 itch，语义就歪了 |
| `version` | 4 → **5**（只多三个可缺省字段/段，无迁移代码） | 老配置读进来 `channel` 空、`prefer` 空，首次刷新补齐 |

**排序**：每组内按 `product_version` 降序，同版本按 `registered_at` 降序。不提供手动排序。

### 11.6.1 同版本的两条规则

先定"同版本"：`pxc_reg::sameVersion()` —— 四段补零后逐段比（`1.22` 与 `1.22.0.0` 是同一版）。

| 情况 | 触发点 | 处理 |
| --- | --- | --- |
| **A. 同渠道 + 同版本 + 不同路径** | 用户拖入 / 「添加 exe」/ Steam 自动发现撞上已登记的副本 | **弹窗二选一**：保留现有 / 用新的替换 |
| **B. 跨渠道 + 同版本**（itch 与 Steam 各一张） | 任一次刷新之后 | 两张**都留**，问启动偏好（§11.6.2） |

**A 为什么必须问**：两份同渠道同版本的 PXC 是同一份东西的两个拷贝，留着只会让"启动哪个"变成掷硬币。
（用户原话：这意味着他电脑上有 2 份完全一样的 PXC。）

| A 的细节 | 决定 |
| --- | --- |
| 文案 | 「本机已有同版本 **1.22.0.5** 的 itch 版：`<路径>`。两份相同的 PXC 没有意义，选择保留哪一个？」 |
| 按钮 | 「保留现有」/「用新的替换」 |
| 「用新的替换」 | 删旧**条目**、登记新的；**不动磁盘文件**（我们不负责删用户的 PXC） |
| Steam 自动发现也走 A | 库里同版本的另一份旧副本，同样是"两份一样的"；不能因为它是自动来的就静默覆盖 |

**B 为什么不合并**：渠道不同、用途不同 —— itch 版版本固定（适合锁在老版本开旧工程），
Steam 版会自己更新（适合日常）。合并成一张会让"这张到底是什么"变得不可知。

### 11.6.2 启动偏好（`prefer`）

| 项 | 决定 |
| --- | --- |
| 语义 | 「这个版本同时有 itch 与 Steam 时，启动工程默认用哪个渠道的 exe」 |
| 存哪 | `registry.prefer["1.22.0.5"] = "steam"`（四段规范化后的键）。**三种状态**：无键 = 没问过；空串 = 问过但他关掉了（走兜底，不再问）；`"itch"`/`"steam"` = 已表态 |
| 作用点 | 工作台启动工程、以及任何"按版本找 exe"的地方：`findMatching(version)` 命中多条时按偏好挑 |
| 没有偏好时兜底 | **Steam 优先**。理由不是"Steam 更好"，而是它的地址稳定（Steam 组常态一张、路径由 Steam 管理）；itch 版可能被用户换目录，兜底要挑一个下次还在的 |
| 何时问 | 两处：**①** 刷新后检测到情况 B 且该版本无偏好 → 置 pending，用户**进入版本库页**时弹一次；**②** **双击这张卡启动**时，若该版本跨渠道且仍没表态 → 先问、选完就按选择把它启起来（这次启动被拦下，等一句回答） |
| ① 与 ② 的关系 | ① 通常先命中（能双击卡片说明人已经在这页），② 是多版本并存（pending 只记一个）或 ① 被换页丢弃时的补充。两个入口共用 `needPrefAsk()` 一个判据 |
| 为什么打开工程时**不**问 | 刷新有三个触发点：启动可能是静默的（窗口都不显示）、启动工程前用户正等着进 PXC。这两处弹模态窗等于用他马上要做的事打断他，而且看不见卡片时问"哪张"没有上下文 |
| ② 被拦下后换页 | 放弃这次启动（弹窗随页面消失，此时再补启动就是"点了别处却突然起进程"），偏好不写，下次进这页还会问 |
| ① 的代价（已接受） | 一直不进这页就不问；兜底规则确定，启动照常，不会卡住 |
| 右键设置 | `设为默认启动 ▸ itch / Steam`，当前项打勾。**仅当该卡所属版本存在跨渠道同版本时**才画这一项（用户明确：没有同版本时右键不出现偏好项） |
| 偏好的一方被删 | 记录保留、不再起作用；同版本后来又出现 → 沿用旧偏好，不重复问 |
| 换了版本 | 不影响。偏好按版本号存，1.22 的选择不会带到 1.23 |

> 界面上**不显示"默认"字样或徽标**：那属于"自动的信息和说明文本"，与用户的口径冲突。
> 反馈放在**操作处**——右键菜单里打勾，这是"你刚做的操作生效了"，不是常驻说明。

## 11.7 Steam 版本变化：角标 + 说明（方案 A，已定）

变化信号：`channel == "steam" && !sameVersion(acked_version, product_version)`。

| 环节 | 行为 |
| --- | --- |
| 出现 | 刷新时发现 Steam 条目的 PE 版本 ≠ `acked_version` → 卡片右上角 16px accent 圆 + 白「!」 |
| 打开说明 | 点**角标或卡片**都行，开 `components::dialog`（360 宽）：标题「Steam 版版本已变化」，正文两段 —— `已从 1.20.1.0 变为 1.22.0.5。` / `Steam 自动更新，或你在 Steam 里切换了版本。工程文件的版本匹配、本机汉化骨架都按新版本计算。` |
| 确认 | 「知道了」→ `acked_version = product_version`，写盘，角标消失，重启不复现 |
| 关闭 / 取消 | 角标保留 —— 没确认就等于没看到，不能因为关了窗就当他已经知情 |
| 连续变化 | `acked_version` 不推进，所以说明里恒为「你上次确认的那一版 → 现在这一版」，不会只剩最后一次跳变 |

不做页顶提示条、不复用启动提示窗（重开这个判断的成本很高，理由记在这里）：提示条会变成常驻说明文字，
与「不展示说明文本」直接冲突；`pxc_toast` 只有启动语义、且 `WS_EX_NOACTIVATE` 一闪而过，讲不清"版本变了会怎样"。

> itch 卡片不参与这个提示：它的 exe 不会自己变。版本号变了说明用户自己换了那个目录里的文件，
> 那是他的动作，不需要我们提醒。

## 11.8 无法识别版本 = 全页唯一的弹窗

| 项 | 规格 |
| --- | --- |
| 触发 | 添加 / 刷新时，该 exe 的 PE 版本读不到（`GetFileVersionInfo` 失败或字段为空） |
| 形态 | `components::dialog`，320 宽，标题「无法识别当前 PXC 版本」，正文「请设置版本号」，一个输入框 + 「确定 / 取消」 |
| 文案 | 固定这两句，不加解释（用户明确："弹窗提示'无法识别当前 PXC 版本，请设置版本号'"） |
| 确定 | 空值不许提交；提交后 `source = "manual"`，卡片正常出现 |
| 取消 | 不登记（老版本的"取消后留在页面上等你填"要去掉） |
| 不弹的情况 | ① 已有版本号、只是这次读不到 → **保留旧值**，不弹（别因为一次读失败就把可信数据清掉）；② 条目已标记「丢失」 |

### 11.8.1 手动指定的版本号 = 锁定，刷新不许覆盖

**为什么必须有这一条**：PXC 自己的 PE 版本资源并不可靠。真机实测（2026-11-03）：

| 安装目录 | exe 的 `ProductVersion` | exe 内嵌数据包里的真版本 |
| --- | --- | --- |
| `PixelComposer 1.21.0.2` | `1.21.0.0` ❗ | `1.21.0.2` |
| `PixelComposer 1.19.0.11` | `1.19.0.11` | `1.19.0.11` |
| Steam `1.22.0.5` | `1.22.0.5` | `1.22.0.5` |
| `1.18.5` / `1.20.1` | `1.18.5.0` / `1.20.1.0` | 无四段串 |

即：1.21.0.2 那个包把版本资源的末段写成了 0。读 PE 资源只能拿到 1.21.0.0 —— 这不是读取 bug，
但**用户右键「设置版本号」改正之后，若下次刷新又被 PE 值盖回去，那一项就等于不存在**
（真机症状：日志里 `手动登记 版本=1.20.1.01` 紧跟一条 `版本变化：1.20.1.01 -> 1.20.1.0`）。

| 规则 | 说明 |
| --- | --- |
| 锁定条件 | `source == "manual"` |
| 刷新行为 | 仍校验存在性与渠道，**不**用 PE 值改 `product_version`；两者不同时只记一条 INFO 日志 |
| 解锁出口 | 右键「重新读取版本」→ 重读成功即 `source = "auto"`，恢复自动跟踪（这也是唯一的出口，别再另外加开关） |
| 修改已有条目 | `addManual` 只改 `product_version` 与 `source`，**保留** `registered_at` / `channel` / `acked_version`（整条覆盖会让同版本卡片乱跳、角标丢失） |
| 指纹 | `registrySignature()` 含 `source`：它决定"刷不刷新版本"，改了不落盘等于锁丢重启就没 |

### 11.8.2 内嵌数据包版本探测（自动纠正 PE 的谎）

既然 PE 会写错（§11.8.1 的表），就再找一个可信来源：**GM 数据包的字符串池**。
`pxc::readEmbeddedVersion(exe, peVersion)` 在字节流里找四段版本串，`pxc_reg::effectiveVersion()`
拿它和 PE 值比，**只取更大的那个**（版本号是骨架目录的键，改错比不准更糟）。

| 项 | 规格 |
| --- | --- |
| 输入 | `peVersion` 必须是纯四段；否则不猜，直接返回 PE 值 |
| 候选 | 四段、每段 1~5 位、无空段、前后不是数字/点；**主次版本必须与 PE 完全相同** |
| 取值 | 多个候选按数值取最大（`1.21.0.2` > `1.21.0.0`） |
| 触发条件 | **PE 末段为 0 才探测**（`1.21.0.0` / `1.20.1.0` / `1.18.5.0`）；`1.19.0.11`、`1.22.0.5` 末段非 0，PE 值本来就对，不浪费磁盘读 |
| 扫描顺序 | ① 同目录 `data.win`（≤32MB，数据包本体）→ ② exe 尾部 20% → ③ 尾部一个四段串都没有才回退整份 |
| manual 条目 | 不探测（用户裁定优先，§11.8.1） |

**实测（2026-11-04，本机）**

| 包 | 版本串位置 | PE 值 | 探测值 |
| --- | --- | --- | --- |
| 1.21.0.2 | 距文件尾 12.5% | 1.21.0.0 | **1.21.0.2** ✅ |
| 1.19.0.11 | 距尾 12.6% | 1.19.0.11 | 1.19.0.11（末段非 0，不探测） |
| Steam 1.22.0.5 | 距尾 12.6% | 1.22.0.5 | 1.22.0.5（同上） |
| 1.18.5 / 1.20.1 | 数据包里没有四段串 | 1.18.5.0 / 1.20.1.0 | 保持 PE 值 |

**成本**（这是设计这套东西时唯一真正的约束）

| 场景 | 耗时 |
| --- | --- |
| 首次（缓存空，3 条要扫，走 data.win） | **178~410ms**（热盘）/ 估计 ~0.6s（冷盘） |
| 首次但只有内嵌数据包（无 data.win，如 Steam 版） | 每条 ~200~300ms（扫 exe 尾部 20%） |
| 之后每次刷新 | **4~5ms**，探测 0 |

**缓存**：`<userdata>/version_probe.json`，键 = 路径 + 文件大小 + 修改时间，三者任一变了才重扫。
启动时 `pxc_probe::load()`，每次刷新末尾 `flush()`（有改动才写）。

> ⚠️ `size` / `mtime` 在缓存里存**字符串**不是 JSON 数字：`store.cpp` 的数字序列化是 `%.10g`，
> 13 位的毫秒时间戳会被截成 `1.337820025e+12`，读回来永远和真实值不等 → 缓存永久失效。
> 第一版就是这么踩的，日志里表现为"每次启动都探测 2~3 条"。

**不做的事**：不解析 GM 的 chunk（STRG/EXIT 等）结构 —— 那玩意随 GameMaker 版本变，
解析失败就是读出个假版本号。这里只做"字节流里找四段串 + 严格的版本语义约束"，
最坏结果是**读不到**（退回 PE 值），不会读出错的。

## 11.16 第一轮反馈后的调整（2026-11-02 晚）

### 11.16.1 询问偏好：加第二个触发点（双击卡片启动）

用户口径：「启动工程不被打断」这条保留，但**启动相关版本、又没设偏好时也要问**。
落地为 `launchRegistryExe()` 入口拦截：

| 环节 | 做法 |
| --- | --- |
| 判据 | `needPrefAsk(version)` —— 跨渠道同版本 **且** `prefer` 里连键都没有（三态只认"没问过"） |
| 拦截 | 记下 `g_prefLaunchExe`，开询问窗，**这次不启动** |
| 选完 | `resumePrefLaunch(version)`：按 `prefer` 用 `choosePreferred()` 挑 exe 再起 —— 选 itch 就起 itch 那份，不是"起完再告诉他" |
| 稍后决定 / 关掉 | 写空串（问过不表态），**照样起**，走兜底（Steam 优先） |
| 中途换页 | 丢掉这次启动（`g_prefLaunchExe.clear()`）。此时补启动就是"点了别处却突然起进程"；偏好没写，下次进这页还会问 |
| 打开工程 | **不问**：`wbLaunchPath` / `openVersionPicker` 只用 `choosePreferred` 静默挑，不弹窗 |

**①进页问 与 ②双击问 的先后**：能双击卡片说明人已经在这页，所以 ① 通常先命中；
② 在多版本并存（`g_prefAsk` 只记一个）或 ① 被换页丢弃时才轮得到。两个入口共用同一个 `needPrefAsk`。

真机验证（构造 `tmp/regtest` 里一份 1.22.0.5 当 itch，凑出跨渠道同版本、`prefer` 为空）：

### 11.16.2 刷新按钮：图标 + 「刷新」

只放图标时 FA 字形在 em 框里的留白不匀、又没有文本作参照，看起来是歪的。改成 `icon(0xF021) + text("刷新")`，

### 11.16.3 修掉一个真 bug：登记表指纹的基准取错了

上一轮加的「登记表没变就不写盘」守卫，把基准取成**进 `refreshRegistry()` 那一刻**的快照：

```cpp
const std::string before = registrySignature();   // 错：addExe 已经改完了
... refreshAll ...
if (registrySignature() != before) saveConfig();
```

`addExe` / `removeExe` / `resolveDup` 都是**先改 `g_cfg.registry` 再调 refreshRegistry**，
于是 `before` 已经是改完的签名，前后一样 → **永远不写盘**。真机表现：新登记的 exe 一重启就没了
（`launcher.json` 一直是 4 条，日志却是"重读 5"）。

修法：基准改成「上次落盘时的签名」`g_regSavedSig`，由 `saveConfig()` 自己维护；`initOnce()` 读完配置后
先 `g_regSavedSig = registrySignature()` 定基准，避免首帧白写一次。

| 验证 | 结果 |
| --- | --- |
| 加一条 itch 1.22.0.5 → 重启看文件 | 5 条、`prefer` 为空 ✅（修前恒定 4 条） |
| 什么都不做直接启动 → 看 mtime | 不变 ✅（守卫本来要解决的"每次启动都重写"仍然成立） |

> 教训：这类"只在变了才写"的守卫，基准必须是**外部持久状态**（上次落盘的值），
> 不能是"函数入口的快照" —— 只要存在"调用方先改数据再调我"的用法，入口快照就恒等于当前值。

| 5 | 丢失态 | 三处一起变：版本号转灰、渠道标签变红「丢失」、图标降透明度；条目**不删**，右键仍有「删除」 |

### 11.17.1 「偏好」与「版本变化」的交互（回答"Steam 更新后会不会用错版本启动"）

结论：**不会，也不需要**——偏好在版本匹配之后才起作用。

| 步 | 发生什么 |
| --- | --- |
| 1 | Steam 自动更新到 `1.23.0.x`，下次刷新把那条 Steam 条目的 `product_version` 改成新值，角标亮 |
| 2 | 打开一个 `1.22.0.5` 的工程 → `findMatching(registry, "1.22.0.5")` **只按版本精确匹配**，Steam 那条已不在结果里 |
| 3 | 命中只剩 itch 的 `1.22.0.5` → 直接用 itch 启动。`prefer["1.22.0.5"] = "steam"` **根本没参与判断**（它只在同版本命中的多条之间做取舍） |
| 4 | 若 itch 那份也不在了 → 命中为空 → 走协商弹窗（推荐最近版本 + 「跨结构打开会损坏文件」警告），**不会静默用 1.23 打开** |

也就是说：**防"用错版本打开"是版本匹配的职责，偏好只负责"同版本时用哪个渠道"**。两件事不要混。

唯一需要留意的边界：偏好里那条记录会一直留着（指向一个已经不存在的版本/渠道），
`choosePreferred` 只在 `matches` 内挑，所以不会挑到不存在的 exe —— 记录陈旧但不产生错误行为。
